# 0. 문서 정보

이 문서는 Sigkill Foundry의 설계 문서다. 스펙 주도 개발(SDD)을 따른다 — 구현은 이 명세에서
도출하고, 명세와 코드가 어긋나면 명세를 먼저 고친 뒤 코드를 맞춘다.

## 문서 구성

설계 문서는 다섯 문서로 이어진다. 문서마다 하나의 질문에 답하고, 앞 문서의 답이 뒤 문서의 입력이 된다.

| 번호 | 문서 | 답하는 질문 |
| --- | --- | --- |
| 1 | 프로젝트 제안서 | 왜 만들고, 무엇을 어디까지 하는가 |
| 2 | 요구사항 명세서 | 무엇을 만족해야 하는가 |
| 3 | 아키텍처 설계서 | 어떻게 구성되고 동작하는가 |
| 4 | 구현 계획서 | 어떤 순서로 만들고, 무엇으로 판정하는가 |
| 5 | 구현 결과 보고서 | 무엇을 만들었고, 판정은 어떻게 나왔는가 |

장은 `문서 번호.장 번호`로 가리킨다 (예: 3.05 설계 결정). 장 안의 절은 `§`로 가리킨다 (예: 3.03 §1).

## 규범 용어

| 표현 | 뜻 |
| --- | --- |
| 반드시 ~한다 (MUST) | 어기면 명세 위반이다 |
| ~해야 한다 (SHOULD) | 어길 때는 이유를 3.05 설계 결정에 남긴다 |
| ~할 수 있다 (MAY) | 선택 사항이다 |

## 요구사항 표기

- 목표는 `G-<번호>`로 식별하고 1.03 목표와 범위에 둔다.
- 요구사항은 `<영역>-<세 자리 번호>`로 식별한다. 번호는 재사용하지 않는다.
- 영역: `ORC`(오케스트레이터) · `RAIL`(claude-rails) · `TRL`(커밋 트레일러) · `BL`(backlog.md 규약)은 2.03 기능 요구사항에, `NFR`(품질)은 2.04 품질 요구사항에 둔다.
- 모든 요구사항은 수용 기준을 하나 이상 가진다(4.02).
- 아직 정하지 않은 값은 `TBD(Q-n)`으로 적고, `Q-n`을 4.03 미결 사항에 둔다.

## 추적 규칙

모든 요구사항은 다음 사슬로 앞뒤가 이어진다. 사슬이 끊긴 항목은 둘 수 없다.

1. 제안서 목표 `G-n` (1.03)
2. → 요구사항 `<영역>-nnn` (2.03 · 2.04) — 요구사항은 자신이 이바지하는 `G-n`을 적는다.
3. → 부품 · 인터페이스 (3.03 · 3.04) — 부품 명세는 자신이 구현하는 요구사항 ID를 적는다.
4. → 수용 기준 (4.02) · backlog 태스크 (4.01) — 요구사항 하나는 backlog 태스크의 AC로 내려간다. 태스크 카드는 자신이 구현하는 요구사항 ID를 적는다.
5. → 결과 판정 (5.02) — 수용 기준마다 통과/실패와 그 증거(테스트 로그 · 실측)를 남긴다.

- 원칙(1.02)에 어긋나는 요구사항은 둘 수 없다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.
- 계획과 다르게 구현한 것은 5.03 계획 대비 편차에 적고, 해당 설계 결정(3.05)에 연결한다.

- 한 장 = 한 문서. 편집 원본은 Claude 앱의 문서이고, 저장소의 `design/**/*.md`는 Claude가 동기화하는 사본이다.
