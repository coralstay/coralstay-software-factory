# 0. 문서 정보

이 문서는 Sigkill Foundry의 설계 문서다. 스펙 주도 개발(SDD)을 따른다 — 구현은 이 명세에서
도출하고, 명세와 코드가 어긋나면 명세를 먼저 고친 뒤 코드를 맞춘다.

## 문서 구성

설계 문서는 다섯 문서로 이어진다. 문서마다 하나의 질문에 답하고, 앞 문서의 답이 뒤 문서의 입력이 된다.

| 번호 | 문서 | 답하는 질문 |
| --- | --- | --- |
| 1 | 프로젝트 제안서 | 왜 만들고, 무엇을 어디까지 하는가 |
| 2 | 요구사항 명세서 | 무엇을 만족해야 하는가 |
| 3 | 아키텍처 설계서 | 어떻게 구성되고 동작하는가 |
| 4 | 구현 계획서 | 어떤 순서로 만들고, 무엇으로 판정하는가 |
| 5 | 구현 결과 보고서 | 무엇을 만들었고, 판정은 어떻게 나왔는가 |

장은 `문서 번호.장 번호`로 가리킨다 (예: 3.05 설계 결정). 장 안의 절은 `§`로 가리킨다 (예: 3.03 §1).

## 규범 용어

| 표현 | 뜻 |
| --- | --- |
| 반드시 ~한다 (MUST) | 어기면 명세 위반이다 |
| ~해야 한다 (SHOULD) | 어길 때는 이유를 3.05 설계 결정에 남긴다 |
| ~할 수 있다 (MAY) | 선택 사항이다 |

## 요구사항 표기

- 목표는 `G-<번호>`로 식별하고 1.03 목표와 범위에 둔다.
- 요구사항은 `<영역>-<세 자리 번호>`로 식별한다. 번호는 재사용하지 않는다.
- 영역: `ORC`(오케스트레이터) · `RAIL`(claude-code-agile-hooks) · `TRL`(커밋 트레일러) · `BL`(backlog.md 규약)은 2.03 기능 요구사항에, `NFR`(품질)은 2.04 품질 요구사항에 둔다.
- 모든 요구사항은 수용 기준을 하나 이상 가진다(4.02).
- 아직 정하지 않은 값은 `TBD(Q-n)`으로 적고, `Q-n`을 4.03 미결 사항에 둔다.

## 추적 규칙

모든 요구사항은 다음 사슬로 앞뒤가 이어진다. 사슬이 끊긴 항목은 둘 수 없다.

1. 제안서 목표 `G-n` (1.03)
2. → 요구사항 `<영역>-nnn` (2.03 · 2.04) — 요구사항은 자신이 이바지하는 `G-n`을 적는다.
3. → 컴포넌트 · 인터페이스 (3.03 · 3.04) — 컴포넌트 명세는 자신이 구현하는 요구사항 ID를 적는다.
4. → 수용 기준 (4.02) · backlog 태스크 (4.01) — 요구사항 하나는 backlog 태스크의 AC로 내려간다. 태스크 카드는 자신이 구현하는 요구사항 ID를 적는다.
5. → 결과 판정 (5.02) — 수용 기준마다 통과/실패와 그 증거(테스트 로그 · 실측)를 남긴다.

- 원칙(1.02)에 어긋나는 요구사항은 둘 수 없다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.
- 계획과 다르게 구현한 것은 5.03 계획 대비 편차에 적고, 해당 설계 결정(3.05)에 연결한다.

## 문서 계층

설계 문서는 최상위 한 곳(이 저장소의 `design/`)과 컴포넌트 세 곳(각 컴포넌트 저장소의 `design/`)에 나뉜다.

- 컴포넌트는 `components/<이름>`에 두는 독립 git 저장소다. 최상위 `.gitignore`가 `components/`를 제외하고, 최상위는 컴포넌트 파일을 하나도 추적하지 않는다. 서브모듈이 아니다(`.gitmodules` 없음).
- 최상위는 목표 `G-n`(1.03) · 원칙(1.02) · 요구사항 ID(2.03 · 2.04)를 소유한다. 요구사항 ID는 최상위에서만 부여한다.
- 컴포넌트 `design/`은 최상위를 상위 문서로 둔다. 원칙을 상속하고, 요구사항을 같은 ID로 이어받아 패키지 · 클래스 · 결정 · 테스트로 내린다. 최상위 결정을 어겨야 하면 최상위 결정을 먼저 고친다.
- 명세를 저장소마다 두는 이유는 3.05 ADR-025에 있다. 명세와 코드가 같은 저장소에 있어야 SDD(명세를 먼저 고친다)가 같은 PR 안에서 성립하고, 에이전트가 그 저장소의 `design/`을 조상 문서로 읽는다(ORC-019).
- 최상위를 고치면 아래 장 대응표로 영향받는 컴포넌트 `design/`을 같이 고친다(편집 규칙, RAIL-024).

### 장 대응표

최상위 장을 고치면 같은 행의 컴포넌트 장이 영향받는 장이다. claude-code-agile-hooks의 전파 강제 훅이 이 표를 읽는다(RAIL-024). 형식 규칙은 다음과 같다.

- `최상위 장`: `00`은 `design/00-문서-정보.md`, `N.MM`은 `design/N-*/MM-*.md`, `부록 <이름>`은 이름의 공백을 `-`로 바꾼 `design/부록-<이름>.md`다.
- `범위`: `전체`는 장 전체다. `§n`은 제목이 `## §n`으로 시작하는 절, 영역 접두어(`ORC` · `RAIL` · `TRL` · `BL`)는 2.03에서 제목이 그 접두어로 시작하는 절이다. 절 밖(장 머리 · `## 원천`)을 고치면 그 장의 모든 행에 해당한다.
- 컴포넌트 열 머리는 `components/<이름>`의 디렉토리 이름과 같다. 칸에는 그 컴포넌트 `design/`의 장을 같은 표기로 ` · `로 나눠 적고, 대응 장이 없으면 `—`를 적는다.
- 행을 더하거나 칸을 고칠 때 훅은 고치지 않는다. 열 구성이나 칸 표기를 바꾸려면 claude-code-agile-hooks DRAFT-13의 훅을 먼저 맞춘다.

## 편집 규칙

- 설계 내용의 원본은 저장소의 `design/**/*.md` 하나다. 다른 곳(Claude 앱 문서 · 위키 등)에 사본이나 편집 원본을 두지 않는다. 고칠 때는 이 파일을 직접 고치고(Claude Code · GitHub 편집기) 커밋 · PR로 남긴다. 오케스트레이터가 띄우는 에이전트도 이 파일을 조상 문서로 읽는다(ORC-019).
- 한 장 = 한 문서. 같은 내용을 두 장에서 고치고 있다면 한쪽을 장 참조 한 줄로 접는다.
- 최상위 `design/`을 고친 변경은 문서 계층의 장 대응표로 찾은 영향받는 컴포넌트 `design/`을 반드시 같이 고친다. 컴포넌트 쪽 변경은 각 컴포넌트 저장소에 같은 태스크 ID로 커밋한다. 영향이 없으면 그 사유를 반드시 남긴다. 사유 기록 형식은 미정 — claude-code-agile-hooks DRAFT-13에서 확정 (RAIL-024, 3.05 ADR-025).
- 외부 문헌의 수치는 종속변수가 같은지 확인한 뒤에만 근거로 쓴다. 인용과 검증 상태는 부록 참고 문헌에서만 관리한다.
- 다이어그램 원본은 `design/diagrams/*.dot`이다. DOT으로 먼저 쓰고, DOT으로 표현할 수 없는 것(시퀀스 등)만 mermaid(`.mmd`)로 쓴다.
- `design/build-diagrams.py`가 원본을 `design/diagrams/<이름>.svg`로 렌더한다. 색은 원본에 센티넬 hex로 적고, 빌드가 SVG 안의 CSS 변수(라이트 기본 · 다크 재정의)로 바꾼다. 빌드 전제: graphviz(`dot`), mermaid 렌더용 `npx` + 로컬 Chrome.
- 생성된 SVG는 손으로 고치지 않는다. 원본을 고치고 빌드를 다시 돌려 같은 커밋에 넣는다. 장 사본은 `![설명](../diagrams/<이름>.svg)`로 참조한다.
- 저장소 Markdown의 외부 링크는 문서 맨 아래 링크 정의 블록에 모으고, 본문은 `[표시][키]`로만 쓴다.
