# 1.02 원칙

이 설계 문서의 모든 요구사항이 따라야 하는 불변 규칙이다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.

| ID | 원칙 | 근거 |
| --- | --- | --- |
| P1 | **판단의 독립성.** 판정 역할(Reviewer · Verifier)은 구현 역할(Implementer)의 컨텍스트를 반드시 물려받지 않는다. | 같은 맥락 안의 자기검토는 그 맥락이 만든 오류를 구조적으로 놓친다. 필요한 것은 다른 프롬프트가 아니라 다른 컨텍스트다 |
| P2 | **컨텍스트 경계 = 프로세스 경계.** 역할마다 반드시 별도 `claude -p` 프로세스로 띄운다. 역할 사이의 전달은 텍스트 산출물(커밋 · 태스크 카드 · 파일)로만 한다. | Claude Code에서 세션 간 전달은 순수 텍스트뿐이고 이력 · 파일은 따라가지 않는다 ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging)) |
| P3 | **회수는 kill이다.** 태스크가 끝나면 역할 프로세스와 그 자손을 SIGTERM → 유예 → SIGKILL로 반드시 끝내고, Registry에서 지우고, 동시성 허가를 반납한다. 상시 대기하는 장수 세션을 두지 않는다. | 헤드리스 세션은 종료가 곧 컨텍스트 폐기다. 단일 지속 에이전트는 작업량이 늘면 정확도가 73.1% → 16.6%로 무너졌다 ([npj Health Systems](https://www.nature.com/articles/s44401-026-00077-0)) |
| P4 | **최종 게이트는 하나다.** Reviewer는 의견을 내고, Verifier 하나가 최종 판정한다. | 판정자가 여럿이면 판정이 갈리고, 수렴 지점이 없으면 AC 루프가 끝나지 않는다 |
| P5 | **판정기는 유한하고 결정적이다.** 통과 기준은 프로젝트가 정한 AC · DoD · 테스트로만 표현한다. 오케스트레이터는 그 결과의 Exit Code만 본다. | 임의의 명세 충족을 판정하는 일반 절차는 없다(결정문제, Turing 1936 §11) |
| P6 | **레일은 규율, 에이전트는 자발성.** 강제할 것은 훅 · 게이트로 강제하고, 그 안의 방법은 에이전트에게 남긴다. 레일은 필요한 만큼만 깐다. | "discipline is certainly not enough in itself to produce intelligence" (Turing 1948 §12) |
| P7 | **계층은 코드 단위에 고정된다.** 태스크 = 파일, AC = 함수, 커밋 = 함수, 에이전트 배정 = 파일. | 파일이 격리 단위이면 두 에이전트가 같은 파일을 만질 일이 구조적으로 없고, 토큰 계량이 함수 단위로 붙는다 |
| P8 | **판단 단위는 태스크다.** 4역할 적용 여부는 프로젝트가 아니라 태스크마다 정한다. | 단순하게 시작한 프로젝트도 이후 태스크는 어려워질 수 있다 |
| P9 | **경계선은 측정해서 정한다.** 임계값 · 경계선을 외부에서 빌려오지 않는다. 측정이 없는 값은 `TBD`로 남긴다. | 4역할의 효용은 아직 어떤 문헌으로도 뒷받침되지 않았다 |

## 반증 기준

Implementer 단독 + self-review 대비 4역할 구조가 AC 재작업률과 회귀 발생률을 유의미하게 낮추지
못하면, P1 · P2를 다시 검토한다 — Reviewer · Verifier를 별도 프로세스가 아니라 Implementer 세션 안의
단계로 접는 안을 3.05 설계 결정에 올린다. 측정 방법은 4.02 수용 기준과 검증에 있다.
