# 1.02 원칙

이 설계 문서의 모든 요구사항이 따라야 하는 불변 규칙이다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.

| ID | 원칙 | 근거 |
| --- | --- | --- |
| P1 | **판단의 독립성.** 판정 역할(Reviewer · Verifier)은 구현 역할(Implementer)의 컨텍스트를 반드시 물려받지 않는다. | 같은 맥락 안의 자기검토는 그 맥락이 만든 오류를 구조적으로 놓친다 — 틀린 전제를 공유한 채 결론만 다시 읽기 때문이다. 필요한 것은 다른 프롬프트가 아니라 다른 컨텍스트다(1.01 논증 사슬 1~2, 자체 논증) |
| P2 | **컨텍스트 경계 = 프로세스 경계.** 역할마다 반드시 별도 `claude -p` 프로세스로 띄운다. 역할 사이의 전달은 텍스트 산출물(커밋 · 태스크 카드 · 파일)로만 한다. | Claude Code에서 세션 간 전달은 순수 텍스트뿐이고 이력 · 파일은 따라가지 않는다 ([Cross-session messaging](https://code.claude.com/docs/en/cross-session-messaging), 부록 참고 문헌 [25]; 1.01 논증 사슬 3, 도구 사실). 독립 프로세스면 각 프로세스 종료 시 자기 몫의 토큰 사용량만 딱 떨어지게 나온다 — 세션 내 위임이면 부모 · 자식 사용량이 한 응답에 섞인다(자체 논증, 가장 견고한 근거의 하나) |
| P3 | **회수는 kill이다.** 태스크가 끝나면 역할 프로세스와 그 자손을 SIGTERM → 유예 → SIGKILL로 반드시 끝내고, Registry에서 지우고, 동시성 허가를 반납한다. 상시 대기하는 장수 세션을 두지 않는다. | 헤드리스 세션은 종료가 곧 컨텍스트 폐기다 — 대화형 `/clear`를 보낼 단계가 없다. 단일 지속 에이전트는 작업량이 늘면 정확도가 73.1% → 16.6%로 무너졌다 ([npj Health Systems](https://www.nature.com/articles/s44401-026-00077-0), 부록 참고 문헌 [21]; 1.01 논증 사슬 5, 외부 근거 — 범위는 정확도 · 토큰까지) |
| P4 | **최종 게이트는 하나다.** Reviewer는 의견을 내고, Verifier 하나가 최종 판정한다. | 판정자가 여럿이면 판정이 갈리고, 수렴 지점이 없으면 AC 루프가 끝나지 않는다. 격리는 판단을 독립시키기 위한 것이지 결정을 분산시키기 위한 것이 아니다(1.01 논증 사슬 6, 자체 논증) |
| P5 | **판정기는 유한하고 결정적이다.** 통과 기준은 프로젝트가 정한 AC · DoD · 테스트로만 표현한다. 오케스트레이터는 그 결과의 Exit Code만 본다. | 임의의 명세 충족을 판정하는 일반 절차는 없다 — "Hence the Entscheidungsproblem cannot be solved."(Turing 1936 §11 p.262, 부록 참고 문헌 [32]). §11이 부정한 것은 일반 절차뿐이고, 프로젝트가 스스로 정한 유한한 판정기는 만들 수 있다. AC(개별 완료 조건)와 DoD(공통 완료 기준)의 구분은 backlog.md가 `--check-ac` · `--check-dod`로 이미 제공한다(부록 참고 문헌 [27]; 1.01 논증 사슬 7, 원리적 제약) |
| P6 | **레일은 규율, 에이전트는 자발성.** 강제할 것은 훅 · 게이트로 강제하고, 그 안의 방법은 에이전트에게 남긴다. 레일은 필요한 만큼만 깐다. | "discipline is certainly not enough in itself to produce intelligence. That which is required in addition we call initiative."(Turing 1948 §12 p.431, 부록 참고 문헌 [33]). CLAUDE.md에 적는 약속만으로는 프롬프트 인젝션 · 컨텍스트 압축으로 깨질 수 있어 기계적으로 강제한다. 백로깅 재진입 조건은 claude-code-agile-hooks의 운영 규칙과 일치하고 조용한 스코프 확장을 구조적으로 막는다 |
| P7 | **계층은 코드 단위에 고정된다.** 태스크 = 파일, AC = 함수, 커밋 = 함수, 에이전트 배정 = 파일. | 파일이 격리 단위이면 워크트리를 분리했을 때 두 에이전트가 같은 파일을 만질 일이 구조적으로 없고, 커밋이 함수 단위이므로 토큰 계량이 함수 단위로 붙는다. 태스크당 최소 커밋 수가 배정 전에 AC 개수로 세어진다 |
| P8 | **판단 단위는 태스크다.** 4역할 적용 여부는 프로젝트가 아니라 태스크마다 정한다. | 단순하게 시작한 프로젝트(Next.js 스캐폴드, Spring+DB 단순 CRUD)도 이후 태스크는 어려워질 수 있다. 4역할 부착은 속도로 정당화하지 않으므로, 판정 독립성이 값을 하는 태스크에만 붙인다(1.03) |
| P9 | **경계선은 측정해서 정한다.** 임계값 · 경계선을 외부에서 빌려오지 않는다. 측정이 없는 값은 `TBD`로 남긴다. | 4역할의 효용은 아직 어떤 문헌으로도 뒷받침되지 않았다. 멀티에이전트 조율의 손익을 다룬 연구가 재는 것은 과제 정확도이고 이 설계가 내세우는 것은 판단의 독립성이라 종속변수가 다르다(부록 참고 문헌 [22] · [23]). 배정 시점에는 그 태스크의 단일 에이전트 기준 성공률을 알 수 없다 |

## 원칙이 겨냥하는 것 — 목적은 자동화가 아니다

이 설계가 파는 것은 처리량도, "지시만 던지면 나오는 소프트웨어"도 아니다. **Reviewer와 Verifier가
Implementer의 추론 경로를 물려받지 않게 만드는 것**이다. 컨텍스트 격리가 곧 게이트이고, 격리를
유지하는 비용(프로세스 분리, 조상 문서 재로딩)은 그 독립성의 값으로 지불한다.

- 한 태스크에 네 역할을 붙이는 선택은 속도로 정당화하지 않는다(P1 · P8).
- 처리량은 태스크 *사이*에서만 추구한다. 태스크 안과 태스크 사이는 층위가 다르다(2.04).

## 규율과 자발성 — 튜링의 어휘

튜링은 1948년 NPL 보고서 *Intelligent Machinery*(부록 참고 문헌 [33])에서 구조가 대체로 무작위한
기계를 비정형 기계(unorganised machine)라 부른다. LLM은 이 계보의 기계이고, 그런 기계의 보편성은
무조건이 아니라 조건부다.

| 인용 | 위치 | 이 설계에서의 쓰임 |
| --- | --- | --- |
| "Machines which are largely random in their construction in this way will be called 'Unorganised Machines'." | 1948 §4 Unorganised machines · *The Essential Turing* p.417 | LLM을 비정형 기계로 본다 |
| "with a B-type unorganised machine with sufficient units one can find initial conditions which will make it into a universal machine with a given storage capacity" | 1948 §8 Organising unorganised machinery · p.423 | 보편성은 조건(초기 조건 = 레일)에 달렸다 |
| "To convert a brain or machine into a universal machine is the extremest form of discipline. But discipline is certainly not enough in itself to produce intelligence. That which is required in addition we call initiative." | 1948 §12 Discipline and initiative · p.431 | **레일이 규율이고, 에이전트가 자발성이다**(P6) |
| "Hence the Entscheidungsproblem cannot be solved." | 1936 §11 Application to the Entscheidungsproblem · p.262 | 일반 판정 절차는 없고 프로젝트별 유한 판정기만 있다(P5) |

훅 · 테스트 게이트 · 워크트리 격리 · 상태 전이 규칙은 전부 규율 쪽이고, 그 안에서 무엇을 어떻게
쓸지는 에이전트에게 남긴다. 그래서 이 설계의 질문은 "얼마나 자동화할 것인가"가 아니라 **"레일을
어디까지만 깔 것인가"** 다 — 규율을 끝까지 밀면 자발성이 사라진다는 경고가 §12 문장에 이미 들어
있다. 판정기를 코드로 쓸 수 있는 자리에서는 사람이 판정 루프에 앉아 있을 이유가 없다는 것이 이
설계의 좁은 주장이다. 1936년 논문 §6의 보편 기계 결과는 배경일 뿐 근거가 아니다.

**인용의 한계.** 튜링의 두 논문은 이 설계에 어휘와 문제 설정을 줄 뿐, 4역할 구조가 효과가 있다는
증거가 아니다. 그 효과는 이 설계가 직접 측정한다(P9 · 4.02). 위 인용문은 B. J. Copeland 편
『The Essential Turing』(Oxford, 2004, 부록 참고 문헌 [34])의 수록 원문과 페이지 단위로 대조했다.

## 근거의 강도

원칙의 근거는 종류가 다르다. 종류를 구분해야 사슬이 끊기는 지점이 보인다(1.01 논증 사슬).

| 종류 | 원칙 |
| --- | --- |
| 자체 논증 | P1 · P4 · P7 · P8 |
| 도구 사실(공식 문서 확인) | P2 · P3(종료 = 컨텍스트 폐기) |
| 외부 근거(범위 한정) | P3(장수 세션 붕괴 — 정확도 · 토큰까지) |
| 원리적 제약 | P5 |
| 방법 원칙 | P6 · P9 |

독립 검증에서도 흔들리지 않은 근거는 다음과 같다.

- **토큰 측정 방식** — coding-agent-git-commit-tool 원본 코드를 직접 읽고 델타 커서 · 실패 투명성 패턴을 가져왔으며, 원저자가 밝힌 근사치 한계까지 반영해 확정이 아니라 미정으로 둔다(3.03 §3).
- **AC와 DoD의 구분** — 개념적으로 정확하고 backlog.md 기능으로 뒷받침되며, Verifier를 DoD · AC 두 갈래로 나누는 근거다(P5).
- **부트스트랩 순서** — 인용 없이 실제 의존성(CLI가 없으면 명령이 존재하지 않음)에서 직접 도출된다(3.02).
- **독립 프로세스가 토큰 귀속을 쉽게 만든다** — 외부 인용 없이 스스로 선 논증이다(P2).
- **학술 인용 3건** — arXiv 2509.06216, IEEE 11343819, MetaGPT ICLR 2024(부록 참고 문헌 [6] · [7] · [9]) 모두 원문 대조로 확인했다.
- **백로깅 재진입 조건** — claude-code-agile-hooks 운영 규칙과 일치하고 조용한 스코프 확장을 구조적으로 막는다(P6 · 3.02).

## 반증 기준

Implementer 단독 + self-review 대비 4역할 구조가 AC 재작업률과 회귀 발생률을 유의미하게 낮추지
못하면, P1 · P2를 다시 검토한다 — Reviewer · Verifier를 별도 프로세스가 아니라 Implementer 세션 안의
단계로 접는 안을 3.05 설계 결정에 올린다. 측정 방법은 4.02 수용 기준과 검증에 있고, "유의미하게"의
기준은 TBD(Q-11)이다.
