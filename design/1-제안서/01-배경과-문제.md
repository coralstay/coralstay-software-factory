# 1.01 배경과 문제

**Sigkill Foundry** — Claude Code 세션을 찍어내고 `kill -9`로 끊어내는 소프트웨어 공장.

## 무엇을 하는가

소프트웨어 태스크를 `backlog.md` 계층(마일스톤 · 태스크 · AC)으로 분해하고, 태스크마다 역할형
Claude Code 에이전트(Implementer · Reviewer · Verifier · Logger)를 독립된 `claude -p` 프로세스로
띄운 뒤, 태스크가 끝나면 프로세스째 죽여서 회수한다. JVM 오케스트레이터가 외부에서 정책을 주입해
스폰과 회수를 맡고, 에이전트는 레일(훅 · 테스트 게이트 · 커밋 계측) 위에서만 일한다.

## 출발 질문 — 왜 · 언제 · 어떻게 · 얼마나

이 설계는 방어할 결론을 정해두고 근거를 모은 것이 아니다. 출발점은 질문 하나다 —
**에이전트 모델을 왜 · 언제 · 어떻게 · 얼마나 써야 하는가?**

| 질문 | 답 | 장 |
| --- | --- | --- |
| **왜** | 처리량이 아니라 **판단의 독립성**. Reviewer · Verifier가 Implementer의 추론을 상속받지 않도록 컨텍스트 격리 자체를 게이트로 쓴다 | 이 장 · 1.02 P1 |
| **언제** | 단일 에이전트가 이미 안정적으로 해내는 태스크에는 쓰지 않는다. 판단 단위는 프로젝트가 아니라 태스크이고, 경계선은 빌려오지 않고 직접 측정한다. 여러 태스크가 동시에 Ready면 의존성 · 파일 결합이 있는 것만 순차, 나머지는 병렬이다 | 1.03 · 2.04 |
| **어떻게** | 네 역할을 완전히 독립된 프로세스로 두고, JVM 오케스트레이터가 정책을 외부에서 주입해 스폰 · 회수한다 | 3.02 · 3.03 §1 |
| **얼마나** | 역할 수 · 모델은 Allocation Policy가 노드와 상태를 보고 정한다. 동시성 상한은 `min(그래프 폭, 자원 실측(peak RSS · API 한도))`이고, 순차 그래프의 **길이(임계 경로)** 와 **폭(동시 배정 가능 태스크 수)** 을 스케줄 라운드마다 센다 | 2.04 · 3.03 §1 |

## 문제 — 같은 맥락 안의 자기검토

LLM은 확률적 기계다. 같은 맥락 안에서 이뤄지는 자기검토는 그 맥락이 만든 오류를 구조적으로
놓친다 — 틀린 전제를 공유한 채 결론만 다시 읽기 때문이다. 같은 세션 안에서 단계만 나누는 방식은
대화 이력을 그대로 공유하므로 이 문제를 풀지 못한다. 필요한 것은 다른 프롬프트가 아니라 **다른
컨텍스트**다.

긴 세션 하나에 모든 일을 시키는 방식도 답이 아니다. 임상 규모 워크로드 실험에서 단일 지속
에이전트는 작업량이 늘자 정확도가 73.1% → 16.6%로 무너졌고, 오케스트레이션된 다중 에이전트는
90.6% → 65.3%로 버텼으며(p<0.01) 토큰은 최대 65배 적었다(부록 참고 문헌 [21]). 이 근거는 도메인이
임상이고 측정한 것이 정확도 · 토큰이므로, "장수 세션보다 태스크 단위 스폰 · 회수가 낫다"는 데에만
쓴다. 판단 독립성 자체의 값은 이 설계가 직접 측정한다(4.02).

### 이 구조가 맞지 않는다는 출처

| 출처 | 주장 |
| --- | --- |
| Anthropic 멀티에이전트 리서치 시스템(부록 참고 문헌 [1]) | 모든 에이전트가 같은 컨텍스트를 공유해야 하거나 에이전트 간 의존성이 많은 도메인은 멀티에이전트에 안 맞는다 |
| Andrew Ng, Multi-Agent Collaboration(부록 참고 문헌 [2]) | 멀티에이전트 협업의 결과 품질은 예측하기 어렵다 |
| Claude Code Agent Teams 문서(부록 참고 문헌 [3]) | 순차적 작업 · 동일 파일 편집 · 의존성 많은 작업에는 단일 세션 · Subagent가 낫다 |

이 설계는 셋 다 해당한다. 역할 넷이 같은 조상 문서를 읽는 것은 컨텍스트 공유 요구이고,
Implementer → Reviewer → Verifier는 강한 순차 의존이다. 그래도 이 구조를 쓰는 이유는 처리량 ·
병렬성이 아니라 판단의 독립성이며, 세 출처 중 어느 것도 이 목적을 반박하지 않는다. [1]이 경고하는
워크로드는 병렬 리서치용이라 비교 대상이 다르다. [2]의 경고(자유 상호작용 시 품질 예측 불가)는
이 설계가 자유 대화형이 아니라 고정 순서 · 고정 트리거 파이프라인인 이유다(3.02).

## 논증 사슬

이 구조가 서는 순서다. 단계마다 근거의 종류를 적는다 — 외부 근거인지, 스스로 선 논증인지, 아직
검증되지 않은 가정인지 구분하지 않으면 사슬이 어디서 끊기는지 보이지 않는다.

| # | 단계 | 근거 종류 |
| --- | --- | --- |
| 1 | LLM은 확률적 기계이고, 같은 맥락 안의 자기검토는 그 맥락이 만든 오류를 구조적으로 놓친다 | 자체 논증 |
| 2 | 그러므로 판정자는 구현자의 추론 경로를 물려받지 않아야 한다. 필요한 것은 다른 프롬프트가 아니라 다른 컨텍스트다. 세션 내 단계 분리는 이력을 공유하므로 조건을 못 채운다 | 자체 논증 |
| 3 | Claude Code에서 컨텍스트 경계는 곧 프로세스 경계다. 세션 간 전달은 순수 텍스트뿐이고 보내는 쪽의 이력 · 파일은 따라가지 않는다(부록 참고 문헌 [25]). 격리가 도구 차원에서 보장된다 | 도구 사실 · 공식 문서 확인 |
| 4 | 별도 프로세스는 조상 문서를 매번 다시 읽는 고정비를 낳는다. 이 비용은 프리픽스 캐싱으로 상쇄된다 — 비용 41~80% 절감, TTFT 13~31% 개선(부록 참고 문헌 [18]), 인프라 레벨 선례([19] · [20]). 조상 프리픽스가 정적이어야 성립한다 | 외부 근거 · 조건부 |
| 5 | "긴 세션 하나면 되지 않나" — 단일 지속 에이전트는 73.1% → 16.6%로 붕괴, 오케스트레이션 다중 에이전트는 90.6% → 65.3% 유지(p<0.01), 토큰 최대 65배 절감([21]) → 장수 세션 대신 태스크마다 스폰 · 회수 | 외부 근거 (범위: 정확도 · 토큰까지) |
| 6 | 판정자가 여럿이면 판정이 갈리고, 수렴 지점이 없으면 AC 루프가 끝나지 않는다 → Reviewer는 의견, Verifier 하나가 최종 게이트. 격리는 판단을 독립시키기 위한 것이지 결정을 분산시키기 위한 것이 아니다 | 자체 논증 |
| 7 | 그 게이트의 기준은 일반 절차로 정할 수 없다(결정문제) → 프로젝트마다 유한한 판정기, 즉 AC · DoD · 테스트. 미들웨어는 그 결과의 Exit Code만 심사한다 | 원리적 제약 · 자체 적용 |
| 8 | 남는 공백은 그 판정기의 **내용**이다(Reviewer pass/fail 기준, Verifier · AC 판정 기준 — TBD(Q-1)) → 채점 기준을 요구하지 않는 walking skeleton으로 실행 기반부터 세우고, 사슬 전체는 반증 기준으로 검사한다 | 미해결 · 측정 대상 |

사슬이 끊기는 지점은 둘이다. **4의 캐싱이 성립하지 않으면 3의 비용이 정당화되지 않고, 8의
실측이 이득을 보이지 않으면 1~2의 전제가 틀린 것이다.** 둘 다 1.02의 반증 기준과 4.02의 측정으로
확인한다.

## 핵심 성질

1. **계층은 코드 단위에 고정된다.** 태스크 = 파일 하나, AC = 함수 하나, 커밋 = 함수 하나,
   에이전트 배정 = 파일 하나. (2.02)
2. **독립성은 프로세스 경계로 보장하고, 종료로 끊는다.** 역할마다 별도 프로세스이고, 회수는
   프로세스와 자손 전부의 종료다. 종료가 곧 컨텍스트 폐기다. (1.02 P2 · P3)
3. **규율은 레일이, 자발성은 에이전트가 맡는다.** 레일은 태스크 읽기 · 상태 전이 · 테스트 통과
   없이는 편집 · 커밋 · 푸시를 막고, 커밋마다 태스크 ID와 토큰 사용량을 남긴다. (1.02 P6 · 3.01 · 3.03)

## 동작 한눈에

1. **부트스트랩** — git init → backlog.md CLI → `backlog init` → coding-agent-git-commit-tool(커밋 훅)
   → claude-code-agile-hooks. 순서는 고정이다. (3.02)
2. **백로깅** — 브리핑 → plan mode → draft → 승인 → promote. 한 번에 만들고, 진행 중 새 마일스톤이
   필요해지면 언제든 다시 들어온다. (3.02)
3. **스케줄** — 선언된 의존성 그래프와 파일 결합도 두 신호로 실행 순서를 정한다. 의존성이 없어도
   결합돼 있으면 순차다. 순차 체인이 워커풀의 빈 슬롯을 막지 않고, 동시 실행 수 상한은
   `min(그래프 폭, 자원 실측)`이다. (3.02 · 2.04)
4. **실행** — Implementer가 AC를 하나 커밋할 때마다 Reviewer(판단)와 Verifier·DoD(결정적 검사)가
   서로 기다리지 않고 동시에 그 커밋을 본다. 셋 다 부착 시 캐싱한 같은 조상 문서를 공유한다. 모든
   AC가 끝나면 Verifier·AC가 최종 판정을 하고, Logger는 내내 관찰한다. (3.02)
5. **회수** — 태스크가 끝나면 전원 kill. (3.02 · 3.03 §1)

## 착수 순서

1. **Walking skeleton** — 4역할 전체가 아니라 Implementer 하나만 스폰 → 작업 → 토큰 집계 → 회수.
   아직 없는 채점 기준을 요구하지 않는 유일한 조각이다. (4.01)
2. **실측** — 헤드리스 세션 간 메시징 실동 여부(Q-9), `claude` 프로세스 peak RSS, API 플랜의 분당 한도. (4.01 · 4.02)
3. **채점 기준은 추측으로 채우지 않는다** — Reviewer pass/fail 기준과 Verifier·AC 판정 기준은 TBD(Q-1)로 둔다.

## 쓰지 않는 경우

단일 에이전트가 이미 안정적으로 해내는 태스크에는 4역할을 붙이지 않는다. 판단은 태스크마다 한다. (1.03)
