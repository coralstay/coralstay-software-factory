# 1.03 목표와 범위

Sigkill Foundry는 판정이 구현의 컨텍스트를 물려받지 않는 태스크 실행을 레일 위에서 계측 가능하게 해내는 것을 목표로 하고, 처리량 자체나 완전 자동화는 목표로 삼지 않는다.

## 목표

모든 요구사항(2.03 · 2.04)은 아래 목표 중 하나 이상에 이바지한다(0. 문서 정보 추적 규칙).

| ID | 목표 | 원칙 | 주로 이어지는 장 |
| --- | --- | --- | --- |
| G-1 | **독립 판정.** 태스크마다 Implementer · Reviewer · Verifier · Logger를 각자 독립된 프로세스로 띄워, 판정 역할이 구현 역할의 컨텍스트를 물려받지 않은 채 커밋을 판정한다. 최종 판정은 Verifier 하나가 내린다 | P1 · P2 · P4 | 3.02 · 3.03 §1 |
| G-2 | **태스크 단위 스폰 · 회수.** 에이전트는 태스크(또는 계층 노드)에 부착될 때 생성되고, 끝나면 프로세스와 자손의 종료 · Registry 제거 · 동시성 허가 반납으로 회수된다. 상시 대기하는 장수 세션은 없다 | P2 · P3 | 3.02 · 3.03 §1 |
| G-3 | **레일로 규율 강제.** 부트스트랩 순서, 백로깅(브리핑 → plan mode → draft → 승인 → promote), 태스크 읽기 · 상태 전이 · 테스트 통과 · Done 요약 없이는 편집 · 커밋 · 푸시가 일어나지 않도록 기계적으로 강제한다 | P5 · P6 | 3.03 §2 · 3.03 §4 |
| G-4 | **계측과 감사 추적.** 모든 커밋에 태스크 ID를 남기고, 토큰 사용량은 토큰 계량 컴포넌트(이름 미정)로 커밋(= 함수) 단위로 잰다(그 전까지는 실행 단위 `session`만, `TBD(Q-18)`). Done 시점에 커밋과 토큰 집계를 읽어 태스크 카드에 기록한다. 스케줄 라운드마다 Ready 집합 크기 · 임계 경로 길이 · 폭 · 실제 동시 가동 수를 남긴다 | P2 · P7 | 3.03 §3 · 3.05 ADR-021 · 2.04 |
| G-5 | **태스크 사이 처리량.** 의존성과 파일 결합도로 순차 체인과 독립 노드를 가르고, 독립 노드는 `min(그래프 폭, 자원 상한)` 안에서 동시 배정한다. 워커풀을 work-conserving하게 유지하고, 이미 착수한(미병합 `task/<ID>` 브랜치가 있는) 태스크에는 배정하지 않는다 | P7 | 2.04 · 3.02 |
| G-6 | **정책 외부 주입.** 어느 노드에 · 몇 개 · 어떤 역할을 · 언제 · 어떤 모델로 붙일지를 오케스트레이터 코어에 고정하지 않고, 교체 가능한 Allocation Policy로 주입한다 | P8 | 3.03 §1 · 3.04 |
| G-7 | **측정으로 경계선 확정.** 태스크별 성공/실패 · AC 재작업 · 회귀 기록을 쌓아, 4역할이 단독 Implementer + self-review보다 나은지(1.02 반증 기준)와 어떤 태스크에 4역할을 붙일지의 경계선을 이 저장소의 실측으로 판정할 수 있게 한다 | P9 | 4.02 · 5.02 |

## 비목표

| 하지 않는 것 | 이유 | 장 |
| --- | --- | --- |
| 태스크 안의 처리량 극대화 | 한 태스크에 네 역할을 붙이는 선택은 속도로 정당화하지 않는다. 처리량은 태스크 사이(G-5)에서만 추구한다 | 1.02 · 2.04 |
| "지시만 던지면 나오는 소프트웨어"(완전 자동화) | 목적은 자동화가 아니라 판단의 독립성이다. 사람은 draft 승인 · 직접 착수(`task/<ID>` 브랜치) · 판정 루프 초과 시 개입 지점에 남는다 | 1.02 · 2.01 |
| 에이전트 간 자유 대화형 협업(AutoGen류 conversable agent) | 자유 상호작용은 결과 품질을 예측하기 어렵다(부록 참고 문헌 [2]). 고정 순서 · 고정 트리거 파이프라인으로 한다. 세션 간 메시징은 포인터만 싣는 보조 채널이다 | 3.02 · 3.04 |
| 세션 내 위임(Subagent · Agent Teams) | 역할마다 다른 설정 · 권한 · 작업 디렉토리가 필요하고, 컨텍스트 경계가 프로세스 경계여야 한다 | 1.02 P2 · 3.05 |
| 마일스톤 노드 에이전트의 작업 배분 | 마일스톤 노드 에이전트는 매니저가 아니라 Done인 자식의 산출물을 읽는 집계자다. 배분 권한은 Allocation Policy에만 있다 | 3.02 · 3.03 §1 |
| 임의 명세 충족의 일반 판정기 | 결정문제로 불가능하다. 프로젝트가 정한 AC · DoD · 테스트만 판정한다 | 1.02 P5 |
| Reviewer · Verifier 채점 기준을 추측으로 채우기 | 근거 없이 채우지 않는다 — TBD(Q-1) | 4.03 |
| 외부 벤치마크의 임계값 차용 | 종속변수(과제 정확도 ≠ 판단의 독립성)가 다르고, 배정 시점에 태스크 난이도를 모른다 | 1.02 P9 |
| backlog.md 저장 상태 어휘 확장 | 사람이 보는 보드는 To Do · In Progress · Done 세 값을 그대로 쓴다. 세밀한 구분은 backlog.md가 계산하는 readiness와 오케스트레이터의 계산된(비저장) 레이어로 한다 | 2.02 |
| 언어 런타임 설치(langtoolchain) | 파이프라인 범위 밖이다. 부트스트랩 순서에 넣지 않는다 | 3.02 |
| 다중 노드(Pod) 분산 실행 | 단일 JVM 수직 확장을 택한다. SPOF는 베어메탈 이중화로 완화한다 | 3.05 |

## 적용 조건

판단 단위는 프로젝트가 아니라 **태스크**다. 같은 프로젝트 안에서도 태스크마다 다시 판단하고, 판단은
배정 시점에 Allocation Policy가 노드와 상태를 보고 한다(G-6 · 1.02 P8). Next.js 스캐폴드나 Spring+DB
단순 CRUD는 판단을 설명하는 예시일 뿐, 그 프로젝트 전체가 4역할 대상에서 영구히 빠진다는 뜻이 아니다.

### 4역할을 붙이는 태스크

| 조건 | 근거 |
| --- | --- |
| 구현자의 추론을 물려받으면 안 되는 태스크 | 판단의 독립성이 이 구조의 존재 이유다. 같은 맥락을 공유한 자기검토로는 잡히지 않는 오류가 대상이다 |
| 판정을 게이트로 닫을 수 있는 작업 | 오케스트레이터는 Exit Code만 심사한다. AC · DoD가 없으면 이 구조가 보장하는 것은 아무것도 없다 |
| 회귀 비용이 큰 작업 | 놓친 회귀의 비용이 검증에 드는 토큰 · 시간과 비대칭일 때, 게이트를 하나 더 두는 편이 싸다 |
| 감사 추적이 필요한 작업 | 모든 시도가 커밋으로 남고, Done 시점에 카드로 기록된다(G-4) |

### 4역할을 붙이지 않는 태스크

| 조건 | 근거 |
| --- | --- |
| 단일 에이전트가 이미 안정적으로 해내는 태스크(Next.js 스캐폴드, 단순 CRUD) | 조율 오버헤드가 이득을 갉아먹는다. 재작업도 회귀도 거의 없는 태스크에 게이트를 네 겹 두면 비용만 남는다. Implementer 단독으로 실행한다 |
| 채점 기준을 쓸 수 없는 작업 | Reviewer · Verifier의 pass/fail 기준이 없으면 4역할은 성립하지 않는다 — TBD(Q-1) |

### 병렬로 돌리지 않는 태스크

| 조건 | 근거 |
| --- | --- |
| 서로 의존하거나(`--dep`) 같은 파일 · 모듈을 건드리는 태스크 | 의존성 그래프와 파일 결합도 두 신호 중 하나라도 있으면 순차 체인으로 묶는다(부록 참고 문헌 [10]) |
| 이미 착수한 태스크(미병합 `task/<ID>` 브랜치가 있다) | 사람이 했든 에이전트가 했든 배정하지 않는다. 사람과 에이전트의 충돌을 막는다(2.02 · 3.02) |

### 경계선

"얼마나 어려워야 4역할을 쓰는가"의 임계값은 이 문서에 두지 않는다 — TBD(Q-11).

- 외부에서 빌려오지 않는다. 멀티에이전트 조율의 손익을 다룬 연구는 과제 정확도를 재고, 이 설계는
  판단의 독립성을 내세운다. 정확도 기준으로 "이득 없음"이 나와도 회귀 방지 가치는 별도로 남고,
  정확도가 올라가도 그것이 독립 판정 덕이라는 보장이 없다(1.02 P9).
- 운용상으로도 쓸 수 없다. 배정 시점에 그 태스크의 단일 에이전트 기준 성공률은 알 수 없고, 벤치마크
  평균 정확도는 눈앞의 태스크의 성공률이 아니다. 놓친 회귀의 비용 비대칭도 평균 지표에는 없다.
- 경계선이 정해지기 전까지의 판단 기준은 1.02 반증 기준 하나다. 작고 단순한 태스크는 Implementer
  단독으로 시작하고, 4역할 전체는 단일 에이전트가 자주 실패하는 더 복잡한 작업에 아껴 쓴다. 그
  "자주"의 경계선은 walking skeleton이 쌓는 태스크별 성공/실패 · 재작업 · 회귀 기록으로 정한다(G-7 · 4.01).

복잡도를 말할 때는 깊이(추론 길이) × 너비(필요 역량의 다양성) 두 축의 형식화를 잣대로 쓴다(부록 참고
문헌 [24]). 스캐폴드류는 두 축 모두 낮게 나올 것으로 예상된다. 이 두 축은 스케줄 계측의 임계 경로
길이 · 그래프 폭과 같은 형태다(2.04).

**근거의 빈틈.** 소프트웨어공학의 "프로세스 오버헤드 대 프로젝트 규모" 문헌(Agile tailoring 등)은
"규모에 맞게 조정하라"는 원칙은 정설이지만 정량적 임계 모델은 없다 — 정성적 원칙 이상으로 해석하지
않는다. ChatDev · MetaGPT · AutoGen류 파이프라인을 trivial한 CRUD 스캐폴드에 직접 돌려 보고한
연구는 없다 — "단순 CRUD에는 쓰지 않는다"는 판단은 상식에 기댄 것이다.
