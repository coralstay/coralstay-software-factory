# 1. 요약

> 상태: 초안

**Sigkill Foundry** — Claude Code 세션을 찍어내고 `kill -9`로 끊어내는 소프트웨어 공장.

## 무엇을 만드는가

소프트웨어 태스크를 `backlog.md` 계층(마일스톤 · 태스크 · AC)으로 분해하고, 태스크마다
역할형 Claude Code 에이전트(Implementer · Reviewer · Verifier · Logger)를 **독립된 `claude -p`
프로세스**로 띄웠다가, 일이 끝나면 프로세스째 죽여서 회수하는 실행 기반이다. JVM 오케스트레이터가
외부에서 정책을 주입해 스폰과 회수를 맡고, 에이전트는 정해진 레일(훅 · 테스트 게이트 · 커밋 계측)
위에서만 일한다.

## 세 가지 핵심

1. **계층이 코드 단위에 고정된다.** 태스크 = 파일 하나, AC = 함수 하나, 커밋 = 함수 하나,
   에이전트 배정 = 파일 하나. 파일이 격리 단위이므로 워크트리를 나누면 두 에이전트가 같은 파일을
   만질 일이 구조적으로 없고, 커밋이 함수 단위이므로 토큰 계량도 함수 단위로 붙는다. (4장)

2. **독립성은 프로세스 경계로 보장하고, 종료로 끊는다.** Reviewer와 Verifier가 Implementer의
   추론을 물려받지 않게 하는 것이 이 구조가 존재하는 이유다(판단의 독립성). 그 독립성을 프롬프트
   지시나 `/clear`에 맡기지 않는다. 역할마다 별도 프로세스로 띄우고, 회수할 때는 프로세스와 그
   자손 전부를 SIGTERM → 유예 → **SIGKILL**로 끝낸 뒤 Registry에서 지우고 동시성 허가를 반납한다.
   헤드리스 세션은 **종료가 곧 컨텍스트 폐기**다 — 끊고 나면 남는 의존이 없다. (6장 · 7.1)

3. **규율은 레일이, 자발성은 에이전트가 맡는다.** 훅(claude-rails)이 태스크 읽기 · 상태 전이 ·
   테스트 통과 없이는 편집 · 커밋 · 푸시를 막고, 커밋 훅(coding-agent-git-commit-tool)이 커밋마다
   태스크 ID와 토큰 사용량을 트레일러로 남긴다. 에이전트가 무엇을 하든 이 레일 밖으로는 나가지
   못한다. (5장 · 7.2 · 7.3)

## 어떻게 작업하는가

- **판단 단위는 태스크다.** 단일 에이전트가 이미 안정적으로 해내는 태스크에는 멀티에이전트를 쓰지
  않는다. 프로젝트가 단순하게 시작했어도 이후 태스크가 어려워지면 그 시점부터 4역할을 쓴다.
  경계선은 남의 임계값을 빌리지 않고 직접 측정해서 정한다. (3장)
- **부트스트랩 순서는 고정이다.** git init → backlog.md CLI → `backlog init` → 커밋 훅 →
  claude-rails. (6장)
- **백로그는 반복해서 다시 들어온다.** 브리핑 → plan mode → draft → 승인 → promote. 진행 중
  새 마일스톤이 필요하면 언제든 이 루프로 돌아온다. (6장)
- **병렬은 두 신호로 정한다.** 선언된 의존성 그래프와, 같은 파일 · 모듈을 건드리는지(결합도).
  의존성이 없어도 결합돼 있으면 순차로 다룬다. 동시 실행 수의 상한은
  `min(그래프 폭, 자원 실측)`이다. (6장 · 9장)
- **4역할 태스크의 흐름.** Implementer가 AC를 하나 커밋할 때마다 Reviewer(판단)와
  Verifier·DoD(결정적 검사)가 서로 기다리지 않고 그 커밋을 동시에 본다. 모든 AC가 끝나면
  Verifier·AC가 최종 판정을 하고, Logger는 그동안 내내 관찰한다. 태스크가 끝나면 전원 kill. (6장)

## 지금 어디까지 왔는가 (2026-10-05)

| 부품 | 상태 |
| --- | --- |
| agent-orchestrator | M1 walking skeleton 71%. 스폰 · 회수 · 워크트리 · backlog 판독 부품은 있으나 아직 서로 배선되지 않았다 |
| claude-rails | 핵심 레일 훅 완성, 테스트 1672개 통과. 역할별 분기는 미착수 |
| coding-agent-git-commit-tool | 트레일러 · 토큰 계량 동작. 최신 구조(GF-127 · 128)가 main에 미머지 |

다음 착수 지점은 **Implementer 하나만** 스폰 → 작업 → 토큰 집계 → kill 하는 walking skeleton이다.
아직 없는 채점 기준을 요구하지 않으면서 스폰 · 회수 · 동시성 · 토큰 측정을 한 번에 검증한다. (12장)

## 아직 정하지 않은 것

Reviewer의 pass/fail 기준과 Verifier · AC 판정 기준은 추측으로 채우지 않는다. 이 공백이 남는 한
4역할 전체의 완료 기간은 추정할 수 없다. 나머지 미해결 질문과 각각을 정해줄 근거는 11장에 있다.
