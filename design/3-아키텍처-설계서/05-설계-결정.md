## ADR-001 역할마다 완전히 독립된 프로세스

- **맥락** — 판정자가 구현자의 추론 경로를 물려받지 않아야 한다(P1). 제품군이 다양해 역할마다 다른 설정 · 권한 · 작업 디렉토리가 필요하다.
- **결정** — Implementer · Reviewer · Verifier · Logger를 전부 별도 프로세스(기본 `claude -p`)로 띄운다. 역할 하나를 다른 프로바이더 CLI로 바꿀 수 있다.
- **근거** — Claude Code에서 컨텍스트 경계는 곧 프로세스 경계이고, 세션 간 전달은 순수 텍스트뿐이라 격리가 도구 차원에서 보장된다. 토큰 귀속도 쉬워진다 — 세션 내부 위임이면 부모 · 자식 사용량이 한 응답에 섞이지만, 독립 프로세스면 각자 자기 몫만 떨어진다.
- **기각한 대안** — Subagent · Agent Teams(세션 내 위임): 대화 이력을 공유해 독립 판정 조건을 못 맞추고, 역할별 설정 · 권한 · 디렉토리를 나눌 수 없다. 같은 세션 안에서 단계만 나누기: 같은 이유.
- **반증** — Implementer 단독 + self-review 대비 AC 재작업률 · 회귀 발생률을 유의미하게 낮추지 못하면 Reviewer · Verifier를 Implementer 세션 안의 단계로 접는다 (1.02 반증 기준).

## ADR-002 Java 25 + virtual thread + Semaphore

- **맥락** — 동시성은 한 자릿수~십수 개의 OS 서브프로세스 규모다. 즉시 스폰과 비동기 큐 사이에서 골라야 한다.
- **결정** — Java 25(JVM), virtual thread + Semaphore. 즉시 스폰과 비동기 큐의 이분법 대신 용량 제한 워커풀로 절충한다 — 평상시엔 즉시 디스패치처럼, 트리거가 몰릴 때만 큐잉된다. AC 루프의 Reviewer처럼 지연에 민감한 경로는 전용 슬롯으로 뗀다.
- **근거** — 이 규모에서는 동시성 모델이 성능을 좌우하지 않는다. virtual thread의 실익은 `Process.waitFor()`를 블로킹으로 써도 되어 비동기 콜백이 사라지는 코드 단순성이다.
- **기각한 대안** — 즉시 스폰만: 트리거가 몰리면 상한 없이 뜬다. 비동기 큐만: 평상시에도 지연이 생긴다. 콜백 기반 비동기 I/O: 이 규모에서 얻는 성능이 없고 코드만 복잡해진다.

## ADR-003 정책은 `AllocationPolicy` 하나로 외부 주입

- **맥락** — "언제 · 얼마나 · 어떤 역할을 · 어떤 모델로" 스폰할지는 태스크와 실측에 따라 바뀐다.
- **결정** — `AllocationPolicy` 인터페이스 하나를 확장 지점으로 두고, 정책은 그 인터페이스를 구현한 **자바 클래스**로 쓴다. 정책은 ① `-Dpolicy.class=` 시스템 프로퍼티 ② `java.util.ServiceLoader`(별도 jar 플러그인) 순으로 고른다. 정책이 지정되지 않았거나 지정한 정책을 로딩 · 생성하지 못하면 에러 메시지를 내고 실행하지 않는다. 내장 정책(`DefaultAllocationPolicy`)은 명시적으로 고를 때만 쓰고, 폴백으로 쓰지 않는다. 고른 정책의 클래스(정규 이름)와 선택 경로를 실행 결과와 실행 기록에 남긴다.
- **근거** — Kubernetes Scheduler Framework처럼 코어는 그대로 두고 정해진 확장 지점만 갈아끼운다. 정책에는 조건 판단(태스크 난이도 · 예상 토큰 · 역할별 분기)이 들어가므로 데이터 형식보다 코드가 맞고, 컴파일러의 타입 검사와 IDE 지원을 받는다(Spring이 XML 설정을 `@Configuration` 자바 클래스로 옮긴 것과 같은 이유). `-Dpolicy.class`와 `ServiceLoader`는 모두 JDK 표준이라 외부 의존성이 없다(NFR-010). 폴백을 두지 않는 것은 정책 지정 실수(오타 · jar 누락)가 조용히 기본 정책 실행으로 바뀌어 다른 모델 · 역할 구성으로 돌고도 드러나지 않는 일을 막기 위해서다 — 어떤 정책으로 돌았는지는 기록으로 확인한다.
- **기각한 대안** — 오케스트레이터 내부 하드코딩: 정책을 바꿀 때마다 코어를 고친다. YAML 설정: JDK에 파서가 없어 외부 라이브러리(SnakeYAML)가 필요하고(NFR-010 위반), 암묵적 타입 변환 함정과 역직렬화 취약점 이력(CVE-2022-1471)이 있으며, 조건 판단은 어차피 표현하지 못한다. key=value 설정: 의존성은 없지만 계층 · 목록 · 조건을 표현하지 못해 정책 범위가 넓어지면 키 규약과 손으로 짠 검증이 늘어난다. 정책 미지정 · 로딩 실패 시 내장 기본 구현으로 폴백: 시작은 되지만 의도하지 않은 정책으로 실행되고 그 사실이 드러나지 않는다. 런타임 컴파일(`javax.tools.JavaCompiler`로 정책 `.java`를 시작 시 컴파일): 재빌드 없이 바꿀 수 있지만 정책 파일이 곧 실행 코드라 에이전트가 쓸 수 없는 위치와 보호 장치를 따로 설계해야 하고, 실행 환경에 JDK가 필요하다.

## ADR-004 지연 · 비용 마진은 전체 공유 버퍼 하나

- **맥락** — 태스크마다 지연 · 비용이 들쭉날쭉하다.
- **결정** — 태스크별 버퍼를 두지 않고 오케스트레이터 전체의 공유 버퍼 하나로 관리한다.
- **근거** — Critical Chain Project Management의 자원 제약 인지 방식을 차용한다(LLM 에이전트에 적용한 선행 연구는 없고 고전 PM 이론에서 가져온 확장이다). Semaphore로 동시 작업량을 제한하는 것은 Little's Law(리드타임 = WIP ÷ 처리량)로도 뒷받침된다.
- **기각한 대안** — 태스크별 개별 버퍼: 버퍼가 태스크마다 흩어져 낭비된다.

## ADR-005 동시성 상한 = `min(그래프 폭, 자원 실측)`

- **맥락** — Semaphore 용량을 무엇으로 정할지.
- **결정** — 자원 상한은 (a) `claude` 프로세스 1개의 peak RSS와 (b) API 플랜의 분당 요청 한도 실측으로 정하고, (c) 스케줄 라운드마다 잰 그래프 폭과 비교해 작은 쪽을 쓴다.
- **근거** — 폭보다 큰 용량은 채울 일감이 없고, 폭보다 작은 용량은 work-conserving을 어긴다. 자원이 남아도 띄울 독립 노드가 없으면 용량은 의미가 없다.
- **기각한 대안** — 벤치마크로 정한 고정 상한: 이 백로그의 구조와 이 호스트의 자원을 반영하지 못한다. 무한정 늘리기: 같은 코드베이스를 동시에 건드리는 에이전트가 많을수록 어긋날 위험이 조합적으로 커진다.
- **반증** — 실측 폭이 거의 항상 1~2이면 워커풀 · Semaphore · 결합도 분석 전체가 과설계다. 순차 실행 하나로 접는다 (NFR-003).

## ADR-006 저장 상태는 3개, 세밀한 구분은 계산 레이어

- **맥락** — 사람용 칸반은 상태가 적고, 자동화 워크플로 엔진은 상태가 많다. Airflow `TaskInstanceState` 13개(예: `UPSTREAM_FAILED`를 `FAILED`와 구분), BPMN 2.0 액티비티 생애주기 약 10~11개, Temporal `WorkflowExecutionStatus` 7~8개.
- **결정** — backlog.md의 `To Do` · `In Progress` · `Done`을 그대로 쓴다. 오케스트레이터에 필요한 구분은 backlog.md가 읽기 시점에 계산하는 readiness(`isReady` · `isBlocked` · `blockingDependencies` · `missingDependencies`)로 얻고, 더 필요하면 오케스트레이터의 계산(비저장) 레이어를 얹는다.
- **근거** — 두 근거는 대상이 다를 뿐 충돌하지 않는다. 3상태는 사람이 보는 보드이고, "지금 하는 방식을 그대로 시각화하고 병목이 증명될 때만 구조를 늘린다"(Anderson, Kanban 2010)의 정석적 사례다. 기계용 구분은 Airflow가 `TaskInstanceState` 위에 `DagRunState`를 따로 두듯 층을 나눠 얻는다. 단, 상태 개수와 인지 부하를 직접 잰 실험 연구는 없다 — 방법론 원칙이다.
- **기각한 대안** — backlog.md 저장 상태 어휘를 늘리기(blocked · archive 등을 상태로): blocked는 의존에서 계산되는 파생 속성이고 archive는 별도 동작이다. 사람의 보드를 기계 사정으로 복잡하게 만든다.

## ADR-007 회수는 kill — 장수 세션을 두지 않는다

- **맥락** — 에이전트를 상시 대기시킬지, 태스크마다 띄우고 끝낼지.
- **결정** — 태스크마다 스폰하고, 끝나면 프로세스 · 자손 종료(SIGTERM → 유예 → SIGKILL) + Registry 제거 + 허가 반납을 한 호출로 한다. 제거에 성공했을 때만 허가를 반납해 멱등으로 만든다.
- **근거** — 헤드리스 세션은 종료가 곧 컨텍스트 폐기다. 임상 규모 실험에서 단일 지속 에이전트는 작업량이 늘자 정확도가 73.1% → 16.6%로 붕괴했고, 오케스트레이션된 다중 에이전트는 90.6% → 65.3%로 버텼으며(p<0.01) 토큰은 최대 65배 적었다 (부록 참고 문헌). 이 근거는 "장수 세션보다 태스크 단위 스폰 · 회수"까지만 쓴다.
- **기각한 대안** — 상시 대기 4역할 + 대화형 `/clear`: 헤드리스 프로세스에는 명령을 더 보낼 통로가 없고, 장수 세션은 작업량이 늘면 무너진다.

## ADR-008 직접 메시징은 포인터만 싣는 보조 채널

- **맥락** — AutoGen류의 실시간 conversable-agent 대화가 이 설계엔 없다. Claude Code는 세션 간 메시징(`ListAgents` · `SendMessage`, 머신 로컬 소켓, Anthropic 서버 비경유)을 기본 기능으로 준다. 메시지는 순수 텍스트이고 보내는 쪽의 이력 · 파일을 포함하지 않는다.
- **결정** — 메시지에는 포인터(태스크 ID · AC 번호 · 파일:라인)만 싣고 본문은 수신자가 파일에서 읽는다. 에이전트 할당 시점에 배선한다. 파일 기반 WAL이 1차 기록이다. 스폰은 bare 모드를 쓰지 않는다(bare 모드는 inbox 소켓을 바인딩하지 않는다). 동작하지 않으면 WAL 디렉토리를 파일 메일박스로 폴링한다.
- **근거** — 메시징이 이력을 싣지 않으므로 판단 독립성(P1)을 해치지 않고, 영구 기록은 파일에 남아 회수(P3)와 함께 사라지지 않는다.
- **기각한 대안** — 에이전트 간 대화로 협업: 맥락이 섞여 판단 독립성을 잃는다. 실험 기능인 Agent Teams: 세션 내 위임이라 ADR-001과 충돌한다.

## ADR-009 재로딩 고정비는 프리픽스 캐싱으로 상쇄

- **맥락** — 독립 프로세스는 부착마다 조상 문서를 루트까지 다시 읽는다.
- **결정** — task → milestone → root 조상 문서 경계에 프롬프트 캐싱을 적용한다. 프리픽스에는 가변값을 섞지 않는다. 판정자들은 같은 프리픽스를 공유해 병렬로 본다.
- **근거** — 캐시에 쓴 프리픽스를 공유하는 에이전트는 정상 비용의 약 2.5~10%로 읽는다(Anthropic Prompt Caching). 별도 평가가 41~80% 비용 절감, TTFT 13~31% 개선을 보고했고, 인프라 레벨 선례(EACC · SGLang RadixAttention)도 있다 (부록 참고 문헌). "백로그 계층을 루트까지 재로딩"을 1:1로 다룬 논문은 없고, 장기 맥락 · 멀티에이전트 컨텍스트 재사용의 특수 사례로 본다.
- **기각한 대안** — 장수 세션으로 재로딩 회피: ADR-007. 보류 — Reviewer · Logger가 Implementer의 요약 + diff만 읽는 비대칭 로딩: 고정비를 더 낮출 수 있지만 판정 근거가 줄어든다 (`TBD(Q-2)`).

## ADR-010 Verifier를 DoD · AC로 나누고, 채점 기준은 추측하지 않는다

- **맥락** — MetaGPT의 QA, ChatDev의 Tester는 나름의 평가 기준을 갖고 있다. 이 설계는 무엇이 pass · fail인지 아직 없다.
- **결정** — 채점 기준과 무관하게 정할 수 있는 것만 정한다. ① Verifier를 DoD(결정적 검사 — 테스트 · lint 종료 코드)와 AC(판단)로 나눈다. ② 판정 출력 스키마 `{ac_id, verdict, evidence, blocking}`. ③ Reviewer 최대 `TBD(Q-11)`회 왕복 후 사람 호출 — AC 루프 무한 반복 방지. ④ Reviewer는 의견, Verifier 하나가 최종 게이트(P4). Reviewer pass · fail 기준과 Verifier · AC 판정 기준은 추측으로 채우지 않는다.
- **근거** — AC(개별)와 DoD(공통)는 backlog.md가 `--check-ac` · `--check-dod`로 이미 주는 구분이다. 판정자가 여럿이면 판정이 갈리고 수렴 지점이 없으면 루프가 끝나지 않는다. 임의 명세의 충족을 판정하는 일반 절차는 없으므로 판정기는 프로젝트가 유한하게 쓴다(P5).
- **기각한 대안** — 다른 프레임워크의 평가 기준 차용: 이 설계의 종속변수(판단의 독립성)와 맞지 않는다. 다수결 판정: 수렴 지점이 없다.

## ADR-011 토큰은 API 사용량 메타데이터로 커밋마다 잰다

- **상태** — 폐기(2026-10-12). ADR-021이 대체한다. 아래는 폐기 전 기록이다 — coding-agent-git-commit-tool은 이제 토큰을 계량하지 않는다.
- **맥락** — LLM은 생성 중 자기가 몇 토큰 썼는지 아는 내장 카운터가 없다. 토큰 수는 API가 응답마다 돌려주는 메타데이터다.
- **결정** — coding-agent-git-commit-tool의 커밋 훅이 세션 트랜스크립트의 assistant `message.usage`를 합산하고 `tool_use` 블록을 세어 커밋 트레일러로 남긴다. 측정 실패는 `unavailable (<사유>)`로 남긴다. 측정 방식은 채택하되 정확도는 확정하지 않는다.
- **근거** — 이미 쓰고 있는 실측 방식이고, 실패-투명성 패턴이 있다. 값은 근사치이고 무관한 대화가 섞이면 과대평가될 수 있다고 도구 스스로 밝힌다. Reviewer · Verifier처럼 짧게 한 번 도는 프로세스는 트랜스크립트 전체를 한 번 합산하면 된다 — 헤드리스 실행이어도 트랜스크립트는 같게 남는다.
- **기각한 대안** — Logger가 다른 역할에게 "얼마나 썼어?"라고 묻기: 모델은 그 값을 모른다. 측정 실패 시 추정치 기록: 조용한 오측정이 된다.

## ADR-012 완료 시점에 커밋을 읽어 카드에 기록한다

- **맥락** — 커밋이 함수 단위라 함수별 작업 내역과 토큰이 커밋에 흩어져 있다. 이력을 나중에 정리하면 흔적이 사라질 수 있다.
- **결정** — Done 전환 시점(`-s Done --final-summary`)에 태스크 브랜치의 커밋을 읽어 함수별 작업 내역 · 토큰 집계를 카드에 기록한다. 토큰은 당분간 커밋 귀속분이 아니라 실행 한 번의 `session`만 기록한다 (ADR-021 예외, `TBD(Q-18)`).
- **근거** — 기록이 카드(와 카드를 담은 커밋)에 남으므로, 이력 정리 방식이 기록 보존과 분리된다.
- **기각한 대안** — `git log`만을 기록으로 삼기: 스쿼시하면 함수별 귀속이 사라진다.

## ADR-013 모든 발자취는 Git에, 정리는 완료 시점에

- **맥락** — 에이전트가 상태를 바꾸고 시도할 때마다 커밋이 남아 사람용 로그 추적이 어려워진다(커밋 파편화).
- **결정** — 발자취는 Git이 전부 품는다. 메인 브랜치가 더러워지는 문제는 태스크 완료 시점에 정리한다. 정리 방식(스쿼시 · 머지 커밋)은 `TBD(Q-4)`이다.
- **근거** — 태스크당 최소 커밋 수 = AC 개수로 배정 전에 세어지고, 파일 하나의 함수 수준이라 수백 개가 되는 일은 드물다. 남은 미지수는 자가 치유 재시도 배수뿐이고, walking skeleton이 남기는 AC당 재시도 분포로 정한다 — 남의 관행을 그대로 가져오지 않는다. 기록 보존은 ADR-012가 해결하므로 이 선택은 이력 가독성의 문제다.
- **대안 비교** — Squash and Merge: 커밋들을 하나로 합쳐 부모 1개 커밋으로 얹는다. 원래 커밋은 `git log main`에서 사라진다. 이미 푸시해 공유한 커밋을 스쿼시하면 해시가 바뀌어 받아간 쪽이 갈라지므로, 그 브랜치를 혼자 가졌을 때만 안전하다(에이전트 워크트리 브랜치는 대체로 해당). Merge commit: 부모 둘로 엮고 커밋이 그대로 남는다.

## ADR-014 Worktree + 1태스크 1에이전트 1파일 1주제, 사람과는 착수 브랜치로

- **맥락** — 여러 에이전트가 같은 소스 파일이나 인덱스 파일을 동시에 건드리면 시스템이 마비된다. 사람도 메인 작업 트리에서 같은 파일을 열고 있을 수 있다.
- **결정** — 에이전트마다 `git worktree`로 물리 폴더와 브랜치를 분리하고, 태스크 하나는 파일 하나만 다룬다. 사람과의 충돌은 착수로 막는다 — 착수는 main에 병합되지 않은 `task/<ID>` 브랜치가 있는 상태이고(2.02 상태와 전이), 오케스트레이터는 착수한 태스크에 배정하지 않는다 (ORC-005, decision-3).
- **근거** — 태스크가 파일 하나에 대응하므로 락의 단위도 파일 하나다. 브랜치는 사람이든 에이전트든 작업을 시작하면 어차피 만들므로 별도 잠금 파일 · 프로토콜이나 main의 착수 커밋이 필요 없고, 병합되면 저절로 풀린다. 승인 게이트가 같은 시점(브랜치 생성 · 전환)에 돌아 승인 없이 브랜치만 만든 착수가 생기지 않는다 (ADR-022).
- **변경** — 2026-10-29 전에는 상태 값을 락으로 썼다 — 사람이 `In Progress`로 옮기면 그 태스크에 배정하지 않았다. 상태 전환 커밋은 `task/<ID>` 브랜치에 들어가므로(RAIL-002) main을 읽는 쪽에는 계속 `To Do`로 보여 락이 되지 못한다. decision-3이 이를 브랜치 존재로 바꿨다.
- **기각한 대안** — 같은 작업 트리에서 브랜치만 나누기: 인덱스와 작업 파일이 공유된다. 별도 잠금 파일: 상태와 락이 따로 놀아 어긋날 수 있다. main에 착수 기록 커밋: 착수마다 main에 커밋이 생기고 브랜치와 따로 놀 수 있다. 상태 값 락: 위 변경.
- **한계** — backlog.md 1.51.0의 화면(`task list` · `view` · `overview` · `search` · `backlog browser`)은 main에서 착수한 카드를 `To Do`로 보인다. 사람은 `git branch -a --list '*task/*'`와 병합 여부로 확인한다 (3.03 §4 주의점).

## ADR-015 고빈도 상태는 임베디드 DB, Git은 최종 영속화

- **맥락** — 상태 값과 프롬프트 캐시를 매번 디스크 마크다운으로 읽고 쓰면 레이턴시가 커진다.
- **결정** — 수없이 바뀌는 조율 정보 · 작업 큐 · 캐싱 상태는 메모리 · 임베디드 DB(SQLite · H2)가 받고, Git은 형상 관리 목적의 최종 영속화에만 쓴다(이중 영속화).
- **근거** — 파일 I/O 병목을 피하면서 진실의 원천은 Git에 남긴다.
- **기각한 대안** — 모든 상태를 backlog.md 마크다운으로만: 고빈도 갱신에 디스크 I/O가 병목이 된다. 외부 DB 서버: 단일 JVM 구성(ADR-017)과 맞지 않는다.

## ADR-016 규칙은 대상 프로젝트의 테스트에

- **맥락** — 아키텍처 · 컴플라이언스 규칙을 미들웨어에 넣을지 대상 프로젝트에 넣을지.
- **결정** — 규칙의 실행과 검증은 대상 프로젝트의 테스트 코드(ArchUnit 레이어 검증, JavaParser · 리플렉션 기반 컴플라이언스 게이트 등)에 두고, 미들웨어는 빌드 결과의 종료 코드만 보고 통과시킬지, 에러 로그를 묶어 재작업을 지시할지만 정한다.
- **근거** — 판정기는 프로젝트마다 유한하게 써야 한다(P5). 미들웨어는 프로젝트 종류와 무관해진다.
- **기각한 대안** — 미들웨어가 규칙을 해석: 프로젝트마다 미들웨어를 고쳐야 하고, 판정 일반 절차가 없다는 제약에 부딪힌다.

## ADR-017 수직 확장(단일 JVM)

- **맥락** — 에이전트 수가 늘 때 Pod 분산(수평)과 고사양 단일 서버(수직) 중 무엇으로 갈지.
- **결정** — 수직 확장. 배정 · 정적 분석 · 웹 화면은 virtual thread가 메모리 위에서 다루고, 무거운 에이전트 코딩과 빌드는 커널 자원(`cgroups`)과 RAM 디스크(`tmpfs`)를 쪼개 쓴다. 병목 대응은 2.04 수직 확장 병목.
- **근거** — 모든 작업 공간이 `tmpfs`에 있고 데이터가 단일 JVM 메모리 버스 안에서 오가면, Pod 사이 gRPC · REST로 소스 · 로그를 주고받는 오버헤드가 0이 된다. 에이전트 구동 속도와 자가 치유 회전이 수평 확장보다 빠르다. 막힌 에이전트는 RAM 디스크 폴더를 통째로 지우고 워크트리를 다시 만들어 새 에이전트를 투입한다.
- **기각한 대안** — 수평 확장(Pod 분산): 인프라 관리 비용과 클라우드 유연성에서 이기지만 네트워크 레이턴시와 직렬화 오버헤드를 진다.
- **리스크** — 장비가 고장 나면 대안이 없는 단일 장애점(SPOF). 이중화된 베어메탈로 완화한다.

## ADR-018 부트스트랩 순서 고정

- **맥락** — 도구 설치와 백로그 생성의 순서.
- **결정** — `git init` → backlog.md CLI → `backlog init` → coding-agent-git-commit-tool → claude-code-agile-hooks → (필요 시) 언어 런타임.
- **근거** — 인용 없이 실제 의존성에서 나온다 — CLI가 없으면 명령이 없고, init 없이는 draft를 담을 곳이 없고, 백로깅 절차를 강제하는 훅은 백로그보다 먼저 있어야 한다.
- **기각한 대안** — "백로그 먼저, 도구는 나중": 다음 단계 명령이 실행되지 않는다.

## ADR-019 판단 단위는 태스크, 경계선은 측정으로

- **맥락** — "얼마나 어려워야 4역할을 쓰는가"의 임계값을 외부 연구에서 가져올 수 있는가.
- **결정** — 4역할 적용 여부는 프로젝트가 아니라 태스크마다 정한다. 임계값을 명시하지 않고, walking skeleton이 쌓는 태스크별 성공 · 실패 · 재작업 · 회귀 기록으로 이 저장소에서 직접 측정해 정한다.
- **근거** — 멀티에이전트 조율 손익 연구가 재는 것은 과제 정확도이고 이 설계가 내세우는 것은 판단의 독립성이라 종속변수가 다르다. 배정 시점에는 태스크의 단일 에이전트 기준 성공률을 알 수 없고, 벤치마크 평균은 눈앞 태스크의 성공률이 아니다. 놓친 회귀의 비용은 검증 비용과 비대칭인데 평균 지표에는 그 비대칭이 없다. 복잡도의 잣대로는 깊이(추론 길이) × 너비(필요 역량의 다양성) 두 축이 있고, 스케줄 계측의 길이 · 폭과 같은 형태다.
- **기각한 대안** — 외부 연구의 정량 임계값을 상수로 쓰기: 위 세 이유로 쓸 수 없다. 프로젝트 종류로 판단: 단순하게 시작한 프로젝트도 이후 태스크는 어려워질 수 있다.

## ADR-020 테스트 먼저는 AC 하나씩 TDD + 비즈니스 규칙 테스트, 훅으로 강제

- **맥락** — 테스트 먼저를 약속(지침 · 카드 문구)으로만 두면 에이전트가 구현을 먼저 쓰고 테스트를 뒤에 붙여도 막을 수단이 없다. 또 테스트를 AC에만 맞추면 AC 문장에 드러나지 않는 비즈니스 로직(경계값 · 거부 조건 · 기록 의무 등)이 테스트에서 빠진다.
- **결정** — 테스트 먼저는 AC 하나씩 TDD로 한다 — AC #n마다 Red(실패하는 테스트) → Green(테스트를 통과하는 최소 구현) → Refactor(정리) → 커밋 → AC #n+1 (RAIL-011). 테스트는 AC와 함께 카드의 비즈니스 규칙도 다룬다. 규칙은 카드 설명의 `## 비즈니스 규칙` 절에 관련 AC와 함께 적고(BL-014), 테스트는 `<카드 ID>#<n>` · `<카드 ID>#B<k>` 표식으로 카드에 잇는다(2.02). claude-code-agile-hooks가 소스 편집 전에 다음 AC와 그 규칙들의 표식을, `Done` 전에 모든 표식을 검사해 강제한다(RAIL-019).
- **근거** — "AC = 함수 = 커밋"(1.02 P7)이므로 테스트 · 구현 · 커밋의 단위도 AC 하나로 맞추면 커밋 하나가 테스트 하나와 함수 하나를 함께 담는다. 카드가 테스트 대상의 원천이 되어 AC와 규칙 목록만 읽으면 무엇을 테스트해야 하는지 정해지고, 표식 문자열만으로 훅이 기계적으로 검사할 수 있다(1.02 P6).
- **기각한 대안** — 테스트를 전부 먼저 쓰고 구현: 앞쪽 AC를 구현하며 알게 된 것이 뒤쪽 테스트에 반영되지 않고, 커밋 하나가 AC 하나에 대응하지 않는다. 스펙 · 스텁 → pending 테스트 → 구현: 테스트가 실패 없이 보류 상태로 남아 테스트 먼저를 검증하지 못하고, 약속으로만 지켜진다. ATDD 이중 루프(인수 테스트 바깥 루프 + 단위 테스트 안쪽 루프): 카드의 AC가 이미 인수 기준이라 바깥 루프가 중복이고, 훅이 두 층을 구분해 검사할 기준이 없다. 커밋 시점 검사: 구현을 다 쓴 뒤에 막으므로 순서를 강제하지 못한다 — 편집 시점에 막아야 테스트가 먼저 생긴다.
- **한계** — 훅은 표식 문자열의 존재만 본다. Bash로 소스를 쓰는 경우와 테스트가 실제로 실패하는지(빨강)는 검사하지 않는다.

## ADR-021 커밋 포맷과 토큰 계량을 분리한다

- **맥락** — coding-agent-git-commit-tool이 커밋 형식 검사 · 트레일러 부착과 함께 토큰 계량까지 맡았다(ADR-011). 커밋 훅이 세션 트랜스크립트를 읽어 토큰을 재므로, 깃 커밋과 토큰 측정이 한 훅에 묶인다.
- **결정** — coding-agent-git-commit-tool은 포맷 레이어로 줄인다 — 커밋 메시지 형식을 검사하고 `Task-Id` · `AI-Tool` · `AI-Model` · `Co-Authored-By` · `Hooks-Commit` · `Signed-off-by` 같은 트레일러만 붙인다. 토큰 계량은 하지 않는다. 토큰 계량은 별도의 토큰 계량 컴포넌트(이름 미정)가 맡는다. 그 컴포넌트의 이름 · 저장소 · 측정 방식은 정하지 않는다(`TBD(Q-18)`).
- **근거** — 강결합이다. 계량이 커밋 훅에 있으면 측정의 단위 · 시점이 커밋에 묶이고, 측정 방식을 바꿀 때마다 모든 대상 저장소의 git 훅을 고쳐야 한다. 측정 실패 사유 · 근사치 한계 같은 측정의 불확실성이 커밋 포맷 도구의 책임으로 섞인다. 포맷은 결정적 검사라 이미 확정할 수 있지만 측정 방식은 아직 실험 단계라, 둘을 나누면 확정된 쪽이 미정인 쪽에 끌려다니지 않는다.
- **기각한 대안** — 커밋 훅에 계량을 그대로 두기(ADR-011): 위 강결합. 포맷 도구 안에서 모듈만 나누기: 저장소와 릴리스 주기가 같아 결합이 그대로 남는다.
- **예외(2026-10-29)** — 토큰 계량 컴포넌트가 정해지기 전까지(`TBD(Q-18)`) 실행 한 번의 토큰(`session`)은 오케스트레이터가 읽는다. 헤드리스 `claude -p` JSON 출력의 `usage`(입력(캐시 포함) + 출력)를 `AgentRunner` 포트 뒤의 `ClaudeCodeRunner`가 읽는다. 측정이 아니라 실행 결과 메타데이터의 판독이라 계량 책임을 옮기지 않는다. 커밋 귀속분(`commits`)은 Q-18이 정해진 뒤 토큰 계량 컴포넌트가 맡는다 (ORC-021, 3.04 §6).

## ADR-022 구현 계획은 SOAP + AC + DoD, 착수 전 계획 → 리뷰 → 계획 승인

- **맥락** — Claude가 backlog.md CLI로 일할 때 구현 계획 없이 태스크를 만들고 착수한다. 계획이 있는지는 아무 훅도 보지 않았고, `backlog draft create`에는 `--plan`이 없다. 자유 형식 계획은 작성됐는지를 기계적으로 판정할 수 없다. 또 착수 전에 사람이 계획을 보고 승인하는 자리가 없다.
- **결정** — 구현 계획은 SOAP 노트 형식 + AC + DoD로 쓴다. 계획은 예약 제목 `### Subjective` · `### Objective` · `### Assessment` · `### Plan`을 이 순서로, 철자 그대로, 한 번씩 쓰고 각 본문을 비우지 않는다 (BL-015, 2.02 구현 계획 형식). 태스크는 계획 → 리뷰 → 계획 승인을 거쳐야 착수한다(`task/<태스크 ID>` 브랜치를 만든다) — 계획 작성 → 사람의 리뷰 → 사람의 계획 승인 (BL-017). 계획 승인은 사람이 자기 키로 서명한 빈 커밋 `Plan-Approved: <태스크 ID>`로 기록한다(`git commit --allow-empty -S`). 훅도 Claude도 이 커밋을 만들지 않는다. claude-code-agile-hooks가 `draft promote`와 `task/<태스크 ID>` 브랜치 생성 · 전환(`git switch -c` · `checkout -b` · `switch` · `checkout` · `worktree add`) 두 시점에 계획 · AC · DoD를 검사하고, 브랜치 생성 · 전환에서 승인 게이트를 돈다 (RAIL-020). `-s "In Progress"`는 계속 하지만 시작 시각을 남기는 기록이고 게이트가 아니다. 게이트는 훅이 설치된 곳에서만 돈다 — 사람이 훅 없이 터미널에서 만든 브랜치는 검사하지 않는다 (decision-3). 승인 게이트는 HEAD에서 닿는 커밋 중 제목이 정확히 `Plan-Approved: <태스크 ID>`인 커밋을 찾아, 그중 하나라도 유효한 서명(`%G?` = `G`)이고 서명자 principal(`%GS`)이 프로젝트 설정 `humanSigners`(3.04 §7)에 있어야 통과시킨다. 서명 키는 둘로 나눈다 — Claude Code 세션은 AI 전용 키로만 서명하고, 사람 키는 ssh-agent 밖에 두어 서명할 때마다 암호를 입력한다. 두 키는 `allowed_signers`에 서로 다른 principal로 올리고, 사람 principal만 `humanSigners`에 적는다 (decision-2, decision-1 대체, claude-code-agile-hooks TASK-58 · decision-14). 게이트 시점은 decision-3이 decision-2의 착수 시점 부분을 대체해 정했다.
- **근거** — 제목을 키워드처럼 고정하면 절을 문자열 일치로 찾을 수 있어 모호한 자연어 판정을 피한다(1.02 P6). SOAP는 확인한 사실(O)과 판단(A)을 나누므로, 리뷰어가 근거와 선택을 따로 따질 수 있다. 검사 시점을 둘로 두는 것은 MCP · 웹 UI로 만든 카드도 착수 시점에 다시 걸러내기 위해서다. 착수 시점을 `-s "In Progress"`가 아니라 브랜치 생성 · 전환으로 두는 것은 착수의 판단 기준(ADR-014)과 같은 시점이어야 승인 없이 브랜치만 만든 착수가 생기지 않기 때문이다. 계획 승인을 서명 커밋으로 두면 git 이력에 남고, 서명자로 누가 남겼는지 검증할 수 있다. 키를 둘로 나누고 사람 키를 ssh-agent 밖에 두면 Claude 세션이 사람 키로 조용히 서명할 수 없으므로, 서명자 principal로 사람과 AI를 가를 수 있다.
- **기각한 대안** — 계획 존재만 검사: 빈 템플릿이나 한 줄짜리 계획도 통과한다. 자유 형식 계획 + 자연어 판정: 판정이 모호하고 훅이 결정적으로 막지 못한다. 계획 승인을 사람만 붙이는 라벨 · 필드로 기록: Claude도 같은 backlog.md CLI로 라벨 · 필드를 쓸 수 있어 사람과 구분되지 않는다. 사람이 만든 리뷰 파일: 같은 이유로 작성자를 구분하지 못한다. 서명 없는 커밋: 커미터 이름 · 이메일은 누구나 설정할 수 있다. 한 키로 유효 서명만 확인: 사람과 AI를 구분하지 못한다. `-s "In Progress"` 때 승인 게이트(decision-2 원안): 착수가 브랜치 존재로 바뀐 뒤에는 브랜치를 먼저 만들고 상태를 나중에 옮기므로, 게이트 전에 착수가 생긴다.
- **결과** — 사람의 판단 지점에 착수 전 계획 승인이 더해진다. 승인 게이트는 승인 커밋이 없을 때 · 서명이 유효하지 않을 때 · 사람이 아닌 서명자가 서명했을 때를 나눠 안내하고, `humanSigners`가 없거나 비었으면 두 키 설정 방법을 안내하며 막는다. 커밋이 빈 커밋인지는 검사하지 않는다. 남은 위험: `allowed_signers`와 프로젝트 설정은 로컬 파일이라 에이전트가 고칠 수 있으므로 설정 변조 차단 훅으로 따로 보호해야 한다. 훅 없이 만든 브랜치는 승인 게이트를 거치지 않는다.

## ADR-023 단계별 커밋 · 테스트 파일 구조 · 커버리지 100%를 훅으로 강제

- **맥락** — 카드 생애주기의 산출물이 기계적으로 검사되지 않는다. 커밋 범위 훅은 draft 생성 커밋과 승격 커밋의 분리만 강제하고, 커밋 하나에 draft 여러 장을 허용한다. 승격 뒤 의존 정리와 순차 · 병렬 순서는 아무도 남기지 않는다. 테스트 먼저 훅(RAIL-019)은 표식이 테스트 파일 어딘가에 있는지만 보고, 파일 안 위치 · 순서와 DoD 표식은 보지 않는다. 커버리지 검사는 opt-in이고 임계값과 리포트 위치를 프로젝트가 정한다.
- **결정** — 세 가지를 훅으로 강제한다. ① 단계별 커밋: draft 작성 · 승격 · 작업 순서 · 시작 기록(`-s "In Progress"`) · 완료마다 커밋하고 push하지 않는다. `task/<ID>` 브랜치의 커밋은 메시지에 그 태스크 ID를 단다 (RAIL-025). 커밋마다 그 단계의 파일만 들어가고, 다음 단계 명령 전에 커밋되지 않은 `backlog/` 변경이 있으면 막는다. draft든 To Do 태스크든 앞으로 할 일이 새로 생기거나 다시 열리거나 의존이 바뀔 때마다 `--dep`로 의존을 정리하고, 의존 그래프를 위상 정렬한 단계별 작업 순서 파일(`backlog/work-order.md`)을 다시 계산해 바로 커밋한다(작업 순서에는 draft도 포함) (BL-016 · RAIL-002 · RAIL-021 · RAIL-023). ② 테스트 파일 구조: JavaScript · TypeScript · Java · Python · C++ 테스트 파일은 요약 → AC/DoD 구역 → Coverage 구역 순서이고, AC · 규칙 · DoD 표식은 AC/DoD 구역 안에만 둔다. 텍스트 끝이 `(수동)`인 DoD 항목은 표식을 요구하지 않는다 (RAIL-022, 2.02 테스트 표식 · 테스트 파일 구조). ③ 커버리지 100%: 5개 언어가 감지되면 `coverageCommand`가 필수이고, 100%(line + branch) 미달이거나 언어별 공식 기본 위치에 리포트가 없으면 push와 `-s Done`을 막는다 (RAIL-006 · NFR-017).
- **근거** — 단계 하나 = 커밋 하나면 이력만 읽어도 카드가 어느 단계에서 무엇이 바뀌었는지 보이고, 단계 사이에 남은 변경이 다음 단계 커밋에 섞이지 않는다. backlog.md는 병렬 묶음을 바로 내지 않으므로(`task list --ready`는 지금 착수 가능한 것만 보여 준다) 위상 정렬 단계를 파일로 남긴다 — 같은 단계는 병렬, 단계 사이는 순차다. 표식을 한 구역에 모으면 카드 → 테스트 대응을 한곳에서 읽고, 커버리지를 채우려는 테스트와 섞이지 않는다. 기준이 100%면 예외를 판단할 일이 없어 훅이 종료 코드와 파일 존재만으로 판정한다(1.02 P5 · P6). 리포트를 공식 기본 위치에 두면 별도 설정 없이 찾는다.
- **기각한 대안** — 커밋 하나에 draft 여러 장: 사람이 승인하는 단위(draft 하나)와 커밋 단위가 어긋난다. 단계에 push까지 넣기: push는 범위 밖이다(유저 결정 2026-10-12). 작업 순서를 파일 없이 `task list --ready`로만 보기: 지금 착수 가능한 것만 보이고 단계 전체의 순차 · 병렬 구분이 남지 않는다. 표식 존재만 검사(RAIL-019 그대로): 표식이 커버리지용 테스트 사이에 흩어진다. 커버리지 임계값을 프로젝트가 정하기: 임계값을 낮춰 우회할 수 있다.
- **결과** — 세부 규약은 claude-code-agile-hooks 구현을 따른다. 단계별 커밋: 단계 명령 전에 `backlog/`에 커밋되지 않은 변경이 있으면 막는다(TASK-59). 작업 순서: 의존은 태스크 파일 frontmatter `dependencies`에서 읽고, 파일 첫 줄의 해시가 현재 미완료 태스크 · 의존과 맞지 않으면 `draft promote`와 `task/<ID>` 브랜치 생성 · 전환(승인 게이트와 같은 시점)을 막는다(decision-3). 지금 구현은 `draft promote` · `-s "In Progress"`에서 막는다(TASK-60). draft 포함과 생성 직후 강제(TASK-64)와 브랜치 시점 이동은 아직 구현 전이다. 오케스트레이터는 작업 순서 파일을 읽지 않는다 (ORC-005). 테스트 파일 구조: 첫 주석 블록에 태스크마다 `<ID>: <요약>` 헤더, 줄 전체가 주석인 구역 표식 `== AC/DoD ==` · `== Coverage ==`를 한 번씩 둔다. 헤더도 구역 표식도 없는 기존 파일은 유예한다(막지 않고 안내만 한다)(TASK-61). `(수동)` DoD: 테스트로 검증할 수 없는 DoD 항목은 가짜 테스트로 표식을 채우지 않고, 텍스트 끝 `(수동)`으로 카드에 드러내 사람이 계획 리뷰 · 승인 때 판단한다(유저 결정 2026-10-29). 커밋 메시지의 태스크 ID: `task/<ID>` 브랜치에서 메시지(제목 · 본문 · 트레일러)에 그 ID가 단어 경계로 없는 커밋은 거부한다. 최상위 TASK-14의 ID 없는 이력은 고치지 않는다 (RAIL-025). 커버리지: 기준 지표는 line + branch이고 임계값은 각 도구 설정에 둔다. 리포트 위치는 `coverageReportDir`로 바꿀 수 있고, `-s Done` 게이트는 새 훅 `require_coverage_on_done.py`가 돈다(TASK-62, 3.04 §7).

## ADR-024 대상 프로젝트의 API 예외 처리는 항상 PRG

- **맥락** — 대상 프로젝트의 API가 예외를 어떻게 돌려줄지 규약이 없다. 유저 결정(2026-10-12)으로 API 예외 처리는 항상 Post/Redirect/Get 패턴을 쓴다.
- **결정** — 상태를 바꾸는 요청(Post)이 예외로 끝나도 그 응답에서 결과를 바로 돌려주지 않고, GET으로 읽을 수 있는 위치로 리다이렉트(Redirect)한 뒤 클라이언트가 GET으로 결과를 읽는다(Get) (NFR-018, 3.04 §9). 강제 방법은 미정이다.
- **근거** — POST 응답에서 결과를 바로 돌려주면 새로고침 · 재시도가 같은 요청을 다시 보낸다. 리다이렉트 뒤 GET으로 읽으면 다시 읽어도 요청이 재전송되지 않는다. 예외도 같은 경로로 돌려 성공과 실패의 응답 흐름을 하나로 맞춘다.
- **기각한 대안** — 예외를 POST 응답 본문에 바로 돌려주기: 새로고침 · 재시도가 요청을 다시 보낸다. 성공만 PRG, 예외는 직접 응답: 응답 흐름이 둘로 갈린다.
- **미정** — 강제 방법(claude-code-agile-hooks의 훅으로 막을지, 대상 프로젝트의 테스트로 둘지(ADR-016))과 리다이렉트 상태 코드 · 예외 정보 전달 방식은 정하지 않았다.

## ADR-025 설계 문서는 저장소마다 두고, 최상위를 고치면 컴포넌트에 전파한다

- **맥락** — 설계 문서는 최상위 한 곳과 컴포넌트 세 곳(agent-orchestrator · claude-code-agile-hooks · coding-agent-git-commit-tool)의 `design/`에 나뉘어 있다. 컴포넌트는 `components/<이름>`에 두는 독립 git 저장소이고, 최상위 `.gitignore`가 제외한다. 서브모듈이 아니다. 이렇게 나눈 이유는 문서 곳곳에 흩어져 있고 결정으로 적힌 적이 없다. 컴포넌트 쪽에는 상속 규칙("어겨야 하면 최상위 결정을 먼저 고친다")만 있고, 최상위를 고치면 컴포넌트도 맞춘다는 전파 의무는 없다. 2026-10-11 사전 점검에서 최상위 ↔ 컴포넌트 불일치가 29건 나왔다. 유저 결정(2026-10-12)으로 전파를 강제하고 그 규칙을 최상위 문서에 둔다.
- **결정** — 설계 문서는 저장소마다 둔다. 최상위는 목표 · 원칙 · 요구사항 ID를 소유하고, 컴포넌트 `design/`은 그것을 같은 ID로 이어받아 패키지 · 클래스 · 결정 · 테스트로 내린다(0 문서 정보 문서 계층). 최상위 `design/`을 고친 변경은 0 문서 정보의 장 대응표로 영향받는 컴포넌트 `design/`을 반드시 같이 고치고, 컴포넌트 쪽은 각 저장소의 카드로 커밋하고 커밋 본문에 최상위 태스크 ID를 참조로 적는다(저장소마다 ID 접두어 · 브랜치 규칙이 달라 같은 ID를 쓸 수 없다). 영향이 없으면 최상위 태스크 브랜치의 커밋 트레일러 `Propagation-None: <컴포넌트>: <사유>`로 사유를 남긴다. claude-code-agile-hooks의 훅이 이를 강제하고, 대응표는 훅이 문서에서 읽는다 (RAIL-024).
- **근거** — SDD는 명세를 먼저 고친 뒤 코드를 맞춘다. 명세가 코드와 같은 저장소에 있어야 둘이 같은 PR에서 함께 바뀐다. 오케스트레이터가 띄우는 에이전트는 작업하는 저장소의 `design/`을 조상 문서로 읽으므로(ORC-019), 명세가 그 저장소 안에 있어야 한다. 문서가 나뉘면 어긋남이 쌓이므로 전파 의무를 두고, 사람의 주의에 맡기지 않고 훅으로 막는다(1.02 P6). 대응표를 문서에 두면 표만 고쳐도 훅을 고치지 않는다.
- **기각한 대안** — 최상위 하나만: 명세가 코드와 다른 저장소에 있어 같은 PR에서 함께 바뀌지 않고, 컴포넌트 저장소에서 일하는 에이전트가 조상 문서로 읽지 못한다. 컴포넌트에 사본: 사본은 원본과 어긋나고, 원본을 하나로 두는 편집 규칙에 어긋난다. 서브모듈: 최상위가 컴포넌트의 특정 커밋을 고정하므로 컴포넌트 저장소가 독립적으로 움직이지 못하고, 서브모듈 갱신 커밋이 따로 생긴다. 고정만 하고 내용을 맞추지는 않으므로 불일치는 그대로 남는다.
- **결과** — 훅(`require_design_propagation.py`)은 최상위 태스크를 `-s Done`으로 옮길 때 막는다. 그 태스크 브랜치에서 base에 없는 커밋의 `design/` diff를 장 대응표의 행에 대응시키고, 영향받는 컴포넌트마다 로컬 `components/<이름>`의 모든 브랜치에서 `Refs: coralstay-software-factory <태스크 ID>` 줄이 있는 커밋을 찾는다. 없으면 그 태스크 브랜치의 `Propagation-None: <컴포넌트>: <사유>` 트레일러를 찾고, 둘 다 없으면 빠진 컴포넌트를 안내하며 막는다. 원격 브랜치는 보지 않고 커밋된 변경만 본다 (claude-code-agile-hooks TASK-63 · decision-15).
