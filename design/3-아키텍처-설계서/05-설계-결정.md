## ADR-001 역할마다 완전히 독립된 프로세스

- **맥락** — 판정자가 구현자의 추론 경로를 물려받지 않아야 한다(P1). 제품군이 다양해 역할마다 다른 설정 · 권한 · 작업 디렉토리가 필요하다.
- **결정** — Implementer · Reviewer · Verifier · Logger를 전부 별도 프로세스(기본 `claude -p`)로 띄운다. 역할 하나를 다른 프로바이더 CLI로 바꿀 수 있다.
- **근거** — Claude Code에서 컨텍스트 경계는 곧 프로세스 경계이고, 세션 간 전달은 순수 텍스트뿐이라 격리가 도구 차원에서 보장된다. 토큰 귀속도 쉬워진다 — 세션 내부 위임이면 부모 · 자식 사용량이 한 응답에 섞이지만, 독립 프로세스면 각자 자기 몫만 떨어진다.
- **기각한 대안** — Subagent · Agent Teams(세션 내 위임): 대화 이력을 공유해 독립 판정 조건을 못 맞추고, 역할별 설정 · 권한 · 디렉토리를 나눌 수 없다. 같은 세션 안에서 단계만 나누기: 같은 이유.
- **반증** — Implementer 단독 + self-review 대비 AC 재작업률 · 회귀 발생률을 유의미하게 낮추지 못하면 Reviewer · Verifier를 Implementer 세션 안의 단계로 접는다 (1.02 반증 기준).

## ADR-002 Java 25 + virtual thread + Semaphore

- **맥락** — 동시성은 한 자릿수~십수 개의 OS 서브프로세스 규모다. 즉시 스폰과 비동기 큐 사이에서 골라야 한다.
- **결정** — Java 25(JVM), virtual thread + Semaphore. 즉시 스폰과 비동기 큐의 이분법 대신 용량 제한 워커풀로 절충한다 — 평상시엔 즉시 디스패치처럼, 트리거가 몰릴 때만 큐잉된다. AC 루프의 Reviewer처럼 지연에 민감한 경로는 전용 슬롯으로 뗀다.
- **근거** — 이 규모에서는 동시성 모델이 성능을 좌우하지 않는다. virtual thread의 실익은 `Process.waitFor()`를 블로킹으로 써도 되어 비동기 콜백이 사라지는 코드 단순성이다.
- **기각한 대안** — 즉시 스폰만: 트리거가 몰리면 상한 없이 뜬다. 비동기 큐만: 평상시에도 지연이 생긴다. 콜백 기반 비동기 I/O: 이 규모에서 얻는 성능이 없고 코드만 복잡해진다.

## ADR-003 정책은 `AllocationPolicy` 하나로 외부 주입

- **맥락** — "언제 · 얼마나 · 어떤 역할을 · 어떤 모델로" 스폰할지는 태스크와 실측에 따라 바뀐다.
- **결정** — `AllocationPolicy` 인터페이스 하나를 확장 지점으로 두고, 정책은 그 인터페이스를 구현한 **자바 클래스**로 쓴다. 내장 기본 구현이 있고, ① `-Dpolicy.class=` 시스템 프로퍼티 ② `java.util.ServiceLoader`(별도 jar 플러그인) 순으로 교체한다.
- **근거** — Kubernetes Scheduler Framework처럼 코어는 그대로 두고 정해진 확장 지점만 갈아끼운다. 정책에는 조건 판단(태스크 난이도 · 예상 토큰 · 역할별 분기)이 들어가므로 데이터 형식보다 코드가 맞고, 컴파일러의 타입 검사와 IDE 지원을 받는다(Spring이 XML 설정을 `@Configuration` 자바 클래스로 옮긴 것과 같은 이유). `-Dpolicy.class`와 `ServiceLoader`는 모두 JDK 표준이라 외부 의존성이 없다(NFR-010).
- **기각한 대안** — 오케스트레이터 내부 하드코딩: 정책을 바꿀 때마다 코어를 고친다. YAML 설정: JDK에 파서가 없어 외부 라이브러리(SnakeYAML)가 필요하고(NFR-010 위반), 암묵적 타입 변환 함정과 역직렬화 취약점 이력(CVE-2022-1471)이 있으며, 조건 판단은 어차피 표현하지 못한다. key=value 설정: 의존성은 없지만 계층 · 목록 · 조건을 표현하지 못해 정책 범위가 넓어지면 키 규약과 손으로 짠 검증이 늘어난다. 런타임 컴파일(`javax.tools.JavaCompiler`로 정책 `.java`를 시작 시 컴파일): 재빌드 없이 바꿀 수 있지만 정책 파일이 곧 실행 코드라 에이전트가 쓸 수 없는 위치와 보호 장치를 따로 설계해야 하고, 실행 환경에 JDK가 필요하다.

## ADR-004 지연 · 비용 마진은 전체 공유 버퍼 하나

- **맥락** — 태스크마다 지연 · 비용이 들쭉날쭉하다.
- **결정** — 태스크별 버퍼를 두지 않고 오케스트레이터 전체의 공유 버퍼 하나로 관리한다.
- **근거** — Critical Chain Project Management의 자원 제약 인지 방식을 차용한다(LLM 에이전트에 적용한 선행 연구는 없고 고전 PM 이론에서 가져온 확장이다). Semaphore로 동시 작업량을 제한하는 것은 Little's Law(리드타임 = WIP ÷ 처리량)로도 뒷받침된다.
- **기각한 대안** — 태스크별 개별 버퍼: 버퍼가 태스크마다 흩어져 낭비된다.

## ADR-005 동시성 상한 = `min(그래프 폭, 자원 실측)`

- **맥락** — Semaphore 용량을 무엇으로 정할지.
- **결정** — 자원 상한은 (a) `claude` 프로세스 1개의 peak RSS와 (b) API 플랜의 분당 요청 한도 실측으로 정하고, (c) 스케줄 라운드마다 잰 그래프 폭과 비교해 작은 쪽을 쓴다.
- **근거** — 폭보다 큰 용량은 채울 일감이 없고, 폭보다 작은 용량은 work-conserving을 어긴다. 자원이 남아도 띄울 독립 노드가 없으면 용량은 의미가 없다.
- **기각한 대안** — 벤치마크로 정한 고정 상한: 이 백로그의 구조와 이 호스트의 자원을 반영하지 못한다. 무한정 늘리기: 같은 코드베이스를 동시에 건드리는 에이전트가 많을수록 어긋날 위험이 조합적으로 커진다.
- **반증** — 실측 폭이 거의 항상 1~2이면 워커풀 · Semaphore · 결합도 분석 전체가 과설계다. 순차 실행 하나로 접는다 (NFR-003).

## ADR-006 저장 상태는 3개, 세밀한 구분은 계산 레이어

- **맥락** — 사람용 칸반은 상태가 적고, 자동화 워크플로 엔진은 상태가 많다. Airflow `TaskInstanceState` 13개(예: `UPSTREAM_FAILED`를 `FAILED`와 구분), BPMN 2.0 액티비티 생애주기 약 10~11개, Temporal `WorkflowExecutionStatus` 7~8개.
- **결정** — backlog.md의 `To Do` · `In Progress` · `Done`을 그대로 쓴다. 오케스트레이터에 필요한 구분은 backlog.md가 읽기 시점에 계산하는 readiness(`isReady` · `isBlocked` · `blockingDependencies` · `missingDependencies`)로 얻고, 더 필요하면 오케스트레이터의 계산(비저장) 레이어를 얹는다.
- **근거** — 두 근거는 대상이 다를 뿐 충돌하지 않는다. 3상태는 사람이 보는 보드이고, "지금 하는 방식을 그대로 시각화하고 병목이 증명될 때만 구조를 늘린다"(Anderson, Kanban 2010)의 정석적 사례다. 기계용 구분은 Airflow가 `TaskInstanceState` 위에 `DagRunState`를 따로 두듯 층을 나눠 얻는다. 단, 상태 개수와 인지 부하를 직접 잰 실험 연구는 없다 — 방법론 원칙이다.
- **기각한 대안** — backlog.md 저장 상태 어휘를 늘리기(blocked · archive 등을 상태로): blocked는 의존에서 계산되는 파생 속성이고 archive는 별도 동작이다. 사람의 보드를 기계 사정으로 복잡하게 만든다.

## ADR-007 회수는 kill — 장수 세션을 두지 않는다

- **맥락** — 에이전트를 상시 대기시킬지, 태스크마다 띄우고 끝낼지.
- **결정** — 태스크마다 스폰하고, 끝나면 프로세스 · 자손 종료(SIGTERM → 유예 → SIGKILL) + Registry 제거 + 허가 반납을 한 호출로 한다. 제거에 성공했을 때만 허가를 반납해 멱등으로 만든다.
- **근거** — 헤드리스 세션은 종료가 곧 컨텍스트 폐기다. 임상 규모 실험에서 단일 지속 에이전트는 작업량이 늘자 정확도가 73.1% → 16.6%로 붕괴했고, 오케스트레이션된 다중 에이전트는 90.6% → 65.3%로 버텼으며(p<0.01) 토큰은 최대 65배 적었다 (부록 참고 문헌). 이 근거는 "장수 세션보다 태스크 단위 스폰 · 회수"까지만 쓴다.
- **기각한 대안** — 상시 대기 4역할 + 대화형 `/clear`: 헤드리스 프로세스에는 명령을 더 보낼 통로가 없고, 장수 세션은 작업량이 늘면 무너진다.

## ADR-008 직접 메시징은 포인터만 싣는 보조 채널

- **맥락** — AutoGen류의 실시간 conversable-agent 대화가 이 설계엔 없다. Claude Code는 세션 간 메시징(`ListAgents` · `SendMessage`, 머신 로컬 소켓, Anthropic 서버 비경유)을 기본 기능으로 준다. 메시지는 순수 텍스트이고 보내는 쪽의 이력 · 파일을 포함하지 않는다.
- **결정** — 메시지에는 포인터(태스크 ID · AC 번호 · 파일:라인)만 싣고 본문은 수신자가 파일에서 읽는다. 에이전트 할당 시점에 배선한다. 파일 기반 WAL이 1차 기록이다. 스폰은 bare 모드를 쓰지 않는다(bare 모드는 inbox 소켓을 바인딩하지 않는다). 동작하지 않으면 WAL 디렉토리를 파일 메일박스로 폴링한다.
- **근거** — 메시징이 이력을 싣지 않으므로 판단 독립성(P1)을 해치지 않고, 영구 기록은 파일에 남아 회수(P3)와 함께 사라지지 않는다.
- **기각한 대안** — 에이전트 간 대화로 협업: 맥락이 섞여 판단 독립성을 잃는다. 실험 기능인 Agent Teams: 세션 내 위임이라 ADR-001과 충돌한다.

## ADR-009 재로딩 고정비는 프리픽스 캐싱으로 상쇄

- **맥락** — 독립 프로세스는 부착마다 조상 문서를 루트까지 다시 읽는다.
- **결정** — task → milestone → root 조상 문서 경계에 프롬프트 캐싱을 적용한다. 프리픽스에는 가변값을 섞지 않는다. 판정자들은 같은 프리픽스를 공유해 병렬로 본다.
- **근거** — 캐시에 쓴 프리픽스를 공유하는 에이전트는 정상 비용의 약 2.5~10%로 읽는다(Anthropic Prompt Caching). 별도 평가가 41~80% 비용 절감, TTFT 13~31% 개선을 보고했고, 인프라 레벨 선례(EACC · SGLang RadixAttention)도 있다 (부록 참고 문헌). "백로그 계층을 루트까지 재로딩"을 1:1로 다룬 논문은 없고, 장기 맥락 · 멀티에이전트 컨텍스트 재사용의 특수 사례로 본다.
- **기각한 대안** — 장수 세션으로 재로딩 회피: ADR-007. 보류 — Reviewer · Logger가 Implementer의 요약 + diff만 읽는 비대칭 로딩: 고정비를 더 낮출 수 있지만 판정 근거가 줄어든다 (`TBD(Q-2)`).

## ADR-010 Verifier를 DoD · AC로 나누고, 채점 기준은 추측하지 않는다

- **맥락** — MetaGPT의 QA, ChatDev의 Tester는 나름의 평가 기준을 갖고 있다. 이 설계는 무엇이 pass · fail인지 아직 없다.
- **결정** — 채점 기준과 무관하게 정할 수 있는 것만 정한다. ① Verifier를 DoD(결정적 검사 — 테스트 · lint 종료 코드)와 AC(판단)로 나눈다. ② 판정 출력 스키마 `{ac_id, verdict, evidence, blocking}`. ③ Reviewer 최대 `TBD(Q-11)`회 왕복 후 사람 호출 — AC 루프 무한 반복 방지. ④ Reviewer는 의견, Verifier 하나가 최종 게이트(P4). Reviewer pass · fail 기준과 Verifier · AC 판정 기준은 추측으로 채우지 않는다.
- **근거** — AC(개별)와 DoD(공통)는 backlog.md가 `--check-ac` · `--check-dod`로 이미 주는 구분이다. 판정자가 여럿이면 판정이 갈리고 수렴 지점이 없으면 루프가 끝나지 않는다. 임의 명세의 충족을 판정하는 일반 절차는 없으므로 판정기는 프로젝트가 유한하게 쓴다(P5).
- **기각한 대안** — 다른 프레임워크의 평가 기준 차용: 이 설계의 종속변수(판단의 독립성)와 맞지 않는다. 다수결 판정: 수렴 지점이 없다.

## ADR-011 토큰은 API 사용량 메타데이터로 커밋마다 잰다

- **맥락** — LLM은 생성 중 자기가 몇 토큰 썼는지 아는 내장 카운터가 없다. 토큰 수는 API가 응답마다 돌려주는 메타데이터다.
- **결정** — coding-agent-git-commit-tool의 커밋 훅이 세션 트랜스크립트의 assistant `message.usage`를 합산하고 `tool_use` 블록을 세어 커밋 트레일러로 남긴다. 측정 실패는 `unavailable (<사유>)`로 남긴다. 측정 방식은 채택하되 정확도는 확정하지 않는다.
- **근거** — 이미 쓰고 있는 실측 방식이고, 실패-투명성 패턴이 있다. 값은 근사치이고 무관한 대화가 섞이면 과대평가될 수 있다고 도구 스스로 밝힌다. Reviewer · Verifier처럼 짧게 한 번 도는 프로세스는 트랜스크립트 전체를 한 번 합산하면 된다 — 헤드리스 실행이어도 트랜스크립트는 같게 남는다.
- **기각한 대안** — Logger가 다른 역할에게 "얼마나 썼어?"라고 묻기: 모델은 그 값을 모른다. 측정 실패 시 추정치 기록: 조용한 오측정이 된다.

## ADR-012 완료 시점에 커밋을 읽어 카드에 기록한다

- **맥락** — 커밋이 함수 단위라 함수별 작업 내역과 토큰이 커밋에 흩어져 있다. 이력을 나중에 정리하면 흔적이 사라질 수 있다.
- **결정** — Done 전환 시점(`-s Done --final-summary`)에 태스크 브랜치의 커밋을 읽어 함수별 작업 내역 · 토큰 집계를 카드에 기록한다.
- **근거** — 기록이 카드(와 카드를 담은 커밋)에 남으므로, 이력 정리 방식이 기록 보존과 분리된다.
- **기각한 대안** — `git log`만을 기록으로 삼기: 스쿼시하면 함수별 귀속이 사라진다.

## ADR-013 모든 발자취는 Git에, 정리는 완료 시점에

- **맥락** — 에이전트가 상태를 바꾸고 시도할 때마다 커밋이 남아 사람용 로그 추적이 어려워진다(커밋 파편화).
- **결정** — 발자취는 Git이 전부 품는다. 메인 브랜치가 더러워지는 문제는 태스크 완료 시점에 정리한다. 정리 방식(스쿼시 · 머지 커밋)은 `TBD(Q-4)`이다.
- **근거** — 태스크당 최소 커밋 수 = AC 개수로 배정 전에 세어지고, 파일 하나의 함수 수준이라 수백 개가 되는 일은 드물다. 남은 미지수는 자가 치유 재시도 배수뿐이고, walking skeleton이 남기는 AC당 재시도 분포로 정한다 — 남의 관행을 그대로 가져오지 않는다. 기록 보존은 ADR-012가 해결하므로 이 선택은 이력 가독성의 문제다.
- **대안 비교** — Squash and Merge: 커밋들을 하나로 합쳐 부모 1개 커밋으로 얹는다. 원래 커밋은 `git log main`에서 사라진다. 이미 푸시해 공유한 커밋을 스쿼시하면 해시가 바뀌어 받아간 쪽이 갈라지므로, 그 브랜치를 혼자 가졌을 때만 안전하다(에이전트 워크트리 브랜치는 대체로 해당). Merge commit: 부모 둘로 엮고 커밋이 그대로 남는다.

## ADR-014 Worktree + 1태스크 1에이전트 1파일 1주제

- **맥락** — 여러 에이전트가 같은 소스 파일이나 인덱스 파일을 동시에 건드리면 시스템이 마비된다. 사람도 메인 작업 트리에서 같은 파일을 열고 있을 수 있다.
- **결정** — 에이전트마다 `git worktree`로 물리 폴더와 브랜치를 분리하고, 태스크 하나는 파일 하나만 다룬다. 사람과의 충돌은 상태 락으로 막는다 — 사람이 태스크를 `In Progress`로 옮기면 그 파일의 태스크에 배정하지 않는다.
- **근거** — 태스크가 파일 하나에 대응하므로 락의 단위도 파일 하나이고, 상태 값 자체가 락이라 별도 잠금 파일 · 프로토콜이 필요 없다. 사람이 상태를 내려놓으면 락도 풀린다.
- **기각한 대안** — 같은 작업 트리에서 브랜치만 나누기: 인덱스와 작업 파일이 공유된다. 별도 잠금 파일: 상태와 락이 따로 놀아 어긋날 수 있다.

## ADR-015 고빈도 상태는 임베디드 DB, Git은 최종 영속화

- **맥락** — 상태 값과 프롬프트 캐시를 매번 디스크 마크다운으로 읽고 쓰면 레이턴시가 커진다.
- **결정** — 수없이 바뀌는 조율 정보 · 작업 큐 · 캐싱 상태는 메모리 · 임베디드 DB(SQLite · H2)가 받고, Git은 형상 관리 목적의 최종 영속화에만 쓴다(이중 영속화).
- **근거** — 파일 I/O 병목을 피하면서 진실의 원천은 Git에 남긴다.
- **기각한 대안** — 모든 상태를 backlog.md 마크다운으로만: 고빈도 갱신에 디스크 I/O가 병목이 된다. 외부 DB 서버: 단일 JVM 구성(ADR-017)과 맞지 않는다.

## ADR-016 규칙은 대상 프로젝트의 테스트에

- **맥락** — 아키텍처 · 컴플라이언스 규칙을 미들웨어에 넣을지 대상 프로젝트에 넣을지.
- **결정** — 규칙의 실행과 검증은 대상 프로젝트의 테스트 코드(ArchUnit 레이어 검증, JavaParser · 리플렉션 기반 컴플라이언스 게이트 등)에 두고, 미들웨어는 빌드 결과의 종료 코드만 보고 통과시킬지, 에러 로그를 묶어 재작업을 지시할지만 정한다.
- **근거** — 판정기는 프로젝트마다 유한하게 써야 한다(P5). 미들웨어는 프로젝트 종류와 무관해진다.
- **기각한 대안** — 미들웨어가 규칙을 해석: 프로젝트마다 미들웨어를 고쳐야 하고, 판정 일반 절차가 없다는 제약에 부딪힌다.

## ADR-017 수직 확장(단일 JVM)

- **맥락** — 에이전트 수가 늘 때 Pod 분산(수평)과 고사양 단일 서버(수직) 중 무엇으로 갈지.
- **결정** — 수직 확장. 배정 · 정적 분석 · 웹 화면은 virtual thread가 메모리 위에서 다루고, 무거운 에이전트 코딩과 빌드는 커널 자원(`cgroups`)과 RAM 디스크(`tmpfs`)를 쪼개 쓴다. 병목 대응은 2.04 수직 확장 병목.
- **근거** — 모든 작업 공간이 `tmpfs`에 있고 데이터가 단일 JVM 메모리 버스 안에서 오가면, Pod 사이 gRPC · REST로 소스 · 로그를 주고받는 오버헤드가 0이 된다. 에이전트 구동 속도와 자가 치유 회전이 수평 확장보다 빠르다. 막힌 에이전트는 RAM 디스크 폴더를 통째로 지우고 워크트리를 다시 만들어 새 에이전트를 투입한다.
- **기각한 대안** — 수평 확장(Pod 분산): 인프라 관리 비용과 클라우드 유연성에서 이기지만 네트워크 레이턴시와 직렬화 오버헤드를 진다.
- **리스크** — 장비가 고장 나면 대안이 없는 단일 장애점(SPOF). 이중화된 베어메탈로 완화한다.

## ADR-018 부트스트랩 순서 고정

- **맥락** — 도구 설치와 백로그 생성의 순서.
- **결정** — `git init` → backlog.md CLI → `backlog init` → coding-agent-git-commit-tool → claude-code-agile-hooks → (필요 시) 언어 런타임.
- **근거** — 인용 없이 실제 의존성에서 나온다 — CLI가 없으면 명령이 없고, init 없이는 draft를 담을 곳이 없고, 백로깅 절차를 강제하는 훅은 백로그보다 먼저 있어야 한다.
- **기각한 대안** — "백로그 먼저, 도구는 나중": 다음 단계 명령이 실행되지 않는다.

## ADR-019 판단 단위는 태스크, 경계선은 측정으로

- **맥락** — "얼마나 어려워야 4역할을 쓰는가"의 임계값을 외부 연구에서 가져올 수 있는가.
- **결정** — 4역할 적용 여부는 프로젝트가 아니라 태스크마다 정한다. 임계값을 명시하지 않고, walking skeleton이 쌓는 태스크별 성공 · 실패 · 재작업 · 회귀 기록으로 이 저장소에서 직접 측정해 정한다.
- **근거** — 멀티에이전트 조율 손익 연구가 재는 것은 과제 정확도이고 이 설계가 내세우는 것은 판단의 독립성이라 종속변수가 다르다. 배정 시점에는 태스크의 단일 에이전트 기준 성공률을 알 수 없고, 벤치마크 평균은 눈앞 태스크의 성공률이 아니다. 놓친 회귀의 비용은 검증 비용과 비대칭인데 평균 지표에는 그 비대칭이 없다. 복잡도의 잣대로는 깊이(추론 길이) × 너비(필요 역량의 다양성) 두 축이 있고, 스케줄 계측의 길이 · 폭과 같은 형태다.
- **기각한 대안** — 외부 연구의 정량 임계값을 상수로 쓰기: 위 세 이유로 쓸 수 없다. 프로젝트 종류로 판단: 단순하게 시작한 프로젝트도 이후 태스크는 어려워질 수 있다.
