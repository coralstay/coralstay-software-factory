# 3.02 동작 명세

동작은 부트스트랩(1회) → 백로깅(반복 재진입) → 태스크 실행(태스크마다 스폰 · 회수) 세 단계이고, 태스크 안에서는 구현은 순차, 그 결과에 대한 판단은 병렬이다.

## 전체 흐름

| 단계 | 하는 일 | 절 |
| --- | --- | --- |
| 환경 구축 | 서버에서 환경 구축 스크립트(`install-tools.sh`)로 Claude Code · backlog.md CLI · coding-agent-git-commit-tool을 한 환경에 탑재한다 | — |
| Phase A | 대상 저장소 부트스트랩 | §1 |
| Phase B | 사람의 상위 명세("OAuth 기능 개발" 등)를 받아 PM 모드가 함수 단위까지 일감을 쪼개 태스크 카드를 만든다 | §2 |
| Phase C 스케줄 | 새 `To Do` 카드를 감지해 실행 순서를 정한다 | §3 |
| Phase C 실행 | 태스크마다 워크트리 · 브랜치를 분기하고 역할 에이전트를 스폰해 AC 루프를 돈다. 끝나면 회수한다 | §4 · §6 |
| 완료 기록 | Done 전환 시 커밋을 읽어 카드에 기록한다 | §7 |
| 시각화 | 정적 분석기가 바뀐 소스의 콜 그래프를 뽑고, 사람은 카드 본문의 대시보드 링크로 코드를 확인한다 | 3.01 계층 3 · 4 |

## §1 Phase A — 저장소 부트스트랩

1회, 역할 분리 전에 한다. 백로그 명령을 쓰려면 CLI와 init이 먼저 있어야 하고, 백로깅 절차를 강제하는 claude-code-agile-hooks도 백로그를 만들기 전에 있어야 한다 — "백로그 먼저, 도구는 나중"은 성립하지 않는다. 순서를 벗어나면 다음 단계 명령 자체가 실행되지 않는다.

![Phase A — 부트스트랩 순서](../diagrams/02-bootstrap.svg)

| 순서 | 단계 | 역할 | 이 순서인 이유 |
| --- | --- | --- | --- |
| 1 | `git init` | 버전 관리 저장소 생성 | 이후 모든 도구(브랜치 · 커밋 훅 · worktree)가 `.git`을 전제로 동작한다 |
| 2 | backlog.md CLI 설치(`npm i -g`) | 계층 · 상태 · draft · promote 명령 제공 | CLI가 없으면 이후 모든 백로깅 명령이 없다 |
| 3 | `backlog init` | 이 저장소 전용 backlog 데이터 폴더 생성 | CLI가 전역에 있어도 프로젝트별 초기화 없이는 draft를 담을 곳이 없다 |
| 4 | coding-agent-git-commit-tool 설치 | 커밋 형식 강제 · 트레일러 부착 | 에이전트가 남기는 많은 커밋을 사람도 LLM도 `git log` 한 번으로 읽게 한다 |
| 5 | claude-code-agile-hooks 설치 | 브리핑 → draft → promote, task view 필독, In Progress + 브랜치 확인, 커밋 전 테스트 강제 | CLAUDE.md의 약속만으로는 프롬프트 인젝션 · 컨텍스트 압축에 깨질 수 있어 기계적으로 강제한다 |

대상 프로젝트의 언어 런타임 설치는 부트스트랩 순서에 넣지 않는다(1.03 비목표). Implementer가 코드를 쓰기 전에 대상 프로젝트 쪽에서 갖춘다.

## §2 Phase B — 백로깅

단일 Claude 세션(PM 모드)이 하고, 아직 역할 분리 전이다. 최초 1회가 아니라 진행 중 새 마일스톤 · 태스크가 필요해지면 언제든 재진입한다 (BL-011 · BL-012 · BL-013).

![Phase B — 백로깅 루프](../diagrams/03-backlogging.svg)

1. 브리핑 — `backlog overview` · `backlog board view` · `backlog search`로 현황을 읽는다. 재진입할 때도 브리핑부터 한다 — 이미 있는 마일스톤 · 태스크와의 중복 생성을 막는다.
2. plan mode — 계획을 프롬프트 출력으로 먼저 보인다.
3. `backlog draft create` — 계획을 draft로 담는다. 아직 태스크가 아니다.
4. 사람 승인 — draft를 확인하고 승인 · 반려한다.
5. `backlog draft promote <ID>` — 태스크로 승격한다. 직후 `--add-ref decision-N` · `--doc`으로 결정 · 문서를 연결하고, draft 단계의 의존을 다시 설정한다 (BL-004 · BL-010).
6. 보드 반영 — 새 마일스톤 · 태스크가 보드에 생긴다.

draft → 승인 → promote가 리뷰 체크포인트다. 태스크 단위로 남기는 이유는 셋이다.

- 에이전트가 사람보다 나을 때 — 태스크 단위로 남은 계획 · 결정 · 커밋을 따라가며 그 판단 과정을 배운다.
- 에이전트가 사람보다 못할 때 — 작은 단위로 쪼개져 있어야 어디서부터 잘못됐는지 짚어낼 수 있다.
- 다른 사람이 끼어들 수 있게 — 태스크 하나가 리뷰 체크포인트 하나가 되어, 다른 사람이 그 지점에서 피드백할 수 있다.

### 재진입 조건

재진입은 임의로 일어나지 않고, Implementer나 Verifier가 AC 밖 작업을 발견했을 때만 일어난다 (RAIL-012).

![범위 밖 작업 발견 시의 재진입](../diagrams/04-scope-reentry.svg)

- 사람이 승인하면 Phase B로 재진입해 새 마일스톤 · 태스크로 보드에 추가한다. 반려하면 현재 태스크 범위를 유지한다.
- 진행 중인 다른 태스크(Phase C)는 브랜치 · 워크트리가 분리돼 있어 재진입과 간섭하지 않는다 — 보드에 새 노드가 추가될 뿐이다.

## §3 Phase C — 실행 순서 결정

Phase B가 한 번에 여러 태스크를 Ready로 만들 수 있으므로, 에이전트를 만들기 전에 실행 순서를 정한다 (ORC-005 · ORC-006 · ORC-007).

| 신호 | 출처 | 효과 |
| --- | --- | --- |
| 선언된 의존 | `--dep`, `--json`의 `dependencies` · `readiness` | 순차 체인으로 묶는다 |
| 파일 · 모듈 결합 | 정적 분석으로 측정 (`TBD(Q-15)`) — 명시적 의존이 없어도 같은 파일을 건드리면 결합으로 본다 | 순차 체인으로 묶는다 |
| 사람이 선점한 파일 | 사람이 `In Progress`로 옮긴 태스크 | 그 파일의 태스크에 배정하지 않는다. 상태 값 자체가 락이라 별도 잠금 파일이 없다 |

- 의존 · 결합 중 하나라도 있으면 순차 체인으로 묶고, 둘 다 없는 노드끼리만 병렬 배정한다.
- 사람 선점 락이 막는 것은 에이전트끼리가 아니라 사람과 에이전트의 충돌이다. 에이전트끼리는 워크트리로 이미 갈라져 있지만, 사람은 메인 작업 트리에서 같은 파일을 열고 있을 수 있다.
- `isReady`는 사람이 선점한 `In Progress`도 참이므로, 배정 조건은 `isReady ∧ status = To Do`다.

![순차 체인과 독립 노드가 같은 큐에서 함께 스케줄된다](../diagrams/05-seq-par.svg)

Request Queue는 이 그래프를 입력으로 받아, 순차 체인은 선행 순서를 지켜 넣고 독립 노드는 Semaphore 용량 안에서 한 번에 여러 개를 admit한다. 지킬 제약은 "체인을 먼저 보낸다"가 아니라 work-conserving이다 — 체인의 admission이 독립 노드가 채울 빈 슬롯을 막지 않는다. 이 형태는 HEFT · DynTaskMAS · Airflow dynamic task mapping · Argo Workflows · Netflix Conductor와 같은 "DAG 생성 → 위상정렬 → 병렬 가능한 노드 동시 실행" 표준 패턴이다(부록 참고 문헌).

큐에 넣기 전에 그래프의 길이와 폭을 계산해 기록한다 (2.04 NFR-001 · NFR-002).

## §4 Phase C — 태스크 실행

Ready가 된 태스크 전용으로 역할 에이전트가 그때 생성되고, 끝나면 회수된다 — 상시 대기하는 에이전트가 아니다. 서로 다른 역할을 맡은 여러 LLM 인스턴스가 함께 문제를 푸는 Multi-Agent Collaboration 패턴을 태스크 단위로 인스턴스화한 것이다.

![Phase C — 태스크 실행 단계](../diagrams/06-phase-c.svg)

| 단계 | 하는 일 |
| --- | --- |
| C1 | 태스크 Ready (§3 순서대로) |
| C2 | Allocation Policy가 정한 역할 에이전트를 동적 생성 — 태스크 워크트리(`../<repo>-wt/<id>`) · `task/<id>` 브랜치에서 |
| C3 | AC 루프 — Implementer 커밋마다 Reviewer와 Verifier · DoD가 병렬로 판단 |
| C4 | 전체 AC 종료 → Verifier · AC 최종 판정 |
| C5 | `--check-ac` · `--check-dod` 모두 통과 시 `Done` + `--final-summary` (BL-009) |
| (점선) | 실행 중 새 마일스톤 · 백로그가 필요하면 Phase B 재진입 — 실행 중 재백로깅이 일어나는 유일한 경로 |

AC(개별 완료 조건)와 DoD(공통 완료 기준)는 backlog.md가 `--check-ac` · `--check-dod`로 이미 제공하는 구분이다. Verifier의 두 갈래(DoD · AC)는 이 구분을 그대로 따른다.

### 태스크 하나 안의 순서

![태스크 하나 안에서 오가는 순서 — par 블록이 Reviewer와 Verifier · DoD의 동시 활성 구간](../diagrams/07-task-sequence.svg)

1. 보드 → Implementer: 태스크 Ready, 동적 생성.
2. AC마다 반복:
   1. Implementer가 구현하고 claude-code-agile-hooks 테스트 게이트를 통과해 커밋한다.
   2. 병렬(par): Reviewer가 AC 완료 알림을 받아 판단하고 자기 디렉토리 WAL에 남긴다 / Verifier · DoD가 같은 커밋을 받아 테스트 · lint 결과를 WAL에 남긴다.
3. 전체 AC + Reviewer 사이클 종료 → Verifier · AC가 최종 판정하고 WAL에 남긴 뒤 보드에 AC · DoD 판정을 알린다.
4. Implementer가 `-s Done`과 final summary를 쓴다.
5. Logger가 통합 기록(recap + 토큰 합계)을 남긴다.

### AC 커밋 순간에 맞물리는 것

Implementer가 AC 하나를 커밋하는 한 순간에 다음이 동시에 작동한다.

| 번호 | 컴포넌트 | 하는 일 | 성격 |
| --- | --- | --- | --- |
| ① | claude-code-agile-hooks | 테스트 게이트 · 절차를 강제한다. Implementer가 유일한 writer라는 권한 구분은 선언이 아니라 이 훅이 강제한다 (RAIL-005 · RAIL-010) | 제어 |
| ② | coding-agent-git-commit-tool | 그 커밋의 토큰 사용량을 측정해 트레일러로 남긴다. Logger는 이 값을 묻지 않고 커밋에서 읽는다 (TRL-004) | 계측 |
| ③ | Allocation Policy | Reviewer와 Verifier · DoD를 동시에 깨운다. Verifier · DoD가 Reviewer를 기다릴 이유가 없는데 기다리게 하면 워커풀의 빈 슬롯을 스스로 놀린다 (ORC-013) | 누가 언제 깨는지 |
| ④ | 프롬프트 캐싱 | 두 판정자는 새로 문서를 읽지 않고 부착 시 캐싱한 같은 조상 문서 프리픽스를 재사용한다 (NFR-007) | 왜 병렬이 저렴한지 |
| ⑤ | Logger | 전 과정을 관찰만 하며 WAL에 쌓는다 | 기록 |

## §5 에이전트 부착 지점

에이전트는 태스크에만 붙지 않는다. 마일스톤을 포함해 계층 어느 노드에도 붙고, 노드마다 붙는 개수도 4로 고정이 아니라 2~4개 등으로 달라진다. 어느 노드에 몇 개, 어떤 역할을, 언제 붙일지는 Allocation Policy가 정한다 (ORC-009).

![에이전트 부착 지점 — 예시이며 마일스톤 단위 에이전트의 검증 항목은 미정](../diagrams/08-agent-attach.svg)

- 마일스톤 노드 에이전트는 매니저가 아니라 집계자다. 자식 태스크에 작업을 배분하지 않고, 이미 Done인 자식의 산출물을 읽어 통합 검증 · 기록만 한다 (ORC-020). 그래서 계층-위임(매니저) 오버헤드에 대한 경계가 이 노드에는 적용되지 않는다.
- 마일스톤 노드 에이전트가 정확히 무엇을 집계 · 검증하는지는 `TBD(Q-7)`이다.

## §6 부착 시 컨텍스트 로딩 · 회수 시 컨텍스트 폐기

### 부착

- 각 에이전트는 역할과 무관하게 태스크 문서 하나가 아니라 상위 마일스톤(들)을 거쳐 프로젝트 루트까지 이어지는 조상 문서를 모두 읽고 시작한다 — 계층 트리를 아래에서 위로 훑는 것과 같다 (ORC-019).
- 조상 문서 프리픽스는 프롬프트 캐싱 대상이므로 타임스탬프 · 세션 ID 같은 가변값을 섞지 않는다 (NFR-007).
- 프롬프트는 `-p` 인자 하나로 넘기고 stdin을 닫아 띄운다. bare 모드는 쓰지 않는다 (ORC-001 · ORC-002).
- Reviewer · Logger가 Implementer의 요약 + diff만 읽는 비대칭 로딩은 `TBD(Q-2)`이다.

### 회수

에이전트는 `claude -p` 헤드리스 프로세스라 세션 컨텍스트는 프로세스가 살아 있는 동안만 있다. 대화형 `/clear`를 보낼 단계는 없고, 프로세스 종료가 곧 컨텍스트 폐기다 (1.02 P3). 회수는 한 호출로 다음을 한다 (ORC-003 · ORC-004).

1. 프로세스가 살아 있으면 자손 목록을 먼저 확보한다.
2. SIGTERM → 유예(`TBD(Q-16)`) → SIGKILL로 프로세스와 자손을 끝낸다. 타임아웃이 나도 자손까지 끝낸다.
3. Session Registry에서 제거한다.
4. 제거에 성공한 경우에만 Semaphore 허가를 반납한다 — 여러 번 불러도 허가가 이중 반납되지 않고, 스폰이 실패해 붙은 프로세스가 없어도 허가가 새지 않는다.

- 다음 태스크에 붙는 에이전트는 이전 태스크의 대화 이력을 이어받지 않고 조상 문서 재로딩으로만 컨텍스트를 만든다. Logger의 WAL 기록이 그 컨텍스트를 잃지 않게 하는 유일한 지속 장치다.
- 한계: 자손은 부모가 살아 있을 때만 찾을 수 있다. 에이전트가 정상 종료하며 백그라운드 자손을 남기면 그 자손은 최상위 프로세스로 재부모화되어 회수 시점에 보이지 않는다 (`TBD(Q-17)`).

## §7 완료 시점의 기록

태스크를 `Done`으로 옮기는 시점(`backlog task edit <ID> -s Done --final-summary …`)에 그 태스크 브랜치의 커밋을 읽어 요약을 카드에 기록한다 (ORC-021). 커밋이 함수 단위이므로 함수별 작업 내역과 토큰 집계가 이때 카드 안으로 들어온다.

- 그래서 이력을 나중에 어떻게 정리하든 기록은 남는다. 커밋을 합치면 `git log`에서는 함수별 흔적이 사라지지만, 내용은 카드(와 카드를 담은 커밋)에 적혀 있다.
- 따라서 완료 브랜치의 스쿼시 여부는 기록 보존이 아니라 이력 가독성의 문제다 (3.05 ADR-013, `TBD(Q-4)`).
