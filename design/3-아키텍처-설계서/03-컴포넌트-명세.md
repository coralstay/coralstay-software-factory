# 3.03 컴포넌트 명세

컴포넌트는 넷이다 — 실행 기반 agent-orchestrator, 규율 claude-code-agile-hooks, 포맷 coding-agent-git-commit-tool, 상태 backlog.md. 앞의 셋은 coralstay 저장소이고, backlog.md는 외부 오픈소스 CLI를 그대로 쓴다. 계측(토큰 계량)은 별도의 토큰 계량 컴포넌트(이름 미정)가 맡고, 이름 · 저장소 · 측정 방식이 정해지면 명세를 더한다 (3.05 ADR-021).

"언제 · 얼마나 · 어떤 역할을 · 어떤 모델로" 스폰할지를 내부에 고정하지 않고, 교체 가능한 정책으로 외부에서 주입한다.

- 아키텍처의 계층 1 "할당자"는 단일 클래스가 아니라 위 컴포넌트들로 나뉜다. 계층 2~4(내장 DB · 정적 분석 · 대시보드)의 자리는 3.01 디렉토리 구조에 있다.
- 동시성 모델은 virtual thread + Semaphore다. 동시성은 한 자릿수~십수 개의 OS 서브프로세스 규모라 동시성 모델이 성능을 좌우하지 않고, virtual thread의 실익은 `Process.waitFor()`를 블로킹으로 써도 되는 코드 단순성이다 (3.05 ADR-002).
- 정책 주입은 `AllocationPolicy` 인터페이스 하나이고, 정책 자체는 자바 클래스로 쓴다. `-Dpolicy.class=`로 지정한 클래스나 `ServiceLoader`로 찾은 별도 jar의 구현을 쓰고, 정책이 지정되지 않았거나 로딩에 실패하면 에러를 내고 실행하지 않는다 — 기본 구현 폴백은 없다 (3.05 ADR-003).
- 다중 프로바이더 통합에 별도 라이브러리가 필요한지는 `TBD(Q-8)`이다 — Spawner가 프로세스만 띄운다면 JVM이 LLM API를 직접 부를 이유가 없다.

### 주의점

- backlog.md의 `isReady`는 "할당해도 된다"가 아니다. 이미 착수한 태스크도 참이고, 상태 전환 커밋이 `task/<ID>` 브랜치에만 있어 main에서는 `To Do`로 보인다. 그래서 `status = To Do`와 함께 main에 병합되지 않은 `task/<ID>` 브랜치(로컬 · 원격)가 없는지를 건다. 작업 순서 파일(`backlog/work-order.md`)은 읽지 않는다 — 훅 없이도 쓸 수 있어야 하고 의존 순서는 `isReady`가 보장한다 (ORC-005, decision-3).
- `WorktreeManager`는 `task/<ID>` 브랜치를 자바 프로세스에서 `git worktree add`로 직접 만들므로 훅의 착수 검사(§2)를 거치지 않는다. 그 워크트리 안의 에이전트 세션이 하는 `-s "In Progress"`가 에이전트 태스크의 착수 검사 지점이다. 오케스트레이터는 훅을 모르므로 이 전환이 거부되면 사유를 해석하지 않고 일반 '착수 안 됨' 실패로 거둔다 (RAIL-020, decision-3).
- readiness는 `--plain`에 없고 `--json`(`schemaVersion: 1`)에만 있다. 기계 판독은 `--json`으로 한다 (BL-002).
- 브랜치가 반영됐는지를 `git branch --no-merged`로 판단하면 오탐이 난다 — 패치가 이미 들어간 브랜치도 잡힌다. 반영 여부는 `git cherry` 기준으로 본다. 착수 판정(ORC-005)도 같은 기준이다.
- 병합 뒤 `task/<ID>` 브랜치를 지우는 것이 규칙이다(GitHub 저장소 설정 'Automatically delete head branches' + 로컬 `git fetch --prune` · 로컬 브랜치 삭제). 커밋이 여러 개인 브랜치를 squash 병합하면 패치 ID가 달라 `git cherry`가 계속 미병합으로 보기 때문이다. 판정은 `git cherry` 그대로 두고, 이 규칙을 지키면 병합 방식은 무엇이든 된다. 한계: squash 병합하고 지우지 않은 브랜치는 지울 때까지 착수로 보여 배정이 막힌다 (decision-3, agent-orchestrator decision-14).
- 오케스트레이터가 직접 만드는 커밋(지금은 실제치 기록 커밋, ORC-021)은 `AI_AGENT` · `CLAUDE_CODE_SESSION_ID` · `CLAUDE_PID`를 지운 환경에서 실행한다. 지우지 않으면 coding-agent-git-commit-tool(GF-130 뒤에는 `CLAUDE_CODE_SESSION_ID` · `CLAUDE_PID`로 에이전트를 판정)이 그 커밋을 부모 Claude 세션의 커밋으로 보고 트랜스크립트를 찾지 못한다(transcript-not-found). 그래서 지금은 사람 커밋으로 보인다. '프로그램 커밋'이라는 셋째 구분은 coding-agent-git-commit-tool GF-130 때 설계한다 (§3 주의점).
- 자손 프로세스는 부모가 살아 있을 때만 찾을 수 있다. 정상 종료한 에이전트가 남긴 백그라운드 자손은 회수 시점에 보이지 않는다 (`TBD(Q-17)`).

### 세 가지 성격

| 성격 | 하는 일 | 요구사항 |
| --- | --- | --- |
| ① 절차 강제 | 애자일 작업 절차 — 백로그 승인(draft 경유), 구현 계획(SOAP + AC + DoD) 없는 승격 · 착수 차단, 계획 → 리뷰 → 계획 승인(사람 서명자의 `Plan-Approved` 커밋), 단계별 커밋, 앞으로 할 일이 생길 때마다 작업 순서 재계산, 태스크 착수(task view 필독 · `task/<ID>` 브랜치 생성 · 전환과 In Progress 전환 두 시점의 착수 검사 — 계획 · AC · DoD, 승인 게이트, 작업 순서), 티켓 브랜치(`task/<ID>`, 커밋 메시지의 태스크 ID), 테스트 먼저(AC 단위 RGR + 비즈니스 규칙), 테스트 파일 구조(요약 → AC/DoD → Coverage), 커밋 전 테스트, 미커밋 턴 종료 차단, Definition of Done(Done + final summary 없이는 push 차단), 최상위 → 컴포넌트 설계 문서 전파 | RAIL-001 ~ RAIL-009 · RAIL-011 · RAIL-012 · RAIL-019 ~ RAIL-025 |
| ② 품질 · 안전 게이트 | 커버리지 100% + 리포트, 커버리지 · 테스트 무력화 방지, 시크릿 · 위험 명령 · 설정 변조 차단 | RAIL-006 · RAIL-013, NFR-017 |
| ③ 기록 · 관측 | 세션 로그, 스탠드업 · 회고 자료, 기술 부채의 자동 기록 | RAIL-014 |

- 성격 ①의 테스트 먼저(AC 단위 TDD + 비즈니스 규칙)도 훅이 강제한다 — 소스 편집 전에 다음 AC와 그 규칙들의 테스트 표식이, `Done` 전에 카드의 모든 표식이 테스트 파일에 있어야 한다 (RAIL-019, 3.05 ADR-020).
- 구현 계획은 SOAP 예약 제목 네 개로 작성 여부를 판정하고, 착수 검사 두 시점 — `task/<태스크 ID>` 브랜치 생성 · 전환과 `-s "In Progress"` — 의 승인 게이트에서 계획 승인 커밋 `Plan-Approved: <태스크 ID>`의 서명자(`%GS`)가 `humanSigners`에 있는지 확인한다. `-s "In Progress"`는 착수 판단이 아니라 기록이지만, 오케스트레이터가 만든 브랜치(훅을 거치지 않는 `git worktree add`)는 여기서 처음 검사되므로 같은 검사를 다시 한다 (RAIL-020, 3.05 ADR-022, decision-3).
- 테스트 먼저 · Done 게이트는 텍스트 끝이 `(수동)`인 AC · DoD 항목의 표식을 요구하지 않는다. 비즈니스 규칙에는 예외가 없다 (RAIL-019 · RAIL-022).
- 단계별 커밋 · 테스트 파일 구조(`(수동)` AC · DoD 예외 포함) · 커버리지 100% · 커밋 메시지의 태스크 ID는 같은 결정에서 나온다 (RAIL-021 · RAIL-022 · RAIL-006 · RAIL-025, 3.05 ADR-023).
- 대상 프로젝트의 API 예외 처리 규약 PRG(NFR-018, 3.05 ADR-024)는 이 컴포넌트가 아직 강제하지 않는다. 강제 방법은 미정이다.
- 기계적으로 검증할 수 있는 규칙은 훅으로 막고, 사람의 판단이 필요한 세 지점(백로그 승인, 착수 전 계획 승인, push 전 코드 리뷰)만 사람에게 남긴다 (RAIL-009 · BL-017, 1.02 P6).
- 훅끼리 서로 import하지 않는다 — 코드 중복이 있어도 한 훅의 버그가 다른 훅에 번지지 않는다 (NFR-016).
- 4역할 구조에 맞게 역할을 인식해 분기해야 한다 — Implementer만 writer이고 나머지 역할의 쓰기를 막는다 (RAIL-010). 세션이 어느 역할인지 식별하는 방식은 `TBD(Q-5)`이다.

### 주의점

- `install.sh`는 `~/.claude/CLAUDE.md`에 마커 블록이 이미 있으면 갱신을 건너뛴다. 그래서 설치된 블록이 저장소의 `CLAUDE.md.snippet`보다 낡을 수 있다.
- 여러 독립 프로세스가 동시에 돌 때의 격리(훅 상태 파일 · 세션 구분)는 검증 근거가 약하다. 4역할 동시 실행 전에 확인한다 (`TBD(Q-5)`).
- 훅으로 아직 강제하지 못하는 것: 스코프 판단(AC 밖 작업, RAIL-012), AC 증거 검증, 사람이 훅 없이 터미널에서 만든 `task/<ID>` 브랜치의 승인 게이트(decision-3).

| 필요조건 | git, 훅이 실행되는 시점의 PATH에서 잡히는 `python3` |
| 테스트 | `python3 -m unittest discover -s tests -v` |
| 정적 검사 | `ruff`(확장자 없는 훅 파일 포함), `shellcheck -s sh install.sh` |
| 소비자 | agent-orchestrator의 `CommitLedger`가 트레일러를 읽는다 (ORC-021) |

### 다루는 범위

| 기둥 | 하는 일 |
| --- | --- |
| 형식 | 사람(또는 에이전트)이 쓰는 제목 · 본문을 정해진 양식으로 검사한다 (TRL-001 · TRL-002) |
| 출처 기록 | 누가 · 어떤 도구와 모델로 · 무슨 태스크로 만들었는지 트레일러로 남긴다 (TRL-003 · TRL-006 · TRL-008) |
| 이력 불변 | 한 번 남긴 기록은 다시 쓰지 않는다(append-only). 로컬 훅은 `git push --no-verify`를 탐지하지 못하므로, main의 force push · 삭제 금지는 원격 저장소 설정이 맡는다 |

- 언어별 lint는 다루지 않는다 — 세 기둥 어디에도 속하지 않고, 사용자에게 언어 도구를 전제하게 만든다.
- 토큰은 재지 않는다. 커밋 훅이 토큰을 재면 깃 커밋과 측정이 강결합되므로 토큰 계량 컴포넌트(이름 미정)로 뺐다 (3.05 ADR-021, 측정 방식 `TBD(Q-18)`).

### 주의점

- 훅은 커밋 객체가 만들어지기 전에 돌고 실패하면 커밋을 막는다. `python3`가 PATH에 없으면 훅이 실행되지 못해 커밋이 막힌다 — 트레일러가 조용히 빠진 커밋은 생기지 않는다. GUI git 클라이언트는 셸 프로파일을 거치지 않아 이 경우가 흔하다.
- `git commit --no-verify`로도 `prepare-commit-msg`는 건너뛸 수 없다 — 검사와 트레일러 삽입이 모두 이 훅에 있으므로 커밋 단계의 우회는 없다. 로컬 훅이 탐지하지 못하는 것은 `git push --no-verify`다.
- 에디터가 `prepare-commit-msg`보다 뒤에 열리므로 최종 메시지 검증은 `git commit -m`(또는 `-F`)만 가능하고, 에디터 경로는 거부한다.
- 이 도구가 `core.hooksPath`를 점유하므로 대상 저장소의 `.git/hooks/*`는 무시된다.
- 에이전트 여부 판정이 환경변수 `AI_AGENT` 값의 첫 `_` 앞부분이 비어 있지 않은지만 본다. GF-130(구현 전)이 판정을 `CLAUDE_CODE_SESSION_ID` · `CLAUDE_PID`로 바꾼다 — 그 뒤에는 Claude 세션 아래에서 도는 프로그램의 커밋도 에이전트 커밋으로 잡히므로, 오케스트레이터는 세 변수를 지우고 커밋한다(§1 주의점). '프로그램 커밋' 구분은 GF-130 때 설계한다.
- 설정 키와 파일명(`gitformat.*` · `gitformat.conf`)은 기존 설치를 깨지 않도록 옛 이름을 쓴다.

## §4 backlog.md 사용 규약

| 항목 | 내용 |

| 출처 | 외부 오픈소스 CLI [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md). 신규 구현 없이 계층 · 상태 모델을 그대로 쓴다 |
| 실측 버전 | 1.51.0 |
| 구현하는 요구사항 | BL-001 ~ BL-017 |
| 저장 위치 | 대상 저장소의 `backlog/`(태스크 · draft · 결정 · 문서가 마크다운 파일) |

| 쓰임 | 명령 | 요구사항 |
| --- | --- | --- |
| 초기화 | `backlog init` | — |
| 브리핑 | `backlog overview` · `backlog board view` · `backlog search` | BL-011 |
| 백로깅 | `backlog draft create` · `draft edit` · `draft promote <ID>` | BL-011 · BL-012 |
| 구현 계획 | `backlog draft edit <ID> --plan` · `task edit <ID> --plan` — SOAP 예약 제목 네 개 (2.02 구현 계획 형식) | BL-015 · RAIL-020 |
| 연결 | `backlog task edit <ID> --add-ref decision-N` · `--doc <path\|url>` | BL-010 |
| 의존 | `backlog task edit <ID> --dep <task-id>` — 앞으로 할 일(draft · To Do)이 생기거나 다시 열리거나 의존이 바뀔 때마다 정리한다 | BL-003 · BL-004 · BL-016 |
| 착수 가능 목록 | `backlog task list --ready` — 의존이 모두 끝난 태스크만 | BL-016 |
| 작업 순서 | 의존을 정리할 때마다 앞으로 할 일(draft 포함)의 의존 그래프를 위상 정렬해 단계별 표 `backlog/work-order.md`를 다시 계산하고 바로 커밋한다(claude-code-agile-hooks의 `scripts/work_order.py`, draft 포함은 TASK-64에서 구현 예정). 훅이 `draft promote`와 착수 검사 두 시점(`task/<ID>` 브랜치 생성 · 전환, `-s "In Progress"`) 때 검사하고, 오케스트레이터는 읽지 않는다. backlog.md는 병렬 묶음을 바로 내지 않는다 | BL-016 · RAIL-023 |
| 계획 승인 | 사람이 자기 키로 서명한 빈 커밋 `Plan-Approved: <ID>` — backlog.md 명령이 아니라 git 커밋이다. 승인 게이트는 착수(브랜치 생성 · 전환)와 시작 기록(`-s "In Progress"`) 두 시점에 돈다 | BL-017 · RAIL-020 |
| 판독(사람) | `backlog task view <ID> --plain` — 제목 · 상태 · 마일스톤 · AC 체크 여부 · 의존 그래프(전이 의존까지 트리) | RAIL-003 |
| 판독(기계) | `backlog task view <ID> --json` — `dependencies` · `readiness{isReady, isBlocked, blockingDependencies, missingDependencies}` · `milestone` · `acceptanceCriteria` | BL-002 |
| 착수 | `git switch -c task/<ID>`(또는 `checkout -b` · `worktree add`) — backlog.md 명령이 아니다. 구현 계획 · AC · DoD와 계획 승인 커밋, 최신 작업 순서 파일이 있어야 한다(훅). 오케스트레이터의 `git worktree add`는 훅을 거치지 않는다 | RAIL-020 · RAIL-023 |
| 시작 기록 | `task/<ID>` 브랜치에서 `backlog task edit <ID> -s "In Progress"` — 착수 판단이 아니라 실제 시작 시각 기록. 훅이 착수와 같은 검사를 다시 한다(오케스트레이터 태스크의 검사 지점) | RAIL-004 · RAIL-020 · RAIL-023 |
| 완료 | `--check-ac` · `--check-dod` · `--final-summary` · `-s Done` | BL-009 |
| 보드 | `backlog browser` — 사람이 카드를 보는 화면 | — |
| 단계 커밋 | draft 작성 · 승격 · 작업 순서 · 시작 기록 · 완료마다 `git commit`. 다음 단계 명령 전에 `backlog/` 변경을 모두 커밋한다. push 없음 (2.02 전이와 커밋) | RAIL-002 · RAIL-021 |

- 상태 값은 `To Do` · `In Progress` · `Done` 셋만 쓰고 늘리지 않는다. 오케스트레이터에 필요한 세밀한 구분은 readiness와 오케스트레이터의 계산 레이어로 얻는다 (2.02, 3.05 ADR-006).
- `draft promote`는 다른 draft를 가리키는 의존(`DRAFT-n`)을 승격된 태스크 ID로 바꾸지 않는다. 승격 뒤 다시 설정한다 (BL-004).
- 마일스톤은 평평하고, 깊이는 `parentTaskId` 서브태스크로 판다 (BL-005).
- backlog.md 1.51.0의 `task list` · `task view` · `overview` · `search`와 `backlog browser`(웹 API)는 main에서 착수한 카드를 `To Do`로 보인다 — 상태 전환 커밋이 `task/<ID>` 브랜치에만 있기 때문이다. 로컬 브랜치만 있을 때도 원격 브랜치만 있을 때도 같다(4.02 실측 사실). backlog.md의 브랜치 스캔(`check_active_branches`)은 ID 발번에만 쓰인다. 사람은 `git branch -a --list '*task/*'`와 병합 여부(§1 주의점)로 착수한 태스크를 확인한다 (2.02 상태와 전이). 병합 뒤 지우지 않은 squash 브랜치도 이 목록에 착수로 남는다(§1 주의점의 브랜치 삭제 규칙).
