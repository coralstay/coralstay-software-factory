# 3.03 컴포넌트 명세

컴포넌트는 넷이다 — 실행 기반 agent-orchestrator, 규율 claude-code-agile-hooks, 계측 coding-agent-git-commit-tool, 상태 backlog.md. 앞의 셋은 coralstay 저장소이고, backlog.md는 외부 오픈소스 CLI를 그대로 쓴다.

## §1 agent-orchestrator

| 항목 | 내용 |
| --- | --- |
| 저장소 | [coralstay/agent-orchestrator](https://github.com/coralstay/agent-orchestrator) |
| 역할 | JVM 오케스트레이터 — 태스크 판독 · 스케줄 · 워크트리 · 스폰 · 회수 · 기록 |
| 구현하는 요구사항 | ORC-001 ~ ORC-031, NFR-001 ~ NFR-004, NFR-006 ~ NFR-015 |
| 언어 · 빌드 | Java 25, Gradle, 외부 런타임 의존성 없음 |
| 진입점 | `orchestrator run <taskId>` — 태스크 하나를 단발 실행한다 (ORC-024) |
| 테스트 | `./gradlew test`. 아직 구현이 없는 `@Tag("pending")` 테스트는 `test`에서 빠지고 `./gradlew pendingTest`로 따로 돈다 |
| 커밋 게이트 | 저장소의 claude-code-agile-hooks 설정 `testCommand: ./gradlew test` |

### 구성

"언제 · 얼마나 · 어떤 역할을 · 어떤 모델로" 스폰할지를 내부에 고정하지 않고, 교체 가능한 정책으로 외부에서 주입한다.

![오케스트레이터 구성 — Allocation Policy가 외부 주입 지점이다](../diagrams/09-orchestrator.svg)

| 컴포넌트 | 책임 | 패키지 · 클래스 | 요구사항 |
| --- | --- | --- | --- |
| Board Watcher | backlog 상태 변화 감지 → Ready 집합 | `backlog/` `BacklogClient`(판독 · 스폰 가능 판정). 감시 루프 방식 `TBD(Q-10)` | ORC-005 · ORC-025 |
| Request Queue | 순차 체인은 선행 순서대로, 독립 노드는 함께 admit | — | ORC-006 · ORC-007 |
| Dispatcher | 용량 제한 워커풀. 평상시엔 즉시 디스패치처럼, 트리거가 몰릴 때만 큐잉. 지연 민감 경로용 전용 슬롯 | — | ORC-008 · ORC-026 |
| Allocation Policy | 노드 + 현재 상태 → (역할, 개수, 시점, 모델 · 프로바이더). 외부 주입 지점 | — (3.04 §4) | ORC-009 ~ ORC-011 |
| Agent Spawner | 역할별 프로세스 기동 · 대기. 기본은 Claude Code CLI, 역할 하나를 다른 프로바이더 CLI로 교체 가능 | `spawn/` `AgentSpawner` | ORC-001 · ORC-002 · ORC-023 |
| Session Registry | 생존 에이전트 추적 · 회수 | `registry/` `SessionRegistry` | ORC-003 · ORC-004 |
| 워크트리 격리 | 태스크별 `../<repo>-wt/<id>` 워크트리 · `task/<id>` 브랜치 | `workspace/` `WorktreeManager` | ORC-012 |
| 커밋 원장 | 태스크 브랜치의 커밋 트레일러 판독 → Done 시점 카드 기록 | `ledger/` `CommitLedger` | ORC-021 |
| 실행 흐름 | `run` 배선 + 실행 결과 기록 | `RunCommand` | ORC-022 · ORC-024 |

- 아키텍처의 계층 1 "할당자"는 단일 클래스가 아니라 위 컴포넌트들로 나뉜다. 계층 2~4(내장 DB · 정적 분석 · 대시보드)의 자리는 3.01 디렉토리 구조에 있다.
- 동시성 모델은 virtual thread + Semaphore다. 동시성은 한 자릿수~십수 개의 OS 서브프로세스 규모라 동시성 모델이 성능을 좌우하지 않고, virtual thread의 실익은 `Process.waitFor()`를 블로킹으로 써도 되는 코드 단순성이다 (3.05 ADR-002).
- 정책 주입은 `AllocationPolicy` 인터페이스 하나 + YAML 기본 구현 + `-Dpolicy.class=` 교체다. 나중에 SPI로 바꿔도 호출부는 바뀌지 않는다 (3.05 ADR-003).
- 다중 프로바이더 통합에 별도 라이브러리가 필요한지는 `TBD(Q-8)`이다 — Spawner가 프로세스만 띄운다면 JVM이 LLM API를 직접 부를 이유가 없다.

### 주의점

- backlog.md의 `isReady`는 "할당해도 된다"가 아니다. 사람이 선점한 `In Progress`도 참이므로 `status = To Do`를 함께 건다 (ORC-005).
- readiness는 `--plain`에 없고 `--json`(`schemaVersion: 1`)에만 있다. 기계 판독은 `--json`으로 한다 (BL-002).
- 브랜치가 반영됐는지를 `git branch --no-merged`로 판단하면 오탐이 난다 — 패치가 이미 들어간 브랜치도 잡힌다. 반영 여부는 `git cherry` 기준으로 본다.
- 자손 프로세스는 부모가 살아 있을 때만 찾을 수 있다. 정상 종료한 에이전트가 남긴 백그라운드 자손은 회수 시점에 보이지 않는다 (`TBD(Q-17)`).

## §2 claude-code-agile-hooks

| 항목 | 내용 |
| --- | --- |
| 저장소 | [coralstay/claude-code-agile-hooks](https://github.com/coralstay/claude-code-agile-hooks) |
| 역할 | 규율 레이어 — Claude Code 작업에 애자일(스크럼 · 칸반) 절차와 품질 · 안전 게이트를 거는 훅 모음 |
| 구현하는 요구사항 | RAIL-001 ~ RAIL-014, NFR-016 |
| 구성 | Claude Code [hooks](https://code.claude.com/docs/ko/hooks) 이벤트(`PreToolUse` · `Stop` 등)마다 도는 Python 스크립트. Backlog.md 워크플로 전용 훅과 프로젝트 종류와 무관한 범용 안전 · 관측 훅으로 나뉜다 |
| 설치 | `install.sh` → `~/.claude/hooks/claude-code-agile-hooks/*.py` + `~/.claude/settings.json` 등록 + `~/.claude/CLAUDE.md` 마커 블록(`CLAUDE.md.snippet`) |
| 프로젝트 설정 | `.claude-code-agile-hooks.json`의 `testCommand` · `coverageCommand`. 옛 이름 `.claude-rails.json`도 읽는다 (3.04 §7) |
| 테스트 | `uvx --with pytest-cov --with pytest-xdist pytest -q -n auto --cov` (순차: `uvx --with pytest-cov pytest -q --cov`). `hooks/` · `scripts/`의 줄 · 분기 커버리지가 100% 미만이면 실패한다 |
| 계약 테스트 | `test_hook_registration_contract.py` — `if` 필터가 검사할 명령을 가리지 않는지. `test_hook_runtime_contract.py` — 등록된 모든 훅을 실제 subprocess로 돌려 빈 입력 · 깨진 JSON · 정상 입력에서 정해진 종료 코드를 내는지(`HOME`을 임시 디렉토리로 바꿔 실행) |
| CI | `main` push와 모든 PR에서 ubuntu · macOS × Python 3.11 · 3.12로 병렬 테스트 + 커버리지 100% |

### 세 가지 성격

| 성격 | 하는 일 | 요구사항 |
| --- | --- | --- |
| ① 절차 강제 | 애자일 작업 절차 — 백로그 승인(draft 경유), 태스크 착수(task view 필독 · In Progress), 티켓 브랜치(`task/<ID>`), 커밋 전 테스트, 미커밋 턴 종료 차단, Definition of Done(Done + final summary 없이는 push 차단) | RAIL-001 ~ RAIL-009 · RAIL-011 · RAIL-012 |
| ② 품질 · 안전 게이트 | 커버리지 · 테스트 무력화 방지, 시크릿 · 위험 명령 · 설정 변조 차단 | RAIL-006 · RAIL-013 |
| ③ 기록 · 관측 | 세션 로그, 스탠드업 · 회고 자료, 기술 부채의 자동 기록 | RAIL-014 |

- 기계적으로 검증할 수 있는 규칙은 훅으로 막고, 사람의 판단이 필요한 두 지점(백로그 승인, push 전 코드 리뷰)만 사람에게 남긴다 (RAIL-009, 1.02 P6).
- 훅끼리 서로 import하지 않는다 — 코드 중복이 있어도 한 훅의 버그가 다른 훅에 번지지 않는다 (NFR-016).
- 4역할 구조에 맞게 역할을 인식해 분기해야 한다 — Implementer만 writer이고 나머지 역할의 쓰기를 막는다 (RAIL-010). 세션이 어느 역할인지 식별하는 방식은 `TBD(Q-5)`이다.

### 주의점

- `install.sh`는 `~/.claude/CLAUDE.md`에 마커 블록이 이미 있으면 갱신을 건너뛴다. 그래서 설치된 블록이 저장소의 `CLAUDE.md.snippet`보다 낡을 수 있다.
- 여러 독립 프로세스가 동시에 돌 때의 격리(훅 상태 파일 · 세션 구분)는 검증 근거가 약하다. 4역할 동시 실행 전에 확인한다 (`TBD(Q-5)`).
- 훅으로 아직 강제하지 못하는 것: 스코프 판단(AC 밖 작업, RAIL-012), AC 증거 검증.

## §3 coding-agent-git-commit-tool

| 항목 | 내용 |
| --- | --- |
| 저장소 | [coralstay/coding-agent-git-commit-tool](https://github.com/coralstay/coding-agent-git-commit-tool) |
| 역할 | 계측 레이어 — 커밋 메시지 형식 검사 + `Task-Id` · `AI-Model` · `Tokens-Used` · `Tool-Calls` 등 트레일러 자동 부착. "커밋 = 함수, 커밋당 토큰 계량"을 실제로 만든다 |
| 구현하는 요구사항 | TRL-001 ~ TRL-009, NFR-004 · NFR-005 |
| 구성 | Python 3 표준 라이브러리 훅(`hooks/prepare-commit-msg` · `commit-msg` · `post-commit`) + 설정 파일(`hooks/gitformat.conf`) + POSIX sh 설치 스크립트(`install.sh`). `core.hooksPath` · `init.templateDir` · `git interpret-trailers` 같은 git 내장 메커니즘만 쓴다 |
| 필요조건 | git, 훅이 실행되는 시점의 PATH에서 잡히는 `python3` |
| 테스트 | `python3 -m unittest discover -s tests -v` |
| 정적 검사 | `ruff`(확장자 없는 훅 파일 포함), `shellcheck -s sh install.sh` |
| 소비자 | agent-orchestrator의 `CommitLedger`가 트레일러를 읽는다 (ORC-021) |

### 다루는 범위

| 기둥 | 하는 일 |
| --- | --- |
| 형식 | 사람(또는 에이전트)이 쓰는 제목 · 본문을 정해진 양식으로 검사한다 (TRL-001 · TRL-002) |
| 출처 기록 | 누가 · 어떤 도구와 모델로 · 무슨 태스크로 · 얼마를 들여 만들었는지 트레일러로 남긴다 (TRL-003 ~ TRL-008) |
| 이력 불변 | 한 번 남긴 기록은 다시 쓰지 않는다(append-only). 로컬 훅은 `--no-verify`를 막지 못하므로, main의 force push · 삭제 금지는 원격 저장소 설정이 맡는다 |

- 언어별 lint는 다루지 않는다 — 세 기둥 어디에도 속하지 않고, 사용자에게 언어 도구를 전제하게 만든다.
- 토큰 수는 모델이 아니라 API가 응답마다 실어 주는 메타데이터다. 그래서 Logger가 다른 역할에게 "얼마나 썼어?"라고 묻는 설계는 성립하지 않고, 측정은 세션 트랜스크립트(`~/.claude/projects/<slug>/<session-id>.jsonl`)의 assistant `message.usage`를 합산하고 `tool_use` 블록을 센다 (TRL-004).
- 측정값은 "그 커밋에 정확히 필요했던 토큰"이 아니라 근사치다. 측정 방식은 채택하되 정확도는 확정하지 않는다 (3.05 ADR-011).

### 주의점

- `post-commit`은 커밋이 이미 만들어진 뒤에 돌아서 커밋을 막지 못한다 — 검사가 아니라 기록만 한다. `python3`가 PATH에 없으면 커밋은 성공한 것처럼 보이지만 트레일러가 조용히 누락된다. GUI git 클라이언트는 셸 프로파일을 거치지 않아 이 경우가 흔하다.
- 에디터가 `prepare-commit-msg`보다 뒤에 열리므로 최종 메시지 검증은 `git commit -m`(또는 `-F`)만 가능하고, 에디터 경로는 거부한다.
- 이 도구가 `core.hooksPath`를 점유하므로 대상 저장소의 `.git/hooks/*`는 무시된다.
- 에이전트 여부 판정이 환경변수(`AI_AGENT`) 존재만 본다. `claude -p`로 여러 역할을 띄울 때 세션별 토큰 귀속이 맞는지는 근거가 없다 (`TBD(Q-18)`).
- 측정이 Claude Code 트랜스크립트 경로에 묶여 있다 — 다른 프로바이더 CLI로 띄운 역할(ORC-023)은 `unavailable`로 남는다.
- 설정 키와 파일명(`gitformat.*` · `gitformat.conf` · `.gitformat-*`)은 기존 설치를 깨지 않도록 옛 이름을 쓴다.

## §4 backlog.md 사용 규약

| 항목 | 내용 |
| --- | --- |
| 출처 | 외부 오픈소스 CLI [MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md). 신규 구현 없이 계층 · 상태 모델을 그대로 쓴다 |
| 실측 버전 | 1.51.0 |
| 구현하는 요구사항 | BL-001 ~ BL-013 |
| 저장 위치 | 대상 저장소의 `backlog/`(태스크 · draft · 결정 · 문서가 마크다운 파일) |

| 쓰임 | 명령 | 요구사항 |
| --- | --- | --- |
| 초기화 | `backlog init` | — |
| 브리핑 | `backlog overview` · `backlog board view` · `backlog search` | BL-011 |
| 백로깅 | `backlog draft create` · `draft edit` · `draft promote <ID>` | BL-011 · BL-012 |
| 연결 | `backlog task edit <ID> --add-ref decision-N` · `--doc <path\|url>` | BL-010 |
| 의존 | `backlog task edit <ID> --dep <task-id>` | BL-003 · BL-004 |
| 판독(사람) | `backlog task view <ID> --plain` — 제목 · 상태 · 마일스톤 · AC 체크 여부 · 의존 그래프(전이 의존까지 트리) | RAIL-003 |
| 판독(기계) | `backlog task view <ID> --json` — `dependencies` · `readiness{isReady, isBlocked, blockingDependencies, missingDependencies}` · `milestone` · `acceptanceCriteria` | BL-002 |
| 착수 | `backlog task edit <ID> -s "In Progress"` | RAIL-004 |
| 완료 | `--check-ac` · `--check-dod` · `--final-summary` · `-s Done` | BL-009 |
| 보드 | `backlog browser` — 사람이 카드를 보는 화면 | — |

- 상태 값은 `To Do` · `In Progress` · `Done` 셋만 쓰고 늘리지 않는다. 오케스트레이터에 필요한 세밀한 구분은 readiness와 오케스트레이터의 계산 레이어로 얻는다 (2.02, 3.05 ADR-006).
- `draft promote`는 다른 draft를 가리키는 의존(`DRAFT-n`)을 승격된 태스크 ID로 바꾸지 않는다. 승격 뒤 다시 설정한다 (BL-004).
- 마일스톤은 평평하고, 깊이는 `parentTaskId` 서브태스크로 판다 (BL-005).
