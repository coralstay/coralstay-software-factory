## 요약 (v3 기준, 자기 말로)

- **무엇을 비교했나.** 단일 에이전트(SAS)와 다중 에이전트 4종을 같은 계산 예산으로 맞춰 비교했다. 다중 에이전트 4종은 다음과 같다(§3, Table 2).
  - Independent: 에이전트끼리 대화하지 않고 결과만 모은다
  - Centralized: 오케스트레이터가 하위 에이전트에만 지시한다
  - Decentralized: 모든 에이전트가 서로 토론한다
  - Hybrid: 오케스트레이터에 제한된 동료 간 대화를 더한다
- **어디서 쟀나.** 벤치마크 6개다: 웹 탐색 BrowseComp-Plus, 재무 분석 Finance-Agent, 게임 계획 PlanCraft, 업무 도구 Workbench, 소프트웨어 공학 SWE-bench Verified, 터미널 작업 Terminal-Bench.
  - 모델 계열은 3개(OpenAI · Google · Anthropic)이고 총 260개 구성이다(§1, §3).
  - SWE-bench Verified와 Terminal-Bench는 Docker 평가 비용 때문에 20문항 부분집합만 썼다(§3).
- **결과 폭.** 단일 대비 상대 성능이 +80.8%(분해 가능한 재무 추론, Centralized)부터 −70.0%(순차 계획, Independent)까지 갈린다(초록, §1). 다중 에이전트가 낫냐 못하냐는 작업 구조와 조율 구조가 맞느냐에 달렸다는 것이 핵심 주장이다.
- **오류 증폭.** 독립형은 개별 오류가 최종 출력까지 그대로 번져 오류를 17.2배 키우고, 중앙형은 오케스트레이터가 집계 전에 오류를 걸러 4.4배로 줄인다(§1). 논문은 중앙형 오케스트레이터를 "validation bottleneck"이라 부른다(§1).
- **역량 포화.** 단일 에이전트가 이미 약 45% 넘게 맞히는 작업에서는 에이전트를 더해도 손해다(§1, 회귀계수 β=−0.236, p=0.004).
- **소프트웨어 공학 결과(이 설계에 가장 가까움).** SWE-bench Verified에서 다중 에이전트 4종 모두 단일(평균 0.522)보다 낮았다(§4.2).
  - Hybrid −2.1%
  - Centralized −3.1%
  - Decentralized −5.4%
  - Independent −14.9%

  논문은 이를 역량 포화로 설명한다. 대부분의 모델이 단일 기준선 45%를 넘기 때문이다.
- **예측 모델.** 모델 역량, 에이전트 수, 도구 수, 단일 기준선, 측정한 조율 지표(효율 · 오버헤드 · 오류 증폭 · 메시지 밀도 · 중복)로 성공률을 회귀한다(§4.3, Table 5).
  - 교차검증 R²는 0.373(Intelligence Index) · 0.413(ACI)이다(§4.3).
  - held-out 구성의 87%에서 최선의 구조를 골랐다(초록).
- **한계(Limitations 절).** 에이전트 수는 9까지만 예비 탐색했다. 통신 오버헤드는 에이전트 수에 따라 초선형으로 늘어난다. 같은 기반 구조의 모델끼리만 섞어 봤다.

## 재는 것과 닿는 범위 (인용 원칙 3 · 4)

- **종속변수는 과제 성공률(벤치마크 정확도)이다.** 판정의 독립성, 리뷰 품질, 회귀 리스크를 재지 않는다. 그래서 **G-1(독립 판정)의 근거로는 쓰지 않는다.**
- **조율 구조는 같은 작업 안에서 에이전트들이 하나의 답을 함께 만드는 구조다.** 이 설계의 4역할(Implementer · Reviewer · Verifier · Logger)은 순서가 정해진 파이프라인이고, 판정자가 구현 컨텍스트를 물려받지 않게 하는 것이 목적이다. 구조가 다르므로 논문의 수치를 4역할 구조에 그대로 옮기지 않는다.
- **닿는 곳은 "에이전트를 몇 개, 어떤 구조로 붙이느냐"다.** 다음 질문에는 범위를 붙여 참고로 쓴다.
  - G-6 Allocation Policy, 1.01 "얼마나"(동시성 상한), R-6(동시 에이전트 수)
  - 하나의 태스크를 여러 에이전트에 나눌지, 독립 태스크를 병렬로 돌릴지
- 소프트웨어 공학 수치(§4.2)는 20문항 부분집합이라 신뢰구간이 넓다. 방향(다중화가 이득이 아니다)만 쓰고 크기는 쓰지 않는다.

## 이 설계와의 연결

| 대상 | 연결 | 쓰는 방식 |
| --- | --- | --- |
| G-6 Allocation Policy (1.03) | 몇 개를 붙일지는 작업 구조(분해 가능 vs 순차)와 단일 기준선으로 갈린다는 결과 | 정책 입력 후보: 태스크의 분해 가능성, 단일 실행 성공률. 근거가 아니라 설계 질문의 출발점 |
| R-6 병렬 충돌 (1.04) | "동시 에이전트 수를 무한정 늘리지 않는다 … 에이전트 적용은 미검증"에 대해, 과제 성능 기준으로는 순차 작업에서 다중화가 손해이고 통신 오버헤드가 초선형으로 는다는 실측 | 범위(과제 성공률 · 같은 작업 안의 조율)를 붙여 각주로만 단다 |
| 1.01 "얼마나" | 동시성 상한을 정할 때 그래프 폭 · 자원 실측과 함께 볼 지표 | 열린 질문으로 둔다 |
| 오케스트레이터 중앙형 | 독립형보다 중앙형이 오류 증폭을 억제한다(§1) | 오케스트레이터가 판정을 쥐는 구조(agent-orchestrator decision-7: 판정은 브랜치 상태)와 같은 방향. 근거가 아니라 일관성 확인 |
| agent-orchestrator AO-33 | 태스크 하나 = 에이전트 하나, 판정은 오케스트레이터 | SWE-bench 결과(§4.2)와 같은 방향. 병렬화는 한 태스크를 쪼개는 쪽이 아니라 서로 독립인 태스크 사이(SessionRegistry 동시 실행 수)에서 한다 |
| G-1 독립 판정 | — | **쓰지 않는다**(종속변수가 다르다) |

## 열린 질문

1. 태스크 카드에 "분해 가능성"이나 "단일 실행 성공률" 같은 속성을 둘 것인가? Allocation Policy의 입력이 될 수 있지만 지금 카드 형식에는 없다.
2. 역량 포화 임계(단일 약 45%)에 해당하는 값을 이 설계의 태스크에서 어떻게 잴 것인가? 오케스트레이터 실행 기록(`runs.jsonl`, AO-7)으로 태스크 유형별 단일 성공률을 모으면 출발점이 될 수 있다.
3. 4역할 파이프라인의 오류 증폭은 별도로 재야 한다. Reviewer · Verifier가 Implementer 오류를 걸러내는 비율이 논문의 "validation bottleneck"과 같은 효과를 내는지는 이 설계의 측정 과제다.
