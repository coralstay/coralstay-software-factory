## Q-1 Reviewer pass/fail · Verifier · AC 판정 기준

- **무엇이 미정인가** — Reviewer가 무엇을 pass/fail로 보는가, Verifier·AC가 AC 충족을 무엇으로 판정하는가. 출력 스키마 `{ac_id, verdict, evidence, blocking}`와 Verifier·DoD(결정적 검사)는 정해졌다.
- **왜 못 정하나** — 채점 기준은 개인 PKM 정리가 끝나야 쓸 수 있다. 추측으로 채우지 않는다. 이 공백이 남는 한 4역할 전체의 완료 기간은 추정할 수 없다(4.01 M4).
- **무엇이 정해주나** — PKM 정리 완료 후의 명세.

## Q-2 조상 문서 로딩의 비대칭화

- **무엇이 미정인가** — 모든 역할이 태스크 → 마일스톤 → 루트까지 조상 문서를 전부 읽는 대신, Reviewer · Logger가 Implementer의 요약 + diff만 읽게 할 것인가.
- **왜 못 정하나** — 고정비를 낮출 수 있지만, 요약을 거치면 판정 역할이 Implementer의 해석을 물려받을 수 있다(1.02 P1). 프리픽스 캐싱이 재로딩 비용을 얼마나 상쇄하는지 아직 모른다.
- **무엇이 정해주나** — 4.02 §실측 항목의 조상 문서 프리픽스 캐시 측정. 캐싱이 비용을 덮으면 대칭 로딩을 유지한다.

## Q-3 상태 개수와 전이 규칙

- **무엇이 미정인가** — 상태 전이 규칙의 최종형, 그리고 오케스트레이터가 backlog.md 위에 계산된(비저장) 상태 레이어를 따로 둘 것인가.
- **왜 못 정하나** — 저장 상태는 backlog.md의 세 값(To Do · In Progress · Done)을 유지하고, 세밀한 구분은 readiness(`isReady` · `isBlocked` · `blockingDependencies` · `missingDependencies`)로 얻는다는 방향은 정해졌다. 그 위에 추가 계산 레이어가 필요한지는 할당자를 만들어 봐야 안다.
- **무엇이 정해주나** — M4 할당 조건 구현과 backlog.md 필드 실측(4.02). backlog.md 자체의 저장 상태 어휘는 늘리지 않는다.
- **정해진 부분(2026-10-29)** — 착수는 상태 값이 아니라 main에 병합되지 않은 `task/<ID>` 브랜치로 판단하고, 할당 조건은 `isReady ∧ status = To Do ∧` 그 브랜치 없음이다 (2.02 상태와 전이, ORC-005, decision-3). backlog.md 1.51.0 화면이 main에서 착수를 보이지 않는 한계(3.03 §4 주의점)를 계산 레이어로 메울지는 이 항목에 남는다.

## Q-4 태스크 브랜치 스쿼시 vs 머지 커밋

- **무엇이 미정인가** — 완료한 태스크 브랜치를 스쿼시할 것인가, 머지 커밋으로 남길 것인가.
- **왜 못 정하나** — 최소 커밋 수는 카드의 AC 개수로 미리 세어진다(커밋 = 함수). 남은 미지수는 자가 치유 재시도 배수이고, 동시 실행 태스크 수만큼 곱해진다. 알려진 제약은 하나다 — 푸시해 공유한 커밋을 스쿼시하면 해시가 바뀌어 받아간 쪽이 갈라진다. 기록 손실은 고려 대상이 아니다. Done 전환 시 커밋을 읽어 태스크 카드에 기록하므로 이력을 합쳐도 내용은 남는다. 따라서 이 선택은 이력 가독성의 문제다.
- **무엇이 정해주나** — M1 walking skeleton이 남기는 재시도 분포.

## Q-5 세션-역할 식별의 세부 방식

- **무엇이 미정인가** — 역할마다 독립 프로세스라는 방향(1.02 P2) 아래에서, 프로세스가 자기 역할을 어떻게 식별되고 제한되는가 — worktree 분리, read-only 파일 권한 등 구체적 구현 방식.
- **왜 못 정하나** — 역할별 쓰기 권한(Implementer만 writer)은 정해졌지만, 그것을 강제할 수단의 비교가 없다.
- **무엇이 정해주나** — M4 Spawner와 M5 역할 인식 훅을 구현하며 격리 방식을 비교한 결과. 결정은 3.05에 남긴다.

## Q-6 Logger 정성적 기록의 구현 위치

- **무엇이 미정인가** — recap 같은 정성적 기록을 어디에, 어떤 형식으로 쓰는가.
- **왜 못 정하나** — Logger가 토큰 합계를 토큰 계량 컴포넌트(이름 미정)에서 받는다는 방향은 정해졌지만(측정 방식은 Q-18), 정성적 기록은 소비자(사람 · 마일스톤 집계자)가 정해지지 않았다.
- **무엇이 정해주나** — Logger 역할 명세와 Q-7의 집계 항목.

## Q-7 마일스톤 노드 에이전트의 집계 · 검증 항목

- **무엇이 미정인가** — 마일스톤(이상) 단위 에이전트가 정확히 무엇을 집계하고 검증하는가.
- **왜 못 정하나** — 매니저가 아니라 집계자라는 역할은 정해졌지만, 구체적 검증 항목은 예시뿐이다.
- **무엇이 정해주나** — 마일스톤 완료 조건 명세. 4.01의 마일스톤 완료 조건이 그 첫 사례다.

## Q-8 다중 LLM 프로바이더 통합 라이브러리의 필요 여부

- **무엇이 미정인가** — 여러 LLM 프로바이더를 쓰려면 별도 통합 라이브러리(예: aisuite)가 필요한가.
- **왜 못 정하나** — Agent Spawner가 프로세스만 스폰한다면 JVM이 LLM API를 직접 부를 이유가 없고, 각 프로바이더의 자체 CLI를 띄우면 된다. 그렇다면 이 항목은 사라지지만, 확인되지 않았다.
- **무엇이 정해주나** — Claude Code 외 코딩 에이전트 실행부(AgentRunner) 구현 시 프로세스 스폰만으로 충분한지 확인한 결과.

## Q-9 헤드리스 세션 간 메시징의 실환경 동작

- **무엇이 미정인가** — Spawner가 띄운 `claude -p` 헤드리스 프로세스가 세션 간 메시징의 inbox 소켓을 실제로 바인딩하는가.
- **왜 못 정하나** — 공식 문서는 헤드리스 세션도 inbox를 바인딩한다고 명시한다(bare 모드 제외). 실환경 확인만 남았다.
- **무엇이 정해주나** — M2 실측(4.02 §실측 항목). 동작하지 않으면 Logger의 WAL 디렉토리를 파일 메일박스로 쓰는 폴백으로 간다.

## Q-10 보드 상태 감지 방식

- **무엇이 미정인가** — Board Watcher가 보드 변화를 backlog CLI 폴링으로 감지할 것인가, 파일시스템 `WatchService`로 감지할 것인가.
- **왜 못 정하나** — 폴링은 CLI가 계산한 readiness를 그대로 쓰지만 지연이 있고, `WatchService`는 즉시 반응하지만 파일 변경을 다시 CLI 판독으로 해석해야 한다. 비교 근거가 없다.
- **무엇이 정해주나** — M4 Board Watcher 구현 시 두 방식의 지연 · 정확도 비교. 결정은 3.05에 남긴다.

## Q-11 측정으로 정하는 임계값

- **무엇이 미정인가** — 다음 값들.
  - 4역할을 붙이는 태스크의 경계선(1.03 적용 조건)
  - 1.02 반증 기준의 "유의미하게 낮춘다"의 기준
  - 병렬 구조 반증 조건의 "폭이 거의 항상 1~2"의 기준
  - Reviewer 최대 왕복 횟수와 판정 역할 재스폰 횟수 N
- **왜 못 정하나** — 임계값은 외부에서 빌려오지 않는다(1.02 P9). 외부 연구는 종속변수(과제 정확도)가 다르고, 배정 시점에는 태스크 난이도를 모른다.
- **무엇이 정해주나** — M1 · M3가 쌓는 태스크별 성공/실패 · 재작업 · 회귀 분포와 Logger의 스케줄 라운드 기록.

## Q-12 자원 상한 실측값 — `claude` 프로세스 peak RSS와 API 분당 한도

- **무엇이 미정인가** — 동시성 상한 `min(그래프 폭, 자원 상한)`의 자원 쪽 값. `claude` 프로세스 1개의 peak RSS와 API 플랜의 분당 요청 한도.
- **왜 못 정하나** — 벤치마크 값은 쓰지 않는다(1.02 P9). 이 호스트 · 이 플랜에서 재야 하는데 아직 동시 스폰을 돌린 적이 없다.
- **무엇이 정해주나** — M1 walking skeleton에서 프로세스 수를 늘려 가며 RSS와 429 응답을 기록한 실측.

## Q-13 태스크 카드에 대응 소스 파일을 적는 형식

- **무엇이 미정인가** — BL-006의 "태스크 = 파일 하나"를 카드에 어떤 필드 · 표기로 적을지.
- **왜 못 정하나** — backlog.md에 전용 필드가 없어 description · label · ref 중 무엇을 쓸지 정해지지 않았고, 오케스트레이터가 그 값을 어떻게 읽을지와 함께 정해야 한다.
- **무엇이 정해주나** — M4 결합 판정 구현에서 파싱하기 쉬운 쪽을 고른다.

## Q-14 `runs.jsonl` · 스케줄 라운드 기록 스키마, `ac_id` 표기, WAL 경로

- **무엇이 미정인가** — 실행 기록 한 줄의 필드, 스케줄 라운드 기록을 같은 파일에 둘지, Reviewer/Verifier WAL의 `ac_id` 표기와 디렉토리 경로.
- **왜 못 정하나** — 필드는 Logger가 무엇을 집계할지(4.02 반증 기준 측정)에 달려 있는데 그 집계가 아직 구현되지 않았다.
- **무엇이 정해주나** — M1에서 첫 기록을 남기고, 4.02 측정에 필요한 필드를 역산한다.

## Q-15 파일 · 모듈 결합도 측정 방식

- **무엇이 미정인가** — "같은 파일/모듈을 건드리는가"를 어떤 도구 · 단위로 판정할지.
- **왜 못 정하나** — 대상 프로젝트 언어마다 정적 분석 도구가 다르고, 카드의 대응 파일(Q-13)만으로 충분한지 아직 모른다.
- **무엇이 정해주나** — M4 스케줄러 구현에서 카드 파일 목록 기반 판정부터 시작해 놓친 충돌을 측정한다.

## Q-16 에이전트 프로세스 타임아웃과 SIGTERM → SIGKILL 유예 시간

- **무엇이 미정인가** — 역할 프로세스의 최대 실행 시간과 SIGTERM 뒤 SIGKILL까지 기다리는 시간.
- **왜 못 정하나** — `claude -p`가 SIGTERM에 얼마나 빨리 정리하고 끝나는지 측정한 적이 없다.
- **무엇이 정해주나** — M1 회수 경로 테스트에서 정상 · 강제 종료 소요 시간 분포를 잰다.

## Q-17 정상 종료 뒤 남은 고아 자손 프로세스 회수

- **무엇이 미정인가** — 에이전트가 정상 종료하며 백그라운드 자손을 남기면, 재부모화된 자손을 어떻게 찾아 끝낼지.
- **왜 못 정하나** — 자손 목록은 부모가 살아 있을 때만 얻을 수 있어 현재 회수 절차로는 보이지 않는다.
- **무엇이 정해주나** — M1에서 프로세스 그룹 · 세션 ID로 묶어 스폰하는 방식을 시험하고 남는 프로세스를 센다.

## Q-18 토큰 계량 컴포넌트(이름 미정)의 측정 방식과 역할 세션별 토큰 귀속의 정확도

- **무엇이 미정인가** — 토큰 계량을 coding-agent-git-commit-tool에서 떼어 낸 뒤(3.05 ADR-021), 그것을 맡을 컴포넌트의 이름 · 저장소 · 측정 방식, 측정값을 어디에 남기는지(커밋 · 카드 · `runs.jsonl`), 그리고 여러 역할을 별도 `claude -p`로 띄울 때 잰 토큰이 정확히 그 세션의 것인지.
- **왜 못 정하나** — 토큰 계량 컴포넌트가 아직 없다. 커밋 훅 방식(ADR-011, 폐기)은 동시 세션에서 트랜스크립트를 고르는 규칙을 검증한 적이 없고, 그 방식을 그대로 가져올지도 정하지 않았다.
- **무엇이 정해주나** — 토큰 계량 컴포넌트의 설계 결정(3.05에 남긴다)과, M2에서 역할 둘을 동시에 띄워 그 컴포넌트의 측정값과 각 트랜스크립트 합계를 대조한 결과.
- **정해진 부분(2026-10-29)** — 그 전까지 실행 한 번의 토큰은 `session`이다 — 헤드리스 `claude -p` JSON 출력의 `usage`(입력(캐시 포함) + 출력)를 오케스트레이터의 `ClaudeCodeRunner`가 읽는다 (3.05 ADR-021 예외, ORC-021). 이 항목에는 커밋 귀속분(`commits`)과 그것을 맡을 컴포넌트가 남는다.

## Q-19 AC 밖 작업 확인(RAIL-012)의 강제 수단

- **무엇이 미정인가** — "AC 밖 작업은 사람에게 먼저 확인"을 훅으로 강제할 방법.
- **왜 못 정하나** — AC와 변경의 대응을 기계적으로 판정할 기준이 없다(태스크 = 파일 규약 Q-13이 정해져야 판정 가능).
- **무엇이 정해주나** — Q-13이 정해진 뒤, 카드 밖 파일을 건드리는 편집을 막는 방식으로 시험한다.

## Q-20 Done 시점 완료 기록(함수별 작업 · 토큰 합계)의 형식

- **무엇이 미정인가** — ORC-021이 태스크 카드에 남기는 기록의 필드와 위치(final summary · 별도 절 · notes).
- **왜 못 정하나** — 커밋 트레일러 형식(TRL)은 정해졌지만 카드 쪽 표기 규약이 없고, 토큰 합계 중 커밋 귀속분의 출처인 토큰 계량 컴포넌트가 미정이다(Q-18).
- **무엇이 정해주나** — M2에서 첫 Done 기록을 남기고 사람이 읽기 쉬운 형식으로 고정한다.
- **정해진 부분(2026-10-29)** — 토큰 합계는 당분간 실행 단위 `session`만 기록한다(Q-18 정해진 부분). 커밋 귀속분과 카드 쪽 표기 형식은 미정이다.
