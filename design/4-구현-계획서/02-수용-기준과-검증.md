# 4.02 수용 기준과 검증

요구사항은 결정적 판정기(테스트 · Exit Code)로 통과를 판정하고, 설계의 전제는 실측과 반증 기준으로 판정하며, 인용은 원문 대조로 판정한다.

## 요구사항 ↔ 수용 기준

| 요구사항 ID | 수용 기준 | 검증 방법 | 판정 증거 |
| --- | --- | --- | --- |
| (2.03 · 2.04의 요구사항 ID마다 한 행) | 요구사항 ID가 확정되면 ID마다 하나 이상의 수용 기준을 이 표에 둔다. 수용 기준은 backlog 태스크의 AC로 그대로 내려간다(4.01) | 아래 §검증 방법 중 하나 | 테스트 로그 · 실측 기록 · 대조 기록 (5.02에 남긴다) |

- 모든 요구사항은 수용 기준을 하나 이상 가진다(0 문서 정보 §요구사항 표기).
- 수용 기준은 판정기를 코드로 쓸 수 있으면 반드시 테스트로 쓴다. 판정기를 코드로 쓸 수 있는 자리에 사람이 판정 루프에 앉지 않는다(1.02 P5).
- 수용 기준마다 결과(통과/실패)와 증거는 5.02 수용 기준 판정에 남긴다.

## 검증 방법

| 방법 | 대상 | 판정 | 도구 |
| --- | --- | --- | --- |
| 테스트 | 기능 요구사항(ORC · RAIL · TRL · BL) | 테스트 명령의 Exit Code. 0이면 통과 | 대상 저장소의 테스트 명령(예: `./gradlew test`), claude-code-agile-hooks 테스트 게이트 |
| 결정적 검사(DoD) | 태스크 공통 완료 기준 | 테스트 · lint 종료 코드. Verifier·DoD가 커밋마다 Reviewer와 병렬로 낸다 | `backlog task edit --check-dod` |
| AC 판정 | 태스크별 완료 조건 | Verifier·AC가 전체 AC + Reviewer 사이클 종료 후 1회 판정한다. 출력은 `{ac_id, verdict, evidence, blocking}` 스키마(3.04). 채점 기준은 TBD(Q-1) | `backlog task edit --check-ac` |
| 실측 | 도구 · 런타임의 사실, 품질 요구사항(NFR) | §실측 항목의 판정 기준 | 실행 기록, 트랜스크립트, Logger 기록 |
| 반증 측정 | 설계의 전제(1.02 원칙) | §반증 기준 측정 | M1 · M4가 남기는 태스크 기록 |
| 원문 대조 | 인용 · 외부 수치 | §인용 검증 | 원문 PDF · 대조본 |

Reviewer와 AC 판정 루프는 무한히 돌지 않는다. Reviewer는 최대 N회 왕복 후 사람을 호출하고, 판정 역할은 N회까지 재스폰한 뒤 넘으면 태스크를 blocked로 둔다. N은 TBD(Q-11).

### 테스트 추적

요구사항에서 내려온 AC와 카드의 비즈니스 규칙 · DoD는 테스트 표식으로 테스트에 이어진다 (2.02 테스트 표식).

| 사슬 | 잇는 것 |
| --- | --- |
| 요구사항 → 카드 | 카드 설명에 적은 요구사항 ID (BL-008) |
| 카드 AC #n → 테스트 | 테스트 이름 · 표시 이름 · 주석의 `<카드 ID>#<n>` |
| 카드 비즈니스 규칙 B<k> → 테스트 | 테스트 이름 · 표시 이름 · 주석의 `<카드 ID>#B<k>`. 규칙은 `(AC #<n>)`으로 AC에 걸린다 (BL-014) |
| 카드 DoD #n → 테스트 | 테스트 이름 · 표시 이름 · 주석의 `<카드 ID>#D<n>` (RAIL-022) |
| 테스트 파일 안 위치 | 요약 → AC/DoD 구역 → Coverage 구역. 표식은 AC/DoD 구역 안에만 둔다 (2.02 테스트 파일 구조) |
| 테스트 → 판정 | 테스트 명령의 Exit Code와 테스트 로그 (5.02) |

- AC와 비즈니스 규칙마다 표식을 단 테스트가 반드시 하나 이상 있다. 표식이 없는 AC · 규칙은 테스트로 판정할 수 없다.
- 표식의 존재는 claude-code-agile-hooks가 소스 편집 전(다음 AC와 그 규칙들)과 `Done` 전환 전(모든 AC · 규칙 · DoD)에 검사한다 (RAIL-019 · RAIL-022, 3.05 ADR-020).
- AC마다 Red → Green → Refactor로 구현한다 — 표식을 단 테스트가 먼저 실패하고(Red), 최소 구현으로 통과하고(Green), 정리한 뒤(Refactor) 커밋한다 (RAIL-011, 3.05 ADR-020). 훅은 표식의 존재만 보고 Red 단계가 실제로 실패했는지는 검사하지 않는다.
- AC · 규칙 · DoD 테스트 아래 Coverage 구역의 테스트로 커버리지 100%를 채운다 (NFR-017, 3.05 ADR-023).

## 실측 항목

| 항목 | 방법 | 판정 기준 | 실패 시 |
| --- | --- | --- | --- |
| 헤드리스 세션 간 메시징 | 터미널 두 곳에서 `claude -p` 헤드리스 프로세스를 띄우고, 세 번째 세션에서 `/list-agents`로 잡히는지 본다. bare 모드는 쓰지 않는다 | 두 헤드리스 프로세스가 목록에 나타나고 메시지를 받는다 | Logger의 WAL 디렉토리를 파일 메일박스로 재사용한다(폴링). Q-9 |
| backlog.md 필드 지원 범위 | `backlog task view <id> --plain`과 `--json` 출력을 의존성 · 마일스톤 · 상태 필드별로 대조한다 | 할당 조건에 쓸 필드와 출력 형식이 확정된다 | 할당 조건을 오케스트레이터의 계산 레이어로 보완한다(Q-3) |
| `claude` 프로세스 peak RSS · API 분당 한도 | 단일 `claude -p` 프로세스의 최대 상주 메모리와, 동시 실행 시 API 분당 한도에 걸리는 지점을 잰다 | 자원 상한 값이 숫자로 나온다 | — (값이 나올 때까지 동시성 상한의 자원 쪽은 TBD) |
| 토큰 계량 정확도 | 토큰 계량 컴포넌트(이름 미정)가 잰 커밋별 토큰 합계와 세션 트랜스크립트의 `message.usage` 총량을 같은 실행에서 비교한다 (측정 방식 `TBD(Q-18)`) | 두 값의 차이를 설명할 수 있다(무관한 대화 혼입 등) | 측정 방식을 확정으로 표시하지 않는다 |
| 조상 문서 프리픽스 캐시 | 같은 조상 체인(태스크 → 마일스톤 → 루트)을 읽는 역할들의 트랜스크립트 `message.usage`에서 캐시 읽기 토큰 비율을 잰다 | 캐시 읽기가 조상 문서 프리픽스를 덮는다 | 재로딩 비용이 정당화되지 않는다 — Q-2(비대칭 로딩)를 앞당긴다 |

backlog.md 실측(1.51.0)으로 확인된 사실은 다음과 같고, 할당 조건(2.03 BL 요구사항)은 이것을 따른다.

- `--plain`은 제목 · 상태 · 마일스톤 · AC 체크 여부 · 전이 의존 트리를 준다. `isReady` · `readiness`는 `--json`(schemaVersion 1)에만 있다.
- `isReady`는 "Done이 아니고 의존이 전부 Done"이라 In Progress 태스크도 참이다. 할당 조건은 `isReady`에 `status == To Do`를 함께 건다.
- `backlog draft promote`는 draft를 가리키는 의존성(DRAFT-n)을 승격된 태스크 ID로 바꾸지 않는다. draft 단계의 의존성은 승격 뒤 다시 건다.

## 반증 기준 측정

### 4역할 구조 (1.02 반증 기준)

| 항목 | 정의 |
| --- | --- |
| 비교군 | Implementer 단독 + self-review |
| 실험군 | 4역할(Implementer · Reviewer · Verifier · Logger, 판정 역할은 별도 프로세스) |
| AC 재작업률 | AC 하나가 Done이 되기까지 같은 AC에 대해 추가로 생긴 구현 커밋 수의 평균. 커밋 = 함수이므로 AC 개수가 최소 커밋 수다(1.02 P7) |
| 회귀 발생률 | Done이 된 태스크 이후에 실패로 바뀐 기존 테스트가 나온 태스크의 비율 |
| 자료 | 태스크별 성공/실패 · 재작업 · 회귀 기록(M1 · M4 실행 기록과 커밋 트레일러) |
| 판정 | 실험군이 두 지표를 유의미하게 낮추지 못하면 반증된다. "유의미"의 기준은 TBD(Q-11) |
| 반증 시 | Reviewer · Verifier를 Implementer 세션 안의 단계로 접는 안을 3.05에 올린다 |

- 경계선(어떤 태스크에 4역할을 붙이는가)은 외부 벤치마크에서 빌려오지 않는다. 외부 연구가 재는 것은 과제 정확도이고, 이 설계가 내세우는 것은 판단의 독립성이라 종속변수가 다르다(1.02 P9).

### 태스크 사이 병렬 구조

| 항목 | 정의 |
| --- | --- |
| 기록 | Logger가 스케줄 라운드마다 Ready 집합 크기 · 임계 경로 길이 · 폭 · 실제 동시 가동 수를 남긴다 |
| 길이 | 의존 간선과 결합 간선을 합친 DAG의 가장 긴 순차 체인의 노드 수 |
| 폭 | 위상 레벨별 노드 수의 최대값. 정확한 값은 최대 antichain(Dilworth 정리, 이분 매칭)으로 낸다 |
| 판정 | 실측된 폭이 거의 항상 1~2에 머물면 반증된다. "거의 항상"의 기준은 TBD(Q-11) |
| 반증 시 | 워커풀 · 세마포어 · 결합도 분석을 접고 순차 실행 하나로 둔다(3.05) |

### 논증 사슬의 끊김 지점

- 조상 문서 프리픽스 캐싱이 성립하지 않으면(§실측 항목), 별도 프로세스의 재로딩 비용이 정당화되지 않는다.
- 4역할 반증 측정이 이득을 보이지 않으면, 1.02 P1 · P2의 전제(같은 맥락의 자기검토는 오류를 놓친다)가 틀린 것이다.

## 인용 검증

- DOI 또는 arXiv가 붙은 인용만 근거로 쓴다. 블로그에서 온 수치는 원문을 확인한 뒤 원문에 없으면 삭제한다.
- 외부 문헌의 수치를 이 설계의 근거로 쓰기 전에 종속변수가 같은지 확인한다. 다르면 인용하지 않는다.
- 튜링 인용(1936 · 1948)은 원문 스캔 · 전사본과 Copeland 편 『The Essential Turing』(Oxford, 2004) 수록 원문을 페이지 단위로 대조한다. 출처와 대조 페이지는 부록 참고 문헌에 있다.
- 인용별 검증 상태는 부록 참고 문헌에서만 관리한다.
