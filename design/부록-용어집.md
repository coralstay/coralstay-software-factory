## 역할

| 용어 | 뜻 | 장 |
| --- | --- | --- |
| 4역할 · 4-role | Implementer · Reviewer · Verifier · Logger. 태스크마다(또는 계층 노드마다) 독립 프로세스로 부착된다. 노드마다 2~4개 등으로 달라질 수 있다 | 2.01 · 3.02 |
| Implementer | 유일한 writer. AC를 하나씩 구현하고 AC마다 커밋하며 backlog 상태를 바꾼다 | 2.01 |
| Reviewer | 읽기 전용. AC 커밋마다 판단(의견)을 내고 판정 스키마로 남긴다. 최대 N회 왕복 후 사람을 부른다 | 2.01 |
| Verifier | 읽기 전용. 최종 게이트. DoD(결정적 검사)와 AC(판단) 두 갈래로 나뉜다 | 2.01 · 1.02 P4 |
| Verifier·DoD | AC 커밋마다 Reviewer와 동시에 결정적 검사(테스트 · lint 종료 코드 등)를 한다 | 2.01 |
| Verifier·AC | 전체 AC + Reviewer 사이클이 끝난 뒤 1회 AC 판정을 한다. 판정 기준은 TBD(Q-1) | 2.01 |
| Logger | 관찰만 한다. 태스크 시작~종료 동안 Reviewer · Verifier의 WAL과 Implementer의 커밋 이력을 취합하고, 스케줄 라운드 계측을 남긴다 | 2.01 |
| 집계자(aggregator) | 마일스톤 노드에 붙는 에이전트의 성격. 자식에게 일을 배분하지 않고, Done인 자식의 산출물을 읽어 통합 검증 · 기록만 한다 | 3.02 |
| 판정 스키마 | Reviewer · Verifier 산출물 형식 `{ac_id, verdict, evidence, blocking}` | 3.04 |

## 계층과 백로그

| 용어 | 뜻 | 장 |
| --- | --- | --- |
| 프로젝트 · 마일스톤 · 태스크 · AC | backlog.md 계층. 마일스톤은 중첩되지 않는 평평한 목록이고, 깊이는 태스크의 `parentTaskId`(서브태스크)로 표현한다 | 2.02 |
| 계층 대응 | 태스크 = 파일 하나, AC = 함수 하나, 커밋 = 함수 하나(= AC 하나), 에이전트 배정 = 파일 하나 | 2.02 · 1.02 P7 |
| AC (Acceptance Criteria) | 태스크마다 다른 개별 완료 조건. 이 설계에서는 함수 하나에 대응한다. `backlog task edit --check-ac`로 체크한다 | 2.02 |
| DoD (Definition of Done) | 태스크 공통 완료 기준. `--check-dod`로 체크한다. Verifier·DoD가 결정적으로 검사한다 | 2.02 |
| 태스크 카드 | backlog.md의 태스크 마크다운 파일. Done 시점에 커밋을 읽은 요약(`--final-summary`)이 기록된다 | 2.02 |
| 상태 값 | backlog.md가 저장하는 세 값: To Do · In Progress · Done. 사람이 보는 보드는 이 세 값만 쓴다 | 2.02 |
| Ready | 실행 가능해진 태스크. 할당 조건은 `isReady` · `status == To Do` · 미병합 `task/<ID>` 브랜치 없음을 함께 건다 | 2.02 · 3.02 |
| readiness · isReady · isBlocked | backlog.md가 의존성에서 읽기 시점에 계산하는 파생 속성(`--json`에만 있다). `isReady`는 "Done이 아니고 의존이 전부 Done"이라 In Progress도 참이다. blocked는 상태 값이 아니다 | 2.02 |
| blockingDependencies · missingDependencies | readiness의 하위 필드. "의존 태스크가 안 끝나서 막힘"과 "의존 태스크가 안 보여서 막힘"을 구분한다 | 2.02 |
| 의존성(`--dep`) | `backlog task edit <ID> --dep <ID>`로 선언하는 태스크 간 선후 관계 | 2.02 · 3.02 |
| draft · promote | 백로깅에서 계획을 담는 임시 태스크(draft)와 그것을 실제 태스크로 승격하는 동작(promote). draft 단계에서 건 의존성은 승격 뒤 다시 설정한다 | 3.02 |
| 브리핑 | 백로깅 시작 시 기존 마일스톤 · 태스크를 확인하는 단계. 중복 생성을 막는다 | 3.02 |
| 백로깅 | 브리핑 → plan mode → draft → 승인 → promote의 루프. 단일 세션이며 진행 중 언제든 재진입한다 | 3.02 |
| 재진입 | 실행 중 새 마일스톤 · 태스크가 필요해져 백로깅 루프로 돌아오는 것. 정해진 조건에서만 트리거된다 | 3.02 |
| 부트스트랩 | 저장소당 1회의 고정 순서: git init → backlog.md CLI → `backlog init` → coding-agent-git-commit-tool → claude-code-agile-hooks | 3.02 |
| milestone archive | 상태 값이 아니라 마일스톤에 대한 별도 동작 | 2.02 |
| 구현 계획 | 태스크 카드의 `--plan` 항목. SOAP 노트 형식으로 쓰고, 카드의 AC · DoD와 함께 승격 · 착수의 전제가 된다 | 2.02 · 3.05 ADR-022 |
| SOAP | 구현 계획의 형식. Subjective(요청 · 배경) · Objective(확인한 사실) · Assessment(판단 · 접근) · Plan(구현 순서). 예약 제목 `### Subjective` · `### Objective` · `### Assessment` · `### Plan`을 이 순서로, 철자 그대로 쓴다 | 2.02 · 3.05 ADR-022 |
| 예약 제목 | 프로그래밍 언어의 키워드처럼 고정한 SOAP 절 제목. 훅이 이 제목으로 절을 찾고 작성 여부를 판정한다 | 2.02 |
| 계획 → 리뷰 → 계획 승인 | 착수 전 절차. 구현 계획 작성 → 사람의 리뷰 → 사람의 계획 승인. 그 뒤에만 착수한다(`task/<ID>` 브랜치) | 2.02 · 3.05 ADR-022 |
| 계획 승인 커밋 | 사람이 자기 키로 서명한 빈 커밋 `Plan-Approved: <태스크 ID>`. 계획 승인의 기록이고 훅이 착수(브랜치 생성 · 전환) 때 승인 게이트에서 확인한다 | 2.02 · 3.04 §1 |
| 승인 게이트 | `task/<ID>` 브랜치를 만들거나 그 브랜치로 전환할 때 계획 승인 커밋을 확인하는 검사. 유효한 서명(`%G?` = `G`)이고 서명자(`%GS`)가 `humanSigners`에 있어야 통과한다. claude-code-agile-hooks가 설치된 곳에서만 돈다 | 2.02 · 3.04 §1 · 3.05 ADR-022 |
| humanSigners | 승인 게이트가 사람으로 인정하는 서명자 principal 목록. 프로젝트 설정 키다. AI 전용 키의 principal은 넣지 않는다 | 3.04 §7 · 3.05 ADR-022 |
| 착수 | main에 병합되지 않은(`git cherry` 기준) `task/<ID>` 브랜치가 있는 상태. main에 착수 커밋을 만들지 않고, `-s "In Progress"`는 착수 판단이 아니라 시작 시각 기록이다. backlog.md 1.51.0 화면은 main에서 착수를 보이지 않는다 | 2.02 · 3.03 §4 · 3.05 ADR-014 |
| 단계별 커밋 | 카드 생애주기의 단계(draft 작성 · 승격 · 작업 순서 · 시작 기록 · 완료)마다 커밋하고 push하지 않는 규칙 | 2.02 · 3.05 ADR-023 |
| 작업 순서 파일 | 앞으로 할 일(draft · To Do)이 생기거나 다시 열리거나 의존이 바뀔 때마다 의존 그래프를 위상 정렬해 다시 계산하는 단계별 표 `backlog/work-order.md`. draft도 포함한다. 같은 단계는 병렬, 단계 사이는 순차다. 훅은 `draft promote`와 `task/<ID>` 브랜치 생성 · 전환 때 최신인지 검사하고, 오케스트레이터는 읽지 않는다 | 2.02 · 3.03 §4 |
| 테스트 표식 | 테스트가 카드의 무엇을 검증하는지 잇는 문자열. AC `<카드 ID>#<n>` · 비즈니스 규칙 `<카드 ID>#B<k>` · DoD `<카드 ID>#D<n>` | 2.02 · 4.02 |
| `(수동)` DoD | 텍스트 끝이 `(수동)`인 DoD 항목. 테스트로 검증하지 않는 항목이라 Done 게이트가 `<카드 ID>#D<n>` 표식을 요구하지 않는다. 표시가 카드에 드러나 사람이 계획 리뷰 · 승인 때 판단한다 | 2.02 · 3.05 ADR-023 |
| 테스트 파일 구조 | 테스트 파일 안의 고정 순서. 요약 헤더 `<ID>: <요약>` → `== AC/DoD ==` 구역 → `== Coverage ==` 구역 | 2.02 |

| RGR (Red → Green → Refactor) | AC 하나마다 실패하는 테스트(Red) → 통과하는 최소 구현(Green) → 정리(Refactor) → 커밋을 반복하는 구현 순서 | 3.05 ADR-020 · 4.02 |

| walking skeleton | Implementer 하나만 스폰 → 작업 → 토큰 집계 → 회수하는 첫 조각. 채점 기준을 요구하지 않는다 | 4.01 |

## 스케줄과 동시성

| 용어 | 뜻 | 장 |
| --- | --- | --- |
| 의존 간선 · 결합 간선 | 실행 순서 DAG의 두 간선. 의존 간선은 `--dep`, 결합 간선은 같은 파일 · 모듈을 건드리는 관계 | 2.04 · 3.02 |
| 파일 결합도 | 정적 분석으로 재는, 태스크들이 같은 파일 · 모듈을 건드리는 정도. 의존성이 없어도 결합돼 있으면 순차다 | 3.02 |
| 순차 체인 | 의존 또는 결합으로 묶여 순서대로 실행해야 하는 태스크 열 | 3.02 |
| 임계 경로 · 길이 | 가장 긴 순차 체인의 노드 수. 전체 소요의 하한이며 용량을 늘려도 줄지 않는다(Amdahl). 시간이 아니라 노드 수로 잰다 | 2.04 |
| 폭 | 동시 배정 가능한 태스크 수. 위상 레벨별 노드 수의 최대값으로 근사하고, 정확한 값은 최대 antichain(Dilworth 정리)이다 | 2.04 |
| 위상 레벨 | DAG를 위상정렬했을 때 같은 깊이에 놓이는 노드 묶음 | 2.04 |
| 최대 antichain | 서로 비교 불가능한(선후 관계 없는) 노드의 최대 집합. 폭의 정확한 값 | 2.04 |
| 스케줄 라운드 | Ready 집합을 큐에 넣는 한 번의 배정 주기. Logger가 Ready 집합 크기 · 임계 경로 길이 · 폭 · 실제 동시 가동 수를 남긴다 | 2.04 |
| 동시성 상한 | `min(그래프 폭, 자원 상한)`. 자원 상한은 `claude` 프로세스 peak RSS와 API 분당 요청 한도로 정한다 | 2.04 |
| work-conserving | 처리할 일감이 있는 동안 워커를 놀리지 않는 성질. 순차 체인의 admission이 독립 노드가 채울 빈 슬롯을 막지 않는다 | 2.04 |
| 워커풀 · Semaphore · 허가 | 동시에 도는 에이전트 수를 제한하는 용량 제한 풀. 스폰 시 허가를 얻고 회수 시 반납한다 | 3.03 §1 |
| 공유 버퍼 | 태스크별 버퍼 대신 오케스트레이터 전체에 두는 지연 · 비용 마진 하나(CCPM 차용) | 3.05 |
| 순차 다음 병렬 | 두 층위의 구분. 태스크 안: 구현은 순차, 판단은 병렬(판단의 독립성). 태스크 사이: 의존 · 결합만 순차, 나머지 병렬(처리량) | 2.04 |

| 프로그램 커밋 | 오케스트레이터 같은 프로그램이 직접 만든 커밋. 지금은 `AI_AGENT` · `CLAUDE_CODE_SESSION_ID` · `CLAUDE_PID`를 지우고 만들어 사람 커밋으로 보인다. 구분은 coding-agent-git-commit-tool GF-130 때 설계한다 | 3.03 §1 |
| 델타 커서 | 이미 처리한 트랜스크립트 줄 수를 저장해 그 이후 구간만 집계하는 커서. 커밋 훅이 토큰을 재던 방식(ADR-011, 폐기)의 패턴이고, 토큰 계량 컴포넌트가 쓸지는 미정 | 3.05 |
| 실패 투명성 | 측정 실패 시 틀린 값 대신 `unavailable (no-session-id / jq-not-installed / transcript-not-found / transcript-parse-failed)` 같은 사유를 남기는 패턴. 커밋 훅이 토큰을 재던 방식(ADR-011, 폐기)에서 왔다 | 3.05 |
| WAL | 역할 에이전트가 자기 디렉토리에 쌓는 파일 기반 영구 기록. 1차 기록이며 회수 후에도 남는 유일한 지속 장치 | 3.04 |

| 감사 추적(audit trail) | 누가 왜 그 행동을 했는지 남긴 기록. 모든 시도가 커밋으로 남는다 | 1.03 G-4 |
| 커밋 파편화 | 시도마다 커밋이 남아 사람용 이력을 읽기 어려워지는 문제 | 1.04 R-5 |
| 스쿼시 · 머지 커밋 | 완료한 태스크 브랜치를 합치는 두 방식. 스쿼시는 커밋을 하나로 합쳐 `git log`에서 지우고, 머지 커밋은 그대로 남긴다(Q-4) | 3.05 · 4.03 |
