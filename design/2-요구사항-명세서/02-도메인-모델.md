# 2.02 도메인 모델

계층은 backlog.md의 실제 구조(평평한 마일스톤 · 서브태스크로만 깊어지는 태스크 · AC)를 그대로 쓰고, 각 층을 코드 단위에 고정한다 — 태스크 = 파일, AC = 함수, 커밋 = 함수.

## 계층

![backlog.md 계층 — 마일스톤은 평평하고, 중첩은 태스크의 parentTaskId로만 표현된다](../diagrams/01-hierarchy.svg)

| 개체 | 정의 | backlog.md 대응 |
| --- | --- | --- |
| 프로젝트 | 대상 Git 저장소 하나. 계층의 루트 | `backlog init`으로 만든 `backlog/` 폴더 |
| 마일스톤 | 태스크 묶음. 중첩되지 않는 평평한 목록이다 | `milestone add / rename / remove / archive` |
| 태스크 | 실행 단위. 마일스톤에 속하지 않고 독립으로 있을 수 있다 | 태스크 카드(`backlog/tasks/*.md`) |
| 서브태스크 | 다른 태스크를 부모로 가진 태스크. 깊이가 필요하면 마일스톤이 아니라 서브태스크로 판다 | `parentTaskId` |
| AC | 태스크의 개별 완료 조건 | `--check-ac` |
| DoD | 모든 태스크에 공통인 완료 기준 | `--check-dod` |
| draft | 승인 전 태스크 후보. 승인되면 태스크로 승격된다 | `backlog draft create / promote` |
| 의존 | 태스크 사이의 선행 관계 | `backlog task edit <id> --dep <task-id>` |
| 결정 · 문서 | 태스크에 연결된 의사결정 · 참고 문서 | `--add-ref decision-N` · `--doc <path\|url>` |

## 태스크 카드 구성

태스크 카드는 설명 · AC · 비즈니스 규칙 · DoD · 구현 계획 · 메모 · 의존/참조로 이루어진다.

| 구성 요소 | 내용 | backlog.md 대응 |
| --- | --- | --- |
| 설명 | 무엇을 왜 하는가, 구현하는 요구사항 ID (BL-008) | `--description` |
| AC | 개별 완료 조건. AC 하나 = 함수 하나 (BL-007) | `--ac` · `--check-ac` |
| 비즈니스 규칙 | AC를 구현할 때 지켜야 할 도메인 규칙. 규칙마다 관련 AC 하나를 적는다 (BL-014) | 설명 안의 고정 절 `## 비즈니스 규칙` |
| DoD | 모든 태스크에 공통인 완료 기준 | `--dod` · `--check-dod` |
| 구현 계획 | SOAP 노트 형식(구현 계획 형식) + 카드의 AC · DoD. 승격 전에 작성하고, 착수 전에 사람이 리뷰하고 계획을 승인한다 (BL-015 · BL-017) | `--plan`(draft는 `draft edit <ID> --plan`) |
| 메모 | 진행 중 남기는 기록 | `--notes` |
| 의존/참조 | 선행 태스크 · 의사결정 · 문서 | `--dep` · `--add-ref` · `--doc` |

### 비즈니스 규칙 절

- 비즈니스 규칙은 설명 안의 `## 비즈니스 규칙` 절에 한 줄에 하나씩 `- B<k> (AC #<n>) <규칙>` 형식으로 적는다.
- `k`는 카드 안에서 1부터 매기는 규칙 번호이고, `n`은 그 규칙이 걸리는 AC 번호다. 규칙 하나는 AC 하나에만 걸린다.
- AC #n을 구현하기 전에 AC #n의 테스트와 함께, 관련 AC가 n인 규칙 B<k>의 테스트도 반드시 있어야 한다 (RAIL-019). `(수동)` AC는 AC 표식 테스트가 없어도 되지만 그 AC에 걸린 규칙의 테스트는 그대로 있어야 한다(아래 테스트 표식).
- 규칙이 없는 카드는 절을 두지 않을 수 있다. 그때 테스트 먼저 검사는 AC 표식만 본다.

### 구현 계획 형식

구현 계획(`--plan`)은 SOAP 노트 형식으로 쓴다. 아래 네 제목은 프로그래밍 언어의 키워드처럼 고정된 예약 제목이다. 이 순서로, 철자 그대로 쓴다. 대소문자 · 띄어쓰기 변형은 인정하지 않는다.

| 예약 제목 | 뜻 | 쓰는 내용 |
| --- | --- | --- |
| `### Subjective` | 주관적 정보 | 요청 · 배경: 유저가 무엇을 왜 원하는가 |
| `### Objective` | 객관적 정보 | 확인한 사실: 코드 · 측정값 · 현재 동작 |
| `### Assessment` | 평가 | 판단: 문제가 무엇이고 어떤 접근을 고르는가 |
| `### Plan` | 계획 | 구현 순서 |

- **작성됨** = 네 제목이 모두 있고, 이 순서이고, 같은 제목이 두 번 나오지 않고, 각 제목 아래 다음 제목 전까지 공백이 아닌 본문이 있다. 하나라도 어긋나면 작성되지 않은 것으로 본다 (BL-015).
- 카드에는 구현 계획과 함께 AC와 DoD가 하나 이상 있어야 한다. 셋이 모두 있어야 승격 · 착수할 수 있다 (RAIL-020).
- **계획 → 리뷰 → 계획 승인** — 구현 계획이 작성되고, 사람이 리뷰하고, 사람이 계획을 승인한 뒤에만 착수한다(`task/<태스크 ID>` 브랜치를 만든다, 아래 상태와 전이) (BL-017).
- 계획 승인은 사람이 자기 키로 직접 서명한 빈 커밋 `Plan-Approved: <태스크 ID>`로 기록한다(`git commit --allow-empty -S -m "Plan-Approved: <태스크 ID>"`). 훅도 Claude도 이 커밋을 만들지 않는다 (3.05 ADR-022, decision-2).
- **승인 게이트** — 착수 검사(아래)의 하나다. 훅은 HEAD에서 닿는 커밋 중 제목이 정확히 `Plan-Approved: <태스크 ID>`인 커밋을 찾는다. 그중 하나라도 유효한 서명(`%G?` = `G`)이고 서명자 principal(`%GS`)이 프로젝트 설정 `humanSigners`(3.04 §7)에 있어야 통과한다. 승인 커밋이 없을 때 · 서명이 유효하지 않을 때 · 사람이 아닌 서명자가 서명했을 때를 나눠 안내한다. 이 게이트는 claude-code-agile-hooks가 설치된 곳에서만 돈다 — 사람이 훅 없이 터미널에서 직접 만든 브랜치는 검사하지 않는다 (3.05 ADR-022, decision-3).
- **착수 검사 두 시점** — 착수 검사(작성된 구현 계획 · AC · DoD(RAIL-020), 승인 게이트, 최신 작업 순서 파일(RAIL-023))는 두 시점에 같은 내용으로 돈다. ① `task/<태스크 ID>` 브랜치를 만들거나 그 브랜치로 전환할 때(`git switch -c` · `checkout -b` · `switch` · `checkout` · `worktree add`, 사람이나 Claude 세션이 실행한 명령) ② `backlog task edit <태스크 ID> -s "In Progress"` 때. 오케스트레이터는 자기 Java 프로세스에서 `git worktree add`로 `task/<태스크 ID>` 브랜치를 직접 만들어 훅을 거치지 않는다. 그래서 그 워크트리 안의 에이전트 세션이 하는 `-s "In Progress"`가 에이전트 태스크의 검사 지점이다. 이 전환이 거부되면 오케스트레이터는 훅을 모르는 채 일반 '착수 안 됨' 실패로 거둔다 (3.05 ADR-022, decision-3).
- **두 키 구성** — 사람과 AI를 서명으로 가르려고 서명 키를 둘로 나눈다. Claude Code 세션은 AI 전용 키로만 서명한다. 사람 키는 ssh-agent 밖에 두어 서명할 때마다 암호를 입력하게 한다. 그래야 Claude 세션이 사람 키로 조용히 서명할 수 없다. 두 키는 `allowed_signers`에 서로 다른 principal로 올리고, 사람 principal만 `humanSigners`에 적는다 (claude-code-agile-hooks TASK-58 · decision-14).

### 테스트 표식

테스트가 어느 카드의 어느 AC · 규칙을 검증하는지는 테스트 이름 · 표시 이름 · 주석 중 하나에 넣는 표식으로 잇는다.

| 대상 | 표식 | 예 |
| --- | --- | --- |
| AC #n | `<카드 ID>#<n>` | `AO-27#1` |
| 비즈니스 규칙 B<k> | `<카드 ID>#B<k>` | `AO-27#B2` |
| DoD #n | `<카드 ID>#D<n>` | `AO-27#D1` |

- AC · DoD 항목 텍스트 끝이 `(수동)`이면 테스트로 검증하지 않는 항목이다. 그 항목에는 표식(AC `<카드 ID>#<n>` · DoD `<카드 ID>#D<n>`)을 요구하지 않는다 — 테스트 먼저 검사도 Done 게이트도 그 항목을 건너뛴다 (RAIL-019 · RAIL-022). AC에도 허용하는 것은 코드 저장소의 문서 전용 카드(예: agent-orchestrator AO-29)처럼 테스트를 쓸 수 없는 일을 가짜 테스트 없이 다루기 위해서다. 비즈니스 규칙에는 이 예외가 없다 — `<카드 ID>#B<k>` 표식은 그대로 요구한다. 표시가 카드에 드러나므로 사람이 계획 리뷰 · 승인 때 테스트 가능한 항목을 `(수동)`으로 뺐는지 판단한다.

예 — 카드 `AO-27`의 설명과 테스트:

```markdown
## 비즈니스 규칙
- B1 (AC #1) 예상 토큰이 구간 상한과 같으면 그 구간의 모델을 고른다
- B2 (AC #1) 예상 토큰이 음수면 거부한다
```

```java
@Test @DisplayName("AO-27#1 예상 토큰으로 모델을 고른다") void selectsModelByTokens() { ... }
@Test @DisplayName("AO-27#B1 구간 상한과 같으면 그 구간의 모델") void boundaryPicksSameTier() { ... }
@Test @DisplayName("AO-27#B2 음수 예상 토큰은 거부") void rejectsNegativeTokens() { ... }
```

### 테스트 파일 구조

JavaScript · TypeScript · Java · Python · C++ 테스트 파일은 카드의 AC · DoD를 바탕으로 쓰고, 파일 안 순서를 고정한다 (RAIL-022).

| 순서 | 구역 | 내용 |
| --- | --- | --- |
| 1 | 테스트 파일 요약 | 첫 주석 블록. 작업한 태스크 ID와 짧은 요약 |
| 2 | AC/DoD 구역 | AC · 비즈니스 규칙 · DoD 표식(`<카드 ID>#<n>` · `<카드 ID>#B<k>` · `<카드 ID>#D<n>`, `(수동)` AC · DoD는 표식 없음)을 단 테스트. 표식은 이 구역 안에만 둔다 |
| 3 | Coverage 구역 | 커버리지 100%(NFR-017)를 채우기 위한 테스트 |

- AC/DoD 구역은 Coverage 구역보다 앞에 있어야 한다. 구역이 빠지거나 순서가 어긋나면 위반이다.
- 요약 헤더는 파일의 첫 주석 블록(앞의 빈 줄 · `#!` 줄은 건너뛴다)에 태스크마다 `<ID>: <요약>` 한 줄로 쓴다.
- 구역 표식은 줄 전체가 주석인 `== AC/DoD ==`와 `== Coverage ==`이고, 각각 정확히 한 번 나온다. 주석 문법은 Python `#`, JavaScript · TypeScript · Java · C++ `//`(`/* ... */` 블록도 된다)이다.
- 새로 만드는 테스트 파일은 항상 검사한다. 이미 있는 파일은 헤더나 구역 표식이 하나라도 있으면 검사하고, 둘 다 없으면 유예한다(막지 않고 구조만 안내한다) (claude-code-agile-hooks TASK-61).

## 계층 ↔ 코드 대응

1.02 P7의 내용이다. 이 대응이 격리 규칙과 커밋 단위를 함께 정한다.

| 계층 | 코드 단위 | 결과 |
| --- | --- | --- |
| 태스크 | 소스 파일 하나 | 태스크 카드 하나가 소스 파일 하나에 대응한다 |
| AC | 함수 하나 | 한 태스크의 AC 개수 = 그 파일에서 건드릴 함수의 개수 |
| 커밋 | 함수 하나 (= AC 하나) | Implementer는 AC 하나를 끝낼 때마다 커밋한다. 토큰 계량 컴포넌트(이름 미정)가 재는 토큰도 함수 단위로 귀속하는 것이 목표다 (`TBD(Q-18)`). 그 전까지 토큰 실제치는 실행 한 번의 `session`만 있다 (3.04 §6) |
| 에이전트 배정 | 파일 하나 (= 태스크 하나) | 1태스크 1에이전트 1파일 1주제. 워크트리를 나누면 두 에이전트가 같은 파일을 만질 일이 구조적으로 없다 |

- 태스크당 최소 커밋 수 = 카드의 AC 개수이고, 배정 전에 셀 수 있다.
- 실제 커밋 수 = 최소 커밋 수 × 자가 치유 재시도 배수. 배수는 실측 대상이다 (`TBD(Q-4)`).
- 카드에 대응 소스 파일을 적는 형식은 `TBD(Q-13)`이다.

## 실행 개체

| 개체 | 정의 |
| --- | --- |
| 역할 | Implementer · Reviewer · Verifier(DoD · AC) · Logger. 권한 · 트리거 · 산출물은 2.01 |
| 에이전트 | 계층 노드 하나에 붙은 역할 인스턴스 하나 = `claude -p` 프로세스 하나. 태스크가 끝나면 회수된다 |
| 부착 | 에이전트가 계층 노드에 붙는 관계. 태스크뿐 아니라 마일스톤 등 계층 어느 노드에도 붙고, 노드당 개수는 2~4개 등으로 달라진다 (3.02 §5) |
| 마일스톤 노드 에이전트 | 매니저가 아니라 집계자다. 이미 Done인 자식의 산출물을 읽어 통합 검증 · 기록만 하고 작업을 배분하지 않는다 |
| 정책 | 노드 + 현재 상태 → (역할, 개수, 시점, 모델 · 프로바이더)를 돌려주는 함수 (3.04 §4) |
| 판정 | Reviewer · Verifier가 AC마다 남기는 `{ac_id, verdict, evidence, blocking}` (3.04 §5) |
| WAL | 역할별 디렉토리에 쌓는 파일 기반 영구 기록. 역할 사이 기록의 1차 원천이다 |
| 커밋 트레일러 | 커밋마다 붙는 `Task-Id` · `AI-Model` 등 (3.04 §2) |
| 실행 기록 | 실행 한 번의 결과 레코드(`runs.jsonl`) (3.04 §6) |
| 워크트리 | 태스크 전용 물리 작업 디렉토리 + `task/<id>` 브랜치. 이 브랜치가 main에 병합되지 않고 있으면 착수한 태스크다(상태와 전이) |
| 스케줄 라운드 | Ready 집합을 큐에 넣는 한 번의 결정. 길이 · 폭을 함께 기록한다 (2.04) |

## 상태와 전이

### 저장 상태

backlog.md가 쓰는 상태 값은 세 가지뿐이고, 보드는 이 세 값을 그대로 쓴다 (BL-001).

| 상태 | `--plain` 글리프 | 의존 그래프 안 표기 |
| --- | --- | --- |
| `To Do` | ○ | `[To Do]` |
| `In Progress` | ◒ | `[In Progress]` |
| `Done` | ✔ | `[completed]` |

| 전이 | 누가 | 조건 |
| --- | --- | --- |
| (draft) → `To Do` | 사람 승인 후 `draft promote` | 사람의 승인 (BL-011 · BL-012) + draft에 작성된 구현 계획(구현 계획 형식) · AC · DoD (BL-015 · RAIL-020). 승격하면 의존을 정리하고 작업 순서를 다시 계산해 바로 커밋한다 (BL-016) |
| `To Do` → `In Progress` | Implementer, 또는 사람 | 착수(`task/<태스크 ID>` 브랜치) 뒤 그 브랜치에서 옮긴다. 착수 판단이 아니라 실제 시작 시각을 카드에 남기는 기록이다. 다만 착수 검사(작성된 구현 계획 · AC · DoD + 승인 게이트 + 최신 작업 순서 파일)를 브랜치 생성 · 전환 때와 같은 내용으로 다시 거친다 — 오케스트레이터가 만든 브랜치는 이 전환에서 처음 검사된다 (BL-017 · RAIL-020 · RAIL-023, 위 착수 검사 두 시점) |
| `In Progress` → `Done` | Implementer | `--check-ac` · `--check-dod` 모두 통과 + `--final-summary` (BL-009) + 모든 AC · 규칙 · DoD 표식의 테스트(`(수동)` AC · DoD 항목은 제외) (RAIL-019 · RAIL-022) + 커버리지 100%(line + branch) (RAIL-006) |
| `In Progress` → `To Do` | 사람 | 착수 철회의 기록. 착수 자체는 미병합 `task/<태스크 ID>` 브랜치를 지워야 풀린다 |

**착수** = main에 병합되지 않은 `task/<태스크 ID>` 브랜치가 있다(로컬 · 원격 어느 쪽이든). 병합 여부는 `git cherry` 기준으로 보고, 병합 뒤 브랜치를 지운다 — squash 병합은 `git cherry`가 알아보지 못하므로 지우지 않으면 착수로 남는다(3.03 §1 주의점). main에 착수 기록 커밋을 따로 만들지 않는다. 오케스트레이터는 착수한 태스크에 배정하지 않으므로(ORC-005) 사람과 에이전트의 충돌은 브랜치 존재로 막힌다 (3.05 ADR-014, decision-3). backlog.md는 main에서 착수한 카드를 `To Do`로 보인다 — 사람은 `git branch -a --list '*task/*'`와 병합 여부로 착수를 확인한다 (3.03 §4 주의점).

### 전이와 커밋

카드 생애주기의 단계마다 커밋하고 push하지 않는다 (RAIL-021). 다음 단계 명령(`draft create` · `draft promote` · `-s "In Progress"` · `-s Done`)은 커밋되지 않은 `backlog/` 변경이 있으면 실행하지 않는다 (claude-code-agile-hooks TASK-59).

draft든 To Do 태스크든 앞으로 할 일이 새로 생기거나 다시 열리거나 의존이 바뀔 때마다 의존을 정리하고 작업 순서를 다시 계산해 바로 커밋한다(작업 순서에는 draft도 포함) (BL-016 · RAIL-023). 그래서 아래 3단계는 승격 뒤에만 오지 않고, draft 작성 · 재오픈 · 의존 변경 뒤에도 바로 온다.

| 순서 | 단계 | 커밋에 들어가는 것 |
| --- | --- | --- |
| 1 | draft 작성(`draft create` + `draft edit --plan`) | 새 draft 파일 하나 (RAIL-002) |
| 2 | 승격(`draft promote`) | 이름 변경과 `backlog/tasks/` 파일만 (RAIL-002) |
| 3 | 의존 정리 · 작업 순서(`--dep` + 작업 순서 재계산) | `backlog/work-order.md`와 의존을 고친 태스크 파일만 (RAIL-023) |
| 4 | 계획 승인(사람) | 사람 키로 서명한 빈 커밋 `Plan-Approved: <태스크 ID>` (BL-017) |
| 5 | 착수(`git switch -c task/<태스크 ID>` 등 브랜치 생성 · 전환) | 커밋 없음. 이때 훅이 착수 검사(계획 · AC · DoD, 승인 게이트, 작업 순서 파일)를 한다 (BL-017 · RAIL-020 · RAIL-023). 오케스트레이터가 `git worktree add`로 만든 브랜치는 훅을 거치지 않는다 |
| 6 | 시작 기록(`-s "In Progress"`) | 그 태스크 파일만 (RAIL-002). 착수 판단이 아니라 기록이지만, 훅이 5단계와 같은 착수 검사를 다시 한다 — 오케스트레이터 태스크는 여기서 검사된다 (BL-017 · RAIL-020 · RAIL-023) |
| 7 | 구현 | AC 하나마다 커밋 하나 — Red → Green → Refactor (RAIL-011). 메시지에 태스크 ID가 있어야 한다 (RAIL-025) |
| 8 | 완료(`-s Done`) | 그 태스크 파일만 (RAIL-002) |

- 6~8단계의 커밋은 `task/<태스크 ID>` 브랜치에 들어간다. 그 브랜치의 커밋은 제목 · 본문 · 트레일러 어딘가에 그 태스크 ID가 단어로 있어야 한다 (RAIL-025).

- 작업 순서 파일은 앞으로 할 일(draft와 미완료 태스크)의 의존 그래프를 위상 정렬한 단계(level)별 표다. 같은 단계는 병렬, 단계 사이는 순차다. 순환 의존이 있으면 만들지 않는다 (BL-016).
- 의존은 태스크 파일 frontmatter의 `dependencies`(`--dep`가 쓰는 값)에서 읽는다. Done이거나 `backlog/tasks/`에 없는 태스크에 대한 의존은 충족된 것으로 본다. 파일 첫 줄에는 미완료 태스크 ID와 의존으로 만든 해시를 적고, 훅은 이 해시가 맞지 않으면 낡은 파일로 본다 (claude-code-agile-hooks TASK-60).
- 훅은 작업 순서 파일을 `draft promote`와 착수 검사 두 시점(`task/<태스크 ID>` 브랜치 생성 · 전환, `-s "In Progress"`) 때 검사한다 (RAIL-023, decision-3). 지금 구현(TASK-60)은 미완료 태스크만 넣고 `draft promote` · `-s "In Progress"`에서 검사한다. draft 포함과 생성 직후 강제는 claude-code-agile-hooks TASK-64에서 구현하고, 브랜치 생성 · 전환 시점 검사도 아직 구현 전이다.

### 파생 속성

"blocked"는 상태 값이 아니라 의존성으로부터 계산되는 파생 속성이고, "archive"는 상태가 아니라 `milestone archive`류의 별도 동작이다.

| 속성 | 뜻 | 출처 |
| --- | --- | --- |
| `isReady` | Done이 아니고 선언한 의존이 전부 Done | `--json`의 `readiness`에만 있다 |
| `isBlocked` | 의존 태스크가 아직 안 끝나서 막힘 | 위와 같음 |
| `blockingDependencies` | 막고 있는 의존 목록 | 위와 같음 |
| `missingDependencies` | 존재하지 않는(보이지 않는) 의존 목록 | 위와 같음 |

- `isReady`는 "할당해도 된다"가 아니다. 이미 착수한 태스크도 `isReady: true`이고, main에서는 상태도 `To Do`로 보인다. 할당 조건은 `isReady ∧ status = To Do ∧ 미병합 task/<ID> 브랜치 없음`이다 (ORC-005). 오케스트레이터는 작업 순서 파일을 읽지 않는다 — 의존 순서는 `isReady`가 이미 보장한다.
- 오케스트레이터에 더 세밀한 구분이 필요하면 저장 상태를 늘리지 않고, 읽기 시점에 계산하는 비저장 레이어를 얹는다 (3.05 ADR-006). 그 레이어의 필요 여부는 `TBD(Q-3)`이다.
