# 2.04 품질 요구사항

동시성은 감으로 정하지 않고 센다 — 실제 동시성은 `min(그래프 폭, 자원 실측)`이고, 그래프의 길이 · 폭과 커밋당 토큰을 계속 기록해 병렬화와 4역할의 이득을 사후에 계산할 수 있게 한다.

## 병렬의 두 층위

"순차 다음 병렬"은 두 층위에서 따로 적용된다. 품질 요구사항은 둘을 섞지 않는다.

| 층위 | 순차인 것 | 병렬인 것 | 목적 |
| --- | --- | --- | --- |
| 태스크 안 | Implementer의 AC 구현 — 같은 브랜치 · 같은 파일이라 본질적으로 순차 | 커밋 하나마다 Reviewer와 Verifier · DoD가 서로 기다리지 않고 동시에 판단 | 판단의 독립성 |
| 태스크 사이 | 의존(`--dep`) 또는 파일 결합이 있는 태스크 체인 | 의존 · 결합이 없는 노드는 동시 배정 | 처리량 |

## 그래프 계측의 정의

의존 간선과 결합 간선을 합친 DAG를 위상정렬한 뒤 두 수치를 뽑는다.

| 수치 | 정의 | 계산 | 뜻 |
| --- | --- | --- | --- |
| 길이 | 임계 경로 — 가장 긴 순차 체인의 노드 수 | 노드별 실행 시간 예측이 없으므로 시간이 아니라 노드 수로 잰다 | 전체 소요의 하한. 용량을 늘려도 줄지 않는다(Amdahl's Law) |
| 폭 | 동시 배정 가능한 태스크 수 | 위상 레벨별 노드 수의 최대값으로 근사. 정확한 값은 최대 antichain(Dilworth 정리, 이분 매칭) | 그 시점에 의미 있는 동시성의 상한 |

- 폭보다 큰 용량은 채울 일감이 없어 낭비되고, 폭보다 작은 용량은 독립 노드를 놀려 work-conserving 제약(ORC-007)을 스스로 어긴다.
- 백로그가 계속 재생성되는 구조라 처리 용량이 늘면 처리량도 거의 선형으로 늘 수 있다(Gustafson's Law). 이 가정이 성립하는지는 NFR-002의 기록으로 확인한다.
- 같은 코드베이스를 동시에 건드리는 에이전트가 많을수록 서로 어긋날 위험이 조합적으로 커진다(Brooks, 1975 — 사람에 대한 경고이며 에이전트에 그대로 적용되는지는 동료심사로 증명되지 않았다). 그래서 동시 에이전트 수를 무한정 늘리지 않는다.

## 요구사항

| ID | 요구사항 | 목표 | 수용 기준(4.02) |
| --- | --- | --- | --- |
| NFR-001 | 동시 가동 에이전트 수의 상한은 반드시 `min(그래프 폭, 자원 상한)`이다. 자원 상한은 벤치마크가 아니라 `claude` 프로세스 1개의 peak RSS와 API 플랜의 분당 요청 한도 실측으로 정한다 (값 `TBD(Q-12)`) | G-5 | 4.02 |
| NFR-002 | 스케줄 라운드마다 Ready 집합 크기 · 임계 경로 길이 · 폭 · 실제 동시 가동 수를 반드시 기록한다 | G-5 | 4.02 |
| NFR-003 | 기록된 폭이 거의 항상 1~2이면, 워커풀 · Semaphore · 결합도 분석을 걷어내고 순차 실행 하나로 접는 결정을 3.05에 올려야 한다 (반증 조건) | G-5 | 4.02 |
| NFR-004 | 토큰 사용량은 반드시 커밋(= 함수) 단위로 관측할 수 있고, 태스크 단위 합계는 Done 시점의 태스크 카드에서 읽을 수 있다 (TRL-004 · ORC-021) | G-4 | 4.02 |
| NFR-005 | 측정할 수 없는 값은 틀린 값 대신 사유와 함께 "측정 불가"로 반드시 남긴다 — 조용한 오측정은 허용하지 않는다 | G-4 | 4.02 |
| NFR-006 | 태스크마다 성공 · 실패, AC 재작업 횟수, 회귀 발생을 반드시 기록한다 — 4역할 적용 경계선과 1.02 반증 기준은 이 기록으로만 정한다 | G-7 | 4.02 |
| NFR-007 | 부착 시 읽는 조상 문서 프리픽스에는 타임스탬프 · 세션 ID 같은 가변값을 반드시 섞지 않는다 — 프롬프트 캐싱이 성립해야 독립 프로세스의 재로딩 고정비가 상쇄된다 | G-5 | 4.02 |
| NFR-008 | 회수 뒤에는 역할 프로세스 · 자손 · 동시성 허가가 하나도 남지 않아야 한다 (정상 종료 후 고아 자손 `TBD(Q-17)`) | G-2 | 4.02 |
| NFR-009 | 오케스트레이터 동시성은 virtual thread 위의 블로킹 호출(`Process.waitFor()`)로 써야 한다 — 비동기 콜백 없이 코드를 단순하게 유지한다 | G-5 | 4.02 |
| NFR-010 | 오케스트레이터는 외부 런타임 의존성 없이 Java 25 표준 라이브러리로 동작해야 한다 | G-5 | 4.02 |
| NFR-011 | 내장 DB와 외부 연산 레이어의 동시 I/O 커넥션 수는 사람이 상한을 설정할 수 있어야 한다 | G-5 | 4.02 |
| NFR-012 | 고빈도로 바뀌는 상태 · 작업 큐 · 프롬프트 캐시는 디스크 마크다운이 아니라 임베디드 DB(SQLite · H2)가 받아야 한다. Git은 최종 영속화만 맡는다 | G-5 | 4.02 |
| NFR-013 | 수직 확장 시 에이전트 프로세스마다 CPU affinity(`taskset` · `cgroups`)를 지정할 수 있다 | G-5 | 4.02 |
| NFR-014 | 수직 확장 시 에이전트 작업 공간을 `tmpfs`(RAM 디스크)에 둘 수 있다 | G-5 | 4.02 |
| NFR-015 | 수직 확장 시 virtual thread 캐리어 스레드 풀 상한(`jdk.virtualThreadScheduler.parallelism` · `maxPoolSize`)을 코어 수에 맞춰 설정할 수 있다 | G-5 | 4.02 |
| NFR-016 | claude-code-agile-hooks의 훅은 서로 import하지 않아야 한다 — 한 훅의 버그가 다른 훅에 번지지 않는다 | G-3 | 4.02 |

## 수직 확장 병목

단일 JVM에서 에이전트를 수백 개 단위로 띄울 때의 커널 · 파일 시스템 병목과 대응이다. NFR-013 ~ NFR-015의 근거다.

| 병목 | 원인 | 대응 |
| --- | --- | --- |
| 프로세스 포크 컨텍스트 스위칭 | 한 JVM에서 `ProcessBuilder`로 `claude` 프로세스를 동시에 100개씩 `fork/exec`하면 커널 스케줄러가 컨텍스트 스위칭에 CPU를 쓴다 | 에이전트마다 CPU affinity 지정 (예: #105는 코어 0~3, #106은 4~7) |
| 디스크 I/O · 파일 시스템 락 | 수십 개 워크트리에서 동시에 `gradlew test`를 돌리면 디스크 컨트롤러와 저널링 락에서 대기가 생긴다 | 작업 공간(`../isolated-agent-...`)을 `tmpfs`에 마운트. 내장 DB도 SQLite `:memory:` 모드 |
| 캐리어 스레드 고갈 | virtual thread가 `waitFor()`나 `ReentrantLock` 구간에서 캐리어 스레드를 붙잡는 pinning이 대규모 부하에서 누적된다 | 예: `-Djdk.virtualThreadScheduler.parallelism=128` · `-Djdk.virtualThreadScheduler.maxPoolSize=256` (128코어 기준) |
